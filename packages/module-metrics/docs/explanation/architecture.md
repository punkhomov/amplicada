# Архитектура

## Конвейер

```
клиентский трекер (floating)        http:observer (core)      обёртка pg-pool
   │  page.view / ui.* пачками            │ роуты RED             │ SQL fingerprint
   ▼                                      ▼                       ▼
POST /api/metrics/collect  →  валидация  MeasurementBuffer (10 с окна пред-агрегации)
   │                                        │                          │
   ▼                                        ▼                          ▼
metrics.events (партиции)          metrics.points + series     slow_queries + fingerprints
   ▲                                        │                          │
   │  metrics.emit (модули)                 │                          │
   │  metrics:definitions — реестр          │                          │
   └──── /events, /catalog, /definitions, /series ◀── админ-приложение ──▶ /routes, /sql, /slow-queries
                                                          │
                                              metrics:panels (панели модулей)
```

Бизнес-события модулей идут тем же путём, что и клиентские: `emit` кладёт событие в буфер,
флаш пишет его в `metrics.events`. Определения и панели — код-контрибуции: первые живут в
core-реестре расширений, вторые — в frontend-сервисе модуля метрик.

События, записанные в журнал, для включённых выходов попадают в durable-очередь
(`metrics.outbox`): диспетчер раз в 15 секунд шлёт батчи адаптерам (webhook), ретраит
5xx/429 с backoff и ведёт журнал доставки; 4xx уходит в DLQ. Выключенные выходы ничего не
получают, а их строки не теряются.

Ошибки приезжают обычными событиями `error.frontend`: сервер считает fingerprint
(тип + маршрут + кадры стека) и обновляет `metrics.error_issues` только по вставленным
событиям. Web Vitals — единственный случай «dual write»: событие `web_vital.*` остаётся в
журнале (рейтинги, контекст), а значение дополнительно идёт в гистограмму, откуда берутся
p75/p95 без перебора сырых событий.

Стор — единственный источник правды: внешние выходы (Яндекс.Метрика, webhook) появятся
позже как подписчики и не влияют на сбор. В закрытом контуре выходов просто не будет.

## Почему партиции, а не `DELETE`

События — append-only поток. Партиционирование по месяцу даёт дешёвое удаление
(`DETACH ... CONCURRENTLY` + `DROP`), меньший vacuum и предсказуемый размер. Retention
настраивается, задача `metrics.maintenance` доводит его до конца.

## Почему polling, а не SSE

Аналитика не требует секундной свежести; в платформе SSE используется для диалогов
(support-chat) и логов задач. Решение владельца — периодическое обновление; вернуться к SSE
можно, если появится сценарий «живой поток ошибок».

## События и измерения

План различает два класса данных: события (семантика, актор, `attributes` jsonb) и
измерения (числовые серии с гистограммами, OTel-подобные). Сейчас реализован только первый;
второй появится на этапе 02 за своим контрактом `MetricsStore`.

## Ограничения

- Нет графиков/трендов: вкладки «Роуты» и «SQL» — таблицы за период.
- SQL вне HTTP-запроса не привязан к роуту (`<unattributed>`).
- Алертов и внешних доставок нет до этапов 04–05 плана.
- `pg_stat_statements` как доп. источник SQL-метрик не подключён.
