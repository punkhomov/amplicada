# Псевдонимизация

В журнале нет логинов, идентификаторов пользователя, IP и User-Agent. Актор и сессия
представлены псевдонимами:

```
actor_hash   = HMAC-SHA256(salt, "analytics:" + identity_user.id)
session_hash = HMAC-SHA256(salt, "session:"   + sessionId)
```

Назначения (`analytics`, `errors`) разделены: один и тот же человек в аналитике и в ошибках
имеет разные псевдонимы, сшить профиль между назначениями нельзя.

## Почему HMAC, а не SHA-256

Голый хеш перебирается по словарю идентификаторов. HMAC с секретом делает перебор
бессмысленным без ключа, а сам ключ хранится **вне БД** — этого требует приказ РКН № 140
(метод «введение идентификаторов»): исходные данные и ключ не хранятся совместно.
Секрет читается core-сервисом `secrets` из `AMPLICADA_METRICS_PSEUDONYM_SALT`; модуль
никогда не обращается к окружению напрямую.

## Что это даёт продуктово

- уникальные пользователи и сессии считаются (`actor_hash`, `session_hash`);
- сырой URL по умолчанию не сохраняется — в данных только шаблон маршрута;
- `store_raw_urls` можно включить для отладки, понимая, что query-параметры могут содержать
  персональные данные.

## Ограничения

- Ротация соли (например, суточная для аналитики) пока не реализована — этап 06 плана.
- Без переменной окружения модуль генерирует процессную соль: псевдонимы стабильны только
  внутри процесса (в логе будет warning).
- Rate-limit и opt-out/DNT на клиенте ещё не сделаны.
