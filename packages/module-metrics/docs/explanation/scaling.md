# Масштаб, лимиты и путь на ClickHouse

Оценки и защитные механизмы модуля. Числа — расчётные (на основе размеров строк Postgres
и практик из `ref/plans/2026-09-18-metrics-module/02-offline-stack.md`), не замеры нагрузки.

## Оценки объёма

| Профиль | Оценка |
|---|---|
| 5000 пользователей, 40 событий/день | ~200K событий/день (~2–20/с) |
| Месячная партиция событий | ~6M строк ≈ 1.5–2 ГБ |
| 100M событий с индексами | ~20–27 ГБ |
| Точки измерений | одна строка на (серию, окно 10 с) — доли процента от сырых наблюдений |
| Роллап-таблиц нет | перцентили считаются из гистограмм, отдельных rollup-таблиц пока не заводили |

## Действующие лимиты

| Механизм | Значение | Где |
|---|---|---|
| Батч приёма | ≤ 500 событий, событие ≤ 8 КБ | `validation.ts` |
| Атрибуты | ≤ 32 ключей, строки ≤ 256 символов | `validation.ts` |
| Приём | `ingestEventsPerMinute` (600 по умолчанию) → 429 | `rate-limiter.ts` |
| Серии измерений | ≤ 2000 за окно; лишние — в серию `__overflow` | `measurement-buffer.ts` |
| Retention | события 30 дн., точки 30 дн., медленные SQL 7 дн., роллапы нет; алерты-история 30 дн. | `metrics.maintenance` |
| Партиции | текущий + 2 месяца вперёд, `DETACH CONCURRENTLY` + `DROP` | `partitions.ts` |
| Sinks | батч ≤ 200 событий (webhook), доставка ≤ 6 попыток | `sinks/` |
| Экспорт | ≤ 20 000 строк на CSV | `exportEvents.csv` |

Ретеншн удаляет только партиции; старые серии `metrics.series` остаются (маленькая таблица,
но при смене кардинальности растёт — при большом объёме добавить очистку «серия без точек за N
дней»).

## Когда уходить на отдельное хранилище

Триггеры (после включённых роллапов, которых пока нет):

- > 100–500M сырых событий или > 50–100 ГБ горячего слоя;
- многонедельные `GROUP BY` по атрибутам в дашбордах, p95 > 1–2 с;
- > 10–20 одновременных аналитических читателей;
- maintenance перестаёт укладываться в окно.

Путь: реализация `MetricsStore` для ClickHouse за существующим контрактом (сбор и UI не
меняются), CDC/dual-write сырых событий, Postgres остаётся system of record для настроек,
правил и очередей. Пока это **не сделано** и не начато.

## Что мониторить

Вкладка «Здоровье»: события за час по видам, размер таблиц, число серий, очередь доставки,
алерты, runtime-счётчики (буфер, overflow, ошибки флаша, последние флаш/доставка). Это
единственная панель эксплуатации; self-метрики в собственный журнал не пишутся (иначе
обратная связь).

## Ограничения

- Cap серий — на окно флаша, а не глобальный: за длинную историю уникальных серий может
  накопиться больше. Глобальная проверка потребовала бы запроса в БД на каждое измерение.
- Диспетчер очереди не защищён от мультипроцессного запуска (`ROLE=worker`).
- Нет сэмплирования измерений (только SQL-замеры по `sampleSqlRate`).
- Точные перцентили по всей истории невозможны — только интерполяция по гистограммам.
