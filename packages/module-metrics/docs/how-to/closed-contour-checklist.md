# Подключить сбор в закрытом контуре

Модуль спроектирован offline-first: внешних вызовов нет ни одного, все данные остаются в
Postgres узла. Чек-лист для развёртывания on-prem.

1. **Соль псевдонимизации.** Задайте `AMPLICADA_METRICS_PSEUDONYM_SALT` (≥ 16 символов,
   случайное значение) в окружении API. Без неё модуль поднимет процессный случайный секрет
   и напишет warning — псевдонимы перестанут быть стабильными между рестартами.
   Соль хранится вне БД — это требование 152-ФЗ к ключу обезличивания.
2. **Сбор включён.** `GET /api/metrics/context` → `enabled: true`. Выключатель — общий
   kill-switch: трекер молчит, приём отвечает `disabled: true`.
3. **Retention.** Задайте срок хранения и включите расписание задачи `metrics.maintenance`
   в `/admin/tasks` (см. [configure-retention-and-sampling.md](./configure-retention-and-sampling.md)).
4. **Сырые URL выключены.** `store_raw_urls = false` (по умолчанию): в данных только шаблон
   маршрута. Включайте только осознанно и на короткий срок.
5. **Проверка отсутствия исходящих вызовов.** Модуль не имеет исходящего HTTP-клиента;
   внешние выходы (Яндекс.Метрика и т.п.) появятся только на этапе 05 плана и будут
   выключены по умолчанию.
6. **Бэкапы.** Это единственный экземпляр данных журнала: внешней копии нет by design.
   Включите `metrics.events` в обычный бэкап Postgres (или исключите, если журнал не ценен).

## Ограничения

- Rate-limit ингестии (Redis token bucket) и opt-out/DNT на клиенте ещё не сделаны —
  этап 01/06; до этого защита ограничена размерами батча и события.
- Алертов нет; наблюдение за объёмом журнала — вручную (размер таблицы/партиций).
