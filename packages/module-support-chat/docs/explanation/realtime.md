# Как доставляются сообщения

Контекст: чат должен показывать новые сообщения без перезагрузки страницы, при этом
API может работать несколькими процессами (`ROLE=web|worker`, реплики).

## Устройство

1. После успешной записи сообщения маршрут публикует событие в Redis-канал
   `support-chat:events` (`src/backend/services/event-bridge.ts`).
2. Каждый процесс API при старте подписывается на канал (`start()` модуля) и реэмитит
   события в локальный `eventBus` — включая процесс, который сам опубликовал событие.
3. SSE-маршруты слушают локальный `eventBus` и пишут события своим подключённым клиентам:
   пользователь получает только свой тред, поддержка — все.
4. На клиенте `useSupportChatEvents` открывает `EventSource` и инвалидирует
   React Query-кэш `['support-chat']`; данные перезапрашиваются без задержки.

Редкий `refetchInterval` (60 секунд) остаётся страховкой на случай обрыва SSE —
браузерный `EventSource` переподключается сам.

Почему через Redis, а не напрямую из `eventBus` процесса: прямой вариант доставлял бы
события только клиентам той же реплики. Отдельный канал модуля (по образцу
`TaskEventBridge` в core) делает доставку корректной при любом числе процессов.

## Следствия для потребителя

- Никаких действий для realtime не требуется: виджет и админ-приложение уже подписаны.
- Если модуль выключен из состава приложения, канал и события не создаются.
- При `stop()` процесса подписка снимается до закрытия Redis (`shutdown.ts` в core).

## Что осознанно не поддерживается

- WebSocket и двусторонний транспорт: отправка идёт обычным POST.
- Push-уведомления и почтовые оповещения — в этом модуле их нет.
