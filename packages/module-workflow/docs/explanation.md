# Как устроен module-workflow

Этот документ объясняет **почему** движок спроектирован именно так — модель токенов, границы
транзакций, конкурентность. За списком полей/эндпоинтов — в [reference.md](./reference.md), за
практическими рецептами — в [how-to.md](./how-to.md).

> Пакет `packages/module-workflow` реализует общий BPM-движок: шаблон процесса (`workflows`) →
> опубликованная версия графа (`workflow_versions.config`, JSON) → запущенный экземпляр
> (`process_instances`), который движется по графу до `end`-ноды. Домен (HR, будущие assessment/appraisal
> и т.п.) не встроен в движок — он подключается через делегатов (см. [reference.md](./reference.md#registry)).

## Модель токенов: от "одна текущая нода" до "N активных токенов"

Исторически (и для 95% реальных процессов) у экземпляра ровно одна текущая позиция в графе —
`process_instances.currentState`. Но нода-шлюз (`gateway`) может работать в трёх режимах:

| `mode` | Семантика | Множит токены? |
|---|---|---|
| `exclusive` (по умолчанию) | Первое совпавшее условие на исходящих рёбрах, иначе `isDefault`. Классический if/else. | Нет |
| `parallel` (AND) | **Все** исходящие рёбра активируются одновременно. | Да — split |
| `inclusive` (OR) | Активируются рёбра, чьё условие совпало (может быть несколько), иначе `isDefault`. | Да — split |

Чтобы не городить два параллельных движка (один для простого случая, другой — для parallel/inclusive),
движок обобщён на уровне данных: экземпляр процесса — это не "текущая нода", а **множество активных
токенов** в `process_instance_tokens`. Обычный последовательный граф — это всегда ровно один токен с
`branchGroupId = null`, который никогда не форкается — в коде `advanceToken()`/`executeAction()` для
этого случая нет отдельной ветки, работает тот же путь, что и для параллельного графа с N=1.

- **Split** (`forkToken()` в `engine.ts`) — токен, дошедший до `parallel`/`inclusive`-шлюза с
  >1 исходящих рёбер, помечается `consumed`; на каждое активированное ребро создаётся новый токен той
  же `branchGroupId`-группы (bookkeeping — строка в `process_instance_forks` с `expectedCount`).
- **Join** — токен, дошедший до шлюза с >1 входящих рёбер того же режима, тоже помечается `consumed`;
  когда `consumed`-токенов группы становится `expectedCount` — создаётся один токен-продолжение, и
  граф идёт дальше уже без разветвления.
- `process_instances.currentState`/`currentStateCode` остаются денормализацией для UI/отчётов, которым
  не нужна полная картина — при единственном активном токене это точное состояние; при активном форке
  это **лейбл внешнего split'а**, не факт (см. `syncCurrentStateLabel` в `engine.ts`). Авторитетный
  источник при форке — `WorkflowEngine.loadActiveTokens()`.

Split и join обязаны образовывать пару "один вход — один выход" (SESE-регион): валидация при публикации
(`resolveParallelBlock` в `graph-analysis.ts`) отклоняет графы, где ветки split сходятся в разных нодах,
где `end` встречается внутри незакрытого блока, или где split/join смешаны в одной ноде.

**Сознательно не реализовано в v1** (см. `ref/plans/2026-07-22-workflow-parallel-gateway.md`):
компенсация/авто-отмена соседних веток при reject одной из них (reject маршрутизирует только свою
ветку до join), циклы внутри одного parallel-блока, `cancelProcessInstance` для всего экземпляра.

## Транзакционные границы

Каждый мутирующий метод движка (`publishVersion`/`startProcess`/`executeAction`) атомарен: либо
открывает свою транзакцию, либо (если вызван с `opts.db`) выполняется в транзакции, переданной
потребителем — это позволяет модулю вроде `module-hr-request` записать свою заявку и стартовать
процесс одним атомарным коммитом. Движок savepoint'ов не создаёт — переданный `db` обязан уже быть
транзакцией.

Внутри этой границы гарантированно атомарны: создание/перемещение токенов, запись `workflow_tasks`,
`workflow_audit_log`, обновление `process_instances`. **Не входят в границу транзакции:**

- **`serviceTask`-делегаты** (`ServiceTaskProvider.execute`) вызываются синхронно, *внутри* транзакции
  движка — получают `ctx.db`. Их side-эффект (внешний HTTP-вызов и т.п.) откат транзакции **не
  отменяет** — стандартное ограничение BPM-движков, делегат должен быть по возможности идемпотентным.
- **`asyncTask`/hook-делегаты** исполняются вне транзакции движка вообще, через таблицу
  `workflow_automation_jobs` (см. ниже) — к моменту их выполнения транзакция, создавшая джобу, уже
  закоммичена. `ctx.db` им не передаётся (его физически не существует к этому моменту).

## Асинхронная автоматика: eager-диспатч + периодический воркер

`asyncTask`-нода и `postEnterHooks` не блокируют транзакцию движка ожиданием внешнего вызова — вместо
этого создаётся строка в `workflow_automation_jobs`, а сам вызов делегата происходит по одному из двух
путей:

1. **Eager**: сразу после коммита транзакции движок вызывает `runAutomationJob(jobId)` напрямую (не
   дожидаясь тика воркера) — типичная задержка до старта автоматики порядка миллисекунд.
2. **Periodic fallback** (`WorkflowAutomationWorker`, зарегистрирован в `task-scheduler` как
   `workflow-automation-worker`): подбирает `pending`-джобы, чей `nextAttemptAt` уже наступил (ретраи
   после ошибки), и восстанавливает джобы, зависшие в `running` дольше 5 минут (падение процесса между
   claim'ом и завершением — типичный крах-сценарий, для которого eager-путь в принципе не сработает:
   некому опубликовать событие, если сам публикатор упал).

   **Важно:** таск-планировщик регистрирует эту задачу **неактивной по умолчанию** (`active: false` —
   дефолт колонки `scheduled_tasks.active` в `platform-core`). Без ручной активации в админке
   task-scheduler'а восстановление после краша и ретраи по расписанию не работают — работает только
   eager-путь. Для процессов, целиком состоящих из `serviceTask`/синхронных шагов, это не критично; для
   `asyncTask`/hooks — нужно включить задачу явно.

Claim джобы — условный `UPDATE ... WHERE status = 'pending'` (не `FOR UPDATE SKIP LOCKED`): если строка
уже забрана другим воркером или ещё не видна текущему соединению (eager-триггер с ещё не
закоммиченной внешней транзакцией), `UPDATE` просто не находит совпадений — это не ошибка.

`route`-джоба (asyncTask) при успехе продолжает `advance()`/`settle()` графа — токен трогается только
через `completeAutomationJob`, который проверяет, что токен всё ещё активен и стоит на ноде джобы,
прежде чем двигать его дальше (защита от повторного/устаревшего вызова). `hook`-джоба (postEnterHooks)
ничего не маршрутизирует — успех/неудача влияют только на статус самой джобы.

## Конкурентность и блокировки

Движок избегает явных advisory-локов — вся сериализация идёт через `SELECT ... FOR UPDATE` на
обычных строках:

- `executeAction` берёт `FOR UPDATE` последовательно: задача → экземпляр → токен. Это сериализует два
  конкурентных действия над одним экземпляром (даже на разных токенах активного parallel-блока) — цена
  корректности здесь в пропускной способности: при parallel-блоке с сотней токенов сто одновременных
  кликов сериализуются через одну строку `process_instances`.
- Join (`joinToken`) берёт `FOR UPDATE` на bookkeeping-строку `process_instance_forks` — это и есть
  защита от classic lost-wakeup: без неё два токена одной группы, финиширующих в параллельных
  транзакциях, могли бы оба увидеть "ещё не все пришли" и ни один не продолжить процесс.
- `completeAutomationJob` берёт `FOR UPDATE` на саму джобу, затем на экземпляр и токен — не проверяет
  явно `job.status`, но комбинация лока на строке джобы (сериализует любые два одновременных вызова для
  одного `jobId`) и проверки `token.nodeId === job.nodeId` после лока делает двойное продвижение графа
  невозможным даже без явной проверки статуса (подробный разбор — в
  ревью).

## Версии неизменяемы

`publishVersion` создаёт новую строку `workflow_versions` (никогда не мутирует существующую) и
переключает `workflows.currentVersionId`. Уже запущенные экземпляры хранят свой
`workflowVersionId` и продолжают жить по **замороженной** конфигурации — публикация новой версии не
меняет поведение уже идущих процессов, только тех, что стартуют после публикации. Это и позволяет
редактировать граф в продакшене без риска сломать процессы, которые уже "внутри" старой версии.

## Модель ошибок

Все проверки движка бросают типизированные ошибки (`errors.ts`), которые `setup.ts` мапит в HTTP-статусы
(`WorkflowValidationError`/`InvalidActionError`/`ValidatorFailedError` → 400, `ForbiddenActionError` →
403, `WorkflowNotFoundError` → 404). Программные потребители (например `module-hr-request`, вызывающие
движок in-process) ловят те же классы напрямую, без похода через HTTP.

## Известные ограничения v1 (сознательные, не забытые)

## О документах в `ref/`

`ref/plans/` для этого модуля описывают **намерения и историю решений** на момент
написания — полезны для понимания "почему так", но не всегда отражают код в текущем состоянии:
некоторые пункты плана помечены `draft`, хотя реализованы, другие описывают функциональность, которая с
тех пор изменилась в последующих итерациях. Если план и код расходятся — источник истины всегда код;
эти docs/*.md написаны по прочтению исходников `src/`, а не по пересказу планов.
