# Постройте свой первый процесс

Пошаговое введение в `module-workflow`: с нуля до запущенного и завершённого процесса, без написания
кода — только визуальный редактор и встроенный делегат `process-initiator` (возвращает того, кто
запустил процесс, — единственный делегат, зарегистрированный самим движком, см.
`backend/delegates.ts`). К концу у вас будет рабочий цикл "заявка → одобрение → завершение" и понимание,
где что искать дальше — в [how-to.md](./how-to.md) (реальные задачи) и [reference.md](./reference.md)
(полный список полей и эндпоинтов).

## Предварительные условия

- Монорепозиторий запущен (`pnpm dev` из корня — `apps/api` на `:3000`, `apps/web` через Vite).
- Вы залогинены в приложении под пользователем с доступом к админке (`module-admin`).
- Открыты инструменты разработчика браузера (консоль) — понадобится один `fetch()`-вызов, для которого
  проще не поднимать отдельный HTTP-клиент, а воспользоваться уже аутентифицированной cookie-сессией
  вкладки.

## Шаг 1 — создайте шаблон процесса

Откройте документ "Процессы (шаблоны)" в админке (`module-admin` → раздел workflow, документ
`workflow`, зарегистрирован в `backend/documents/workflow.ts`) и создайте новую запись:

| Поле | Значение |
|---|---|
| Код | `demo-approval` |
| Название | `Демо: согласование` |
| Активен | ✓ |

**Проверка**: запись появилась в списке документа со статусом "Активен".

## Шаг 2 — постройте граф в визуальном редакторе

Откройте вкладку "Редактор графа" карточки только что созданного процесса (ведёт на
`/admin/workflows/{id}/editor`). По умолчанию редактор уже содержит связку `start → end` — этого
недостаточно, добавим шаг согласования между ними:

1. Перетащите из палитры ноду **"Задача пользователя"** на холст между `start` и `end`.
2. Удалите прямое ребро `start → end` (выделите его и нажмите Delete).
3. Соедините `start` → новая нода → `end`, потянув за точки на краях нод.
4. Кликните на новую ноду и в панели свойств справа:
   - **Исполнитель (делегат)** → выберите `Инициатор заявки` (`process-initiator`) — единственный
     доступный в свежем проекте делегат, ставит исполнителем того, кто стартовал процесс.
   - **Редактируемые ключи payload** → впишите `decision` — разрешит `executeAction` принимать
     `payloadPatch: { decision: ... }` на этом шаге.
5. Кликните на ребро **новая нода → end** и в панели свойств задайте **Действие (action)** → `approve`.

**Проверка**: на холсте виден граф `start → [Задача пользователя] → end` с подписанным ребром `approve`.

## Шаг 3 — опубликуйте версию

Нажмите **"Опубликовать v1"** в правом верхнем углу редактора.

**Проверка**: бейдж сменился на "Опубликована v1"; если вместо этого появился красный баннер с
ошибками валидации — самая частая причина на этом шаге: не выбран исполнитель или не проставлен
`action` на ребре из `userTask` (см. предыдущий шаг).

## Шаг 4 — запустите процесс

Процесс стартует HTTP-вызовом `POST /api/workflows/demo-approval/start` — на этом шаге проще всего
выполнить его прямо из консоли браузера (той же вкладки, где открыто приложение — cookie-сессия
подставится автоматически):

```javascript
const res = await fetch('/api/workflows/demo-approval/start', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ payload: { amount: 100 } }),
});
const instance = await res.json();
console.log(instance.id); // понадобится на следующем шаге
```

**Проверка**: ответ — `201` с телом `ProcessInstanceRow` (`id`, `currentState`, `payload`, ...).
`currentState` должен быть равен `id` ноды "Задача пользователя" (не `start` — движок автоматически
прошёл транзитный `start` и остановился на первом стоп-узле, см.
[explanation.md](./explanation.md#транзакционные-границы)).

## Шаг 5 — найдите свою задачу

```javascript
const tasks = await (await fetch('/api/workflows/tasks/my')).json();
console.log(tasks);
```

**Проверка**: в списке есть задача с `workflowCode: 'demo-approval'` и `status: 'pending'` — это та
же нода, где остановился процесс на шаге 4 (исполнитель — `process-initiator`, то есть вы сами, раз вы
и стартовали процесс).

## Шаг 6 — откройте таймлайн процесса

Перейдите на `/admin/workflows/processes/{instance.id}` (id из шага 4) — это уже готовая страница
модуля (`ProcessTimelinePage`), не нужно ничего писать. Вы увидите текущий этап, блок с кнопкой
действия `approve` (поскольку вы — назначенный исполнитель, `isAssignee: true`) и пустой пока таймлайн.

**Проверка**: кнопка `approve` видна и активна.

## Шаг 7 — выполните действие

Нажмите кнопку `approve` на странице таймлайна (она вызывает `POST
/api/workflows/processes/{id}/actions/approve` — тот же роут, что описан в
[reference.md](./reference.md#процессы-routesprocessests)).

**Проверка**: бейдж статуса сменился на "Завершена", в таймлайне появилась запись перехода
`[Задача пользователя] → Конец` с вашим логином как актором.

## Что дальше

- Добавьте условное ветвление (exclusive gateway) вместо линейного графа — рецепт в
  [how-to.md](./how-to.md#как-спроектировать-ветвление-exclusive-gateway).
- Зарегистрируйте свой собственный `AssigneeProvider`/`ServiceTaskProvider` из вашего модуля вместо
  единственного встроенного `process-initiator` — [how-to.md](./how-to.md#как-зарегистрировать-делегата-исполнителя-assignee-provider).
- Почитайте, почему движок устроен через токены, а не "одну текущую ноду", и что из этого следует для
  конкурентности — [explanation.md](./explanation.md).
