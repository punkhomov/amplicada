# Постройте первую оргструктуру

Пошаговое введение в module-hr через админку — без кода, только карточки документов
(`module-admin`, раздел «HR-структура»). К концу у вас будет юрлицо, дерево из двух отделов с
пересчитанным `path`, и понимание, где что искать дальше — в [how-to.md](./how-to.md) (программные
вызовы `HrStructureService`) и [reference.md](./reference.md) (полный список полей).

## Предварительные условия

- Инфраструктура поднята через `pnpm infra:up`, приложения запущены через `pnpm dev` из корня.
- Вы залогинены под пользователем с доступом к админке.
- Миграции пакета применены (происходит автоматически при старте `apps/api`).

## Шаг 1 — создайте юрлицо

Откройте админку → раздел «HR-структура» → документ «Юридические лица» → «Создать».

| Поле | Значение |
|---|---|
| Код | `MAIN-LLC` |
| Краткое название | `ООО Главная Компания` |
| ИНН | `7700000000` |

Сохраните. **Проверка**: запись появилась в списке с колонками «Код», «Краткое название», «ИНН» —
причём ровно одной строкой, а не по строке на каждую версию. Если колонок нет или строк несколько,
смотрите, как устроены list-расширения Node+Version документов (см.
[reference.md](./reference.md#почему-у-пяти-nodeversion-документов-по-два-list-расширения)).

## Шаг 2 — создайте корневой отдел

Документ «Подразделения» → «Создать»:

| Поле | Значение |
|---|---|
| Код | `ROOT` |
| Название | `Компания` |
| Вышестоящее подразделение | *(оставить пустым)* |

Сохраните, откройте карточку заново. **Проверка**: под капотом
`hr_department_version.path = 'ROOT'` — совпадает с `code`, так как родителя нет
(`HrStructureService.buildDepartmentPath` возвращает сам `code`, если `parentNodeId` не задан).

## Шаг 3 — создайте дочерний отдел

Тот же документ → «Создать»:

| Поле | Значение |
|---|---|
| Код | `DEV` |
| Название | `Разработка` |
| Вышестоящее подразделение | `Компания` (тот, что создали на шаге 2) |

**Проверка**: `path` этой версии — `ROOT/DEV` (родительский `path` + `/` + свой `code`).

## Шаг 4 — переименуйте дочерний отдел

Откройте карточку `DEV`, измените «Название» на `Разработка и эксплуатация`, сохраните.

**Проверка**: новой версии не появилось. Карточка — обычная CRUD-форма без поля «действует с», поэтому
её правка трактуется как **исправление записи**, а не как новый факт: текущая строка
`hr.department_version` правится на месте, `validFrom`/`validTo` не двигаются. В таблице для этого
`nodeId` по-прежнему ровно одна строка с `validTo IS NULL`.

Отредактируйте отдел ещё раз в тот же день — тоже одна строка. Раньше вторая правка в день создания
роняла сохранение с 500 (интервал «с сегодня по вчера»), см.
[explanation.md](./explanation.md#правка-карточки--это-коррекция-записи-а-не-новый-факт).

Новые версии создают только явные операции с датой (`deactivateX`, `transferEmployee`) — у них
`effectiveDate` осмыслен. Кнопок в UI для них сегодня нет, дёргать можно только программно.

## Шаг 5 — переподчините отдел (проверка каскада `path`)

Создайте ещё один отдел с кодом `BACKEND` и родителем `DEV` — его `path` будет `ROOT/DEV/BACKEND`.
Теперь откройте карточку `DEV` и смените «Вышестоящее подразделение» на *(пусто)* — сделайте его
корневым.

> Поле «Вышестоящее подразделение» объявлено как `widget: 'reference'`, но виджет выбора в админке не
> реализован — рендерится обычный текстовый инпут. Практически: родителя приходится задавать, вписывая
> UUID узла руками (взять его можно из URL карточки родителя).

**Проверка**: `path` у `DEV` стал равен `DEV`. `path` у `BACKEND` (потомок `DEV`, вы его не трогали
напрямую) должен был пересчитаться каскадом на `DEV/BACKEND` — это и есть работа
`reparentDepartment`/`cascadeDepartmentPath`, описанная в
[how-to.md](./how-to.md#как-переподчинить-отдел-с-каскадом-path).

Новых версий при этом снова не появится: переподчинение из карточки — тоже коррекция. Записи «переехал
такого-то числа» не остаётся, это осознанный выбор.

## Шаг 6 — попробуйте закрыть отдел с активным сотрудником (guard rail)

Если у вас заведена штатная единица в `BACKEND` с активным назначением сотрудника (документы
«Штатные единицы» → «Назначения» — назначения пока без отдельной карточки, только через сервис/SQL),
попробуйте деактивировать `BACKEND` через прямой вызов `HrStructureService.deactivateDepartment` (нет
кнопки в UI на момент написания).

**Проверка**: вызов бросит `NodeHasActiveAppointmentsError` — отдел не закроется, пока сотрудник не
переведён или не уволен. Если штатных единиц с активными назначениями нет — деактивация пройдёт: у
отдела не останется версии с `validTo IS NULL`.
