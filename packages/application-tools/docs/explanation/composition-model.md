# Состав, граф и жизненный цикл

Композиция отвечает на три разных вопроса: какие модули выбрало приложение,
в каком порядке они инициализируются и какие сервисы можно использовать во время setup.
Эти вопросы связаны, но наличие установленного пакета само по себе не отвечает на все три.

## Установленный пакет и активный модуль

Генератор начинает с прямых production dependencies приложения и выбирает пакеты с
`amplicada: true`. Обычная библиотека, devDependency или вложенный пакет не становятся
активным модулем только от присутствия в node_modules (`src/application.ts:104`).
При `--config` используется явно перечисленный полный состав, который тоже должен
быть объявлен в dependencies каждого target (`src/application.ts:215`).

| Состояние admin | Что происходит с интеграцией auth |
|---|---|
| Пакет отсутствует | Optional peer пропускается; auth регистрирует свою страницу входа |
| Пакет установлен, но исключён явным профилем | Admin setup не вызывается; интеграция пропускается |
| Пакет выбран приложением | Admin setup выполняется раньше auth setup |

Последняя строка следует из optional peer в package.json auth. Для обязательного
peer первые два состояния были бы ошибкой состава. Проверка версий пакетов остаётся
за пакетным менеджером; генератор дополнительно запрещает разные установки одного
модуля в графе (`src/application.ts:123`).

## Что происходит при сборке и при запуске

```text
package.json приложения
  → выбор модулей
  → чтение их exports, dependencies и peers
  → проверка полноты состава и циклов
  → сортировка графа пакетов
  → отдельные frontend/backend imports и CSS
  → компиляция приложения

Запуск собранного приложения
  → загрузка статических imports
  → проверка runtime id и dependencies
  → регистрация метаданных всех модулей
  → последовательный await setup каждого модуля
  → последовательный start
```

Генератор не импортирует исполняемый код пакетов для discovery. Поэтому build-time
проверка знает npm-имена, exports и связи, но не читает runtime id из объекта module.
Generated-массив берёт id из импортированных объектов и передаёт зависимости bootstrap
(`src/application.ts:148`). Например, при выбранных admin и auth frontend-код имеет вид:

```ts
import type { FrontendModule } from '@amplicada/platform-core/contracts/frontend';
import { module as admin } from '@amplicada/module-admin/frontend';
import { module as auth } from '@amplicada/module-auth-password/frontend';

export const modules: FrontendModule[] = [
  { ...admin, dependencies: [] },
  { ...auth, dependencies: [admin.id] },
];
```

Переименования локальных переменных в примере служат читаемости; CLI использует module0,
module1. Bootstrap повторно проверяет граф, в том числе дубликаты runtime id, до setup
(`packages/platform-core/src/contracts/module-registration.ts:10`). Сортировка setup
не задаёт порядок побочных эффектов верхнего уровня JavaScript-модулей.

## Откуда берётся порядок сторон

Граф содержит связи обязательных dependencies/peers, если соответствующий пакет
является модулем. Optional peer добавляет связь только между выбранными модулями.
Отсутствующий optional peer не активируется автоматически (`src/application.ts:123`).

Сначала сортируется единый пакетный граф, затем результат фильтруется по exports стороны.
Если frontend A зависит от backend-only B, а B зависит от frontend C, в frontend
сохраняется порядок C → A. Это перенос ограничения порядка, а не вызов backend B
из браузера (`src/application.ts:153`).

Обе стороны модуля используют один граф. Отдельной настройки «обязательная зависимость
только для backend» сейчас нет. При выбранном HR workflow должен присутствовать в составе
и его доступные стороны включаются соответствующими targets. У независимых модулей
нет гарантии порядка, на которую следует опираться для получения сервисов: объявляйте связь.

## Что гарантирует проверка присутствия

`context.modules.getById('admin')` возвращает зарегистрированные метаданные текущей
стороны. Все эти метаданные доступны до первого setup. Сам по себе getById не сообщает,
что сервисы admin уже созданы (`packages/platform-core/src/contracts/module-registration.ts:10`).

Безопасный вызов сервиса в setup требует одновременно:

1. Поставщик выбран приложением и имеет нужную сторону.
2. Потребитель объявил обязательную связь либо optional peer.
3. Поставщик зарегистрировал сервис в своём setup.
4. Вызываемая операция не требует ещё не выполненного start.

При этих условиях последовательное ожидание setup гарантирует доступность сервиса.
Если поставщик выбран, но не выполнил контракт, resolve выдаёт ошибку. Отсутствующий
optional-модуль можно пропустить; ошибку выбранного модуля скрывать не следует.
Циклы между выбранными optional peers также запрещены (`src/application.ts:143`).

## Практические границы

Изменение package.json требует повторной генерации, сборки и перезапуска. Удаление
модуля из состава убирает его generated imports/CSS, но не удаляет данные, файлы,
миграции или фоновые записи из хранилищ. CLI не устанавливает пакеты и не исполняет
install hooks (`src/application.ts:240`, `src/cli.ts:23`).

Zero-config относится к составу: приложение один раз подключает CLI к build/dev/typecheck
и импортирует generated-массивы и CSS. Инфраструктура, секреты и обязательная политика
установки остаются настройками проекта. При ручном подключении без CLI вызывающий код
сам задаёт полный массив и runtime dependencies.
