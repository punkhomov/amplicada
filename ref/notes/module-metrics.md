# module-metrics — заметки

> План и контракты: `ref/plans/2026-09-18-metrics-module/` (00-overview, 01-contracts,
> 02-offline-stack). Реализованы этапы 00 и 01 (журнал событий, трекер pageview+клики,
> rate-limit, opt-out/DNT, лента/каталог/настройки в админке).
> Стоп-лист (D-001…D-018):
> - Не хранить события в Document System — D-001 (rejected).
> - Не позволять произвольный id события (и не менять тип колонки на text) — D-002 (rejected).
> - Не хешировать актора голым SHA-256 и не хранить соль в БД — D-003 (rejected).
> - Не писать сэмплы/события напрямую в таблицы в обход сервиса `metrics` — D-004 (rejected).
> - Не удалять старые события `DELETE`-ом и не резать партиции под `ACCESS EXCLUSIVE` — D-005 (rejected).
> - Не делать публичный write-key для ингестии и не собирать сырые URL по умолчанию — D-006 (rejected).
> - Не разводить реалтайм (SSE) для дашбордов метрик — D-007 (rejected, polling).
> - Не ставить token bucket/Lua и не считать лимит по IP при известной сессии — D-008 (rejected).
> - Не собирать клики autocapture'ом всего DOM и не строить клиентскую страницу opt-out — D-009 (rejected).
> - Не строить HTTP-метрики модульным `onRoute`/async-ALS — только core-точки — D-010 (rejected).
> - Не считать перцентили точными (`percentile_cont`) по всей истории и не брать t-digest — D-011 (rejected).
> - Не хранить сырой SQL с литералами и не инструментировать запросы самого модуля — D-012 (rejected).
> - Не писать бизнес-события прямыми INSERT и не тянуть рантайм-импорт модуля метрик потребителями — D-013 (rejected).
> - Не группировать ошибки по тексту сообщения и не хранить сырые стеки без нормализации — D-014 (rejected).
> - Не писать свои Web Vitals и не считать p75 перебором сырых событий — D-015 (rejected).
> - Не отправлять наружу синхронно из запроса и не хранить секреты выходов в БД — D-016 (rejected).
> - Не встраивать оценку правил в запись событий и не плодить PromQL-подобные выражения — D-017 (rejected).
> - Не отправлять в Метрику события без ClientId/UserId и не хранить OAuth-токен в настройках — D-018 (rejected).

## D-001. События — партиционированные таблицы модуля, не документы — accepted (2026-09-18)

**Контекст.** Append-only поток событий (pageview и далее — UI, ошибки, бизнес-события)
с высоким темпом записи и retention по времени. У Document System есть `document_index`,
extension-поля, generic-карточка и list-UI.

**Решение.** Схема `metrics`, таблица `metrics.events` — range-партиционирование по
`occurred_at` (месяц), PK `(occurred_at, id)`, BRIN по времени и btree под реальные
фильтры; настройки — синглтон `metrics.settings`. Документы не используются.

**Почему именно так.** Прецедент support-chat (`notes/module-support-chat.md`, D-001):
generic-карточка и extension-поля для потока событий не нужны, а FK на индекс и
`allocateDocumentId` на каждое событие — лишняя цена. Партиции дают дешёвый retention
(`DETACH`+`DROP`) и меньший vacuum.

**Отвергнуто.** Документ-событие (бесплатный generic list) — не окупается: события не
редактируют и не открывают карточкой. TimescaleDB — Community-функции под TSL, для
append-only хватает vanilla (`plans/2026-09-18-metrics-module/02-offline-stack.md`).

**Что изменит решение.** Если события начнут править/связывать с документами (например,
прикреплять к карточке обращения) — часть может стать расширением документа, но сырой
журнал останется таблицей.

**Грабли.** Drizzle-схема не описывает партиции — их создаёт миграция `0000_init.sql` и
задача `metrics.maintenance`; вставка без партиции падает, поэтому `start()` модуля
гарантирует месяцы вперёд.

**Код.** `migrations/0000_init.sql`, `src/backend/schemas/events.ts`,
`src/backend/services/partitions.ts`.

## D-002. `id` события — uuid, клиентский ключ идемпотентности — accepted (2026-09-18)

**Контекст.** Клиент шлёт события батчами, при повторе (beacon + fetch) батч может прийти
дважды; журнал должен дедуплицировать. Колонка `id` — `uuid`.

**Решение.** Клиент генерирует `crypto.randomUUID()`, сервер валидирует строгий uuid и
вставляет `ON CONFLICT (occurred_at, id) DO NOTHING`; в ответе есть `duplicates`.

**Почему именно так.** Живая проверка показала: валидация «любая безопасная строка 8–64»
пропускала `evt-…`, и вставка падала на типе колонки. Тип и контракт должны совпадать,
дедуп бесплатно получается из PK.

**Отвергнуто.** `text`-колонка под внешние id (Segment-стиль `messageId`) — пока внешних
источников нет; при появлении — отдельная колонка `external_id`, а не размывание PK.

**Что изменит решение.** Ингестия от внешних систем с собственными id.

**Код.** `src/backend/services/validation.ts`, `src/backend/services/metrics-store.ts`.

## D-003. Псевдонимизация — HMAC с солью из core-сервиса `secrets` — accepted (2026-09-18)

**Контекст.** Нужны «уникальные пользователи» и сессии, но 152-ФЗ и приказ РКН № 140
требуют обезличивания, а соль (ключ) нельзя хранить рядом с данными.

**Решение.** `Pseudonymizer` — HMAC-SHA256(соль, `purpose:value`), назначения разделены
(`analytics`, `errors`, `session`), псевдонимы не сшиваются между собой. Соль читается
через новый core-сервис `secrets` (`AMPLICADA_METRICS_PSEUDONYM_SALT`). Если соль не
задана — процессный случайный секрет + warning (псевдонимы не переживут рестарт).

**Почему именно так.** Голый SHA-256 перебирается по словарю id; соль в БД — «ключ рядом
с данными». Core-сервис `secrets` — минимальное изменение платформы, заодно закрывает
будущие OAuth-токены провайдеров (этап 05).

**Отвергнуто.** Соль в `metrics.settings` (rejected): противоречит требованию раздельного
хранения. Чтение `process.env` модулем напрямую (rejected): ломает конвенцию «env читает
только core».

**Что изменит решение.** Полноценный секрет-стор/KMS; ротация соль раз в сутки для
аналитики (Plausible-модель) — этап 06.

**Грабли.** Без env-переменной псевдонимы «плывут» при рестарте — это видно по warning
в логе; для прода переменная обязательна.

**Код.** `src/backend/services/pseudonym.ts`, `packages/platform-core/src/backend/services/secrets-service.ts`.

## D-004. Единая точка записи — сервис `metrics` — accepted (2026-09-18)

**Контекст.** События будут приходить из нескольких источников: клиентский трекер (ingest),
HTTP-коллектор, SQL-коллектор, задачи, бизнес-события модулей.

**Решение.** Все пишут через `MetricsService.collect/emit`; наружу — `context.services.resolve('metrics')`
(модули проверяют `has('metrics')`, если модуль опционален). Напрямую в таблицы не пишет никто.

**Почему именно так.** Единая валидация, псевдонимизация, сэмплирование, лимиты и будущие
sink'и — в одном месте; модули не знают схему.

**Отвергнуто.** Прямые INSERT из модулей (rejected): разъезжаются правила и дедуп.

**Код.** `src/backend/services/metrics-service.ts`, `src/backend/setup.ts`.

## D-005. Retention — партиции: `DETACH CONCURRENTLY` + `DROP` — accepted (2026-09-18)

**Контекст.** События живут ограниченное время (по умолчанию 30 дней), объём растёт.

**Решение.** Задача `metrics.maintenance` (партиции вперёд + удаление старых) и вызов
`ensureEventPartitions()` в `start()`. Удаление — `ALTER TABLE … DETACH PARTITION … CONCURRENTLY`,
затем `DROP TABLE`. Расписание задачи настраивается в админке (task-scheduler).

**Почему именно так.** `DELETE` оставляет dead tuples и не возвращает диск; detach
concurrently не берёт `ACCESS EXCLUSIVE` на родителя (PG14+).

**Отвергнуто.** `pg_partman` (rejected на этом этапе): лишняя зависимость в закрытом
контуре, логика простая. `DELETE` по возрасту (rejected).

**Что изменит решение.** Несколько таблиц-потоков (измерения, exemplars) — общий
maintenance-механизм.

**Грабли.** Партиций в БД три (текущий + 2); если процесс не стартовал месяц, вставка
упадёт — митигация: задача в админке + ensure в `start()`.

**Код.** `src/backend/services/partitions.ts`, `src/backend/setup.ts`.

## D-006. Ингестия — same-origin под сессией, без публичного ключа; сырые URL выключены — accepted (2026-09-18)

**Контекст.** Клиентский трекер шлёт батчи на свой же сервер. Внешние SaaS используют
публичный write-key (Sentry DSN), но у нас платформа и SPA — один origin.

**Решение.** `POST /api/metrics/collect` принимает сессию, если она есть (псевдоним актора),
иначе аноним; лимиты (батч ≤ 500, событие ≤ 8 КБ, атрибуты ≤ 32); ответ 202 с частичным
успехом; `enabled=false` в настройках отклоняет запись. Сырой URL не сохраняется, пока не
включён `store_raw_urls`; в данных — только шаблон маршрута (`/support/:id`).

**Почему именно так.** Меньше поверхность атаки, нет публичного ключа для ротации; URL —
главный источник кардинальности и PII (query-параметры).

**Отвергнуто.** Публичный DSN-ключ (rejected); хранить сырые URL по умолчанию (rejected).

**Что изменит решение.** Внешние страницы/интеграции, которым нужен сбор без сессии, —
отдельный keyed-эндпоинт.

**Грабли.** Rate-limit (Redis token bucket) ещё не сделан — этап 01; пока защита — размеры
батчей и лимит 500 событий.

**Код.** `src/backend/routes.ts`, `src/backend/services/validation.ts`.

## D-007. Дашборды — polling, без SSE — accepted (2026-09-18)

**Контекст.** В платформе есть SSE-паттерн (support-chat, задачи) на Redis.

**Решение.** Админ-лента событий обновляется React Query polling (`refetchInterval` 15 с).

**Почему именно так.** Аналитика не требует секундной свежести, а SSE тянет Redis-каналы,
подписки и сложность. Решение владельца (2026-09-18): периодическое обновление достаточно.

**Отвергнуто.** Живые дашборды на SSE (deferred, не rejected навсегда): вернуться, если
появится сценарий «смотреть поток ошибок в реальном времени».

**Код.** `src/frontend/lib/query-options.ts`.

## D-008. Rate-limit приёма — фиксированное минутное окно в Redis — accepted (2026-09-18)

**Контекст.** Публичный `POST /collect` принимает батчи; нужна защита от зацикленного или
враждебного клиента. В core уже есть Redis; лимит должен настраиваться админом.

**Решение.** `IngestRateLimiter` (`INCRBY` + `EXPIRE` на ключ `metrics:rl:<key>:<window>`),
лимит — `settings.ingestEventsPerMinute` (по умолчанию 600). Ключ — хеш пользователя, сессии
или IP (в Redis, не в БД). При превышении — 429 `{error:'rate_limited', retryAfter}` и
заголовок `Retry-After`. Проверка идёт **до** `collect`, стоимость — число событий в батче.

**Почему именно так.** Фиксированное окно — три Redis-вызова без Lua и блокировок; на границе
окна возможно «двойное» окно (до 2× лимита), для телеметрии это приемлемо. Ключ-хеш не
сохраняет идентификаторы в БД и живёт с TTL 2 минуты.

**Отвергнуто.** Sliding window/token bucket на Lua (rejected): сложнее, точность не нужна.
Лимит только по IP (rejected): за NAT пострадают все; сессия/пользователь точнее.
Свой счётчик в Postgres (rejected): запись на каждый батч дороже Redis.

**Что изменит решение.** Жалобы на «двойное окно» или необходимость квот на интеграторов —
переход на sliding window/Lua или отдельные лимиты по ключам sink'ов.

**Грабли.** node-redis v4 использует camelCase (`incrBy`), а не `incrby` — ошибка вылезла
живьём как 500 на первом же лимитированном запросе.

**Код.** `src/backend/services/rate-limiter.ts`, `src/backend/routes.ts`, настройка
`ingest_events_per_minute` (миграция `0001_rate_limit.sql`).

## D-009. Клики — только `data-metrics`; opt-out — флаг/DNT/GPC в трекере — accepted (2026-09-18)

**Контекст.** Для продуктовой аналитики нужны UI-события, но autocapture всего DOM (PostHog-стиль)
даёт объём, случайные PII и хрупкость селекторов. Пользователю нужен способ не отправлять телеметрию.

**Решение.** Трекер слушает клики в capture-фазе и реагирует только на `[data-metrics]`: имя —
значение атрибута, `data-metrics-*` — атрибуты события, плюс `element`. Сэмплирование —
`sampleClickRate`. Opt-out проверяется при инициализации: `localStorage['metrics.optout']='1'`,
`navigator.doNotTrack==='1'` (или legacy `window.doNotTrack`) либо `navigator.globalPrivacyControl` —
трекер не поднимается, запросы `context`/`collect` не идут.

**Почему именно так.** Явная разметка даёт осмысленные имена без эвристик и не собирает текст
элементов; opt-out — требование приватности (152-ФЗ/GDPR-практика), серверный kill-switch уже есть.

**Отвергнуто.** Autocapture DOM (rejected): объём, PII, ломкие селекторы. Клиентская страница
настроек приватности (rejected на этом этапе): пользователь ставит флаг вручную, UI — когда
появится раздел настроек пользователя. Отправлять «событие opt-out» на сервер (rejected):
это и есть телеметрия, которой пользователь не хочет.

**Что изменит решение.** Требование «отключить аналитику кнопкой» — появится клиентский UI,
флаг останется тем же. Появление авто-инструментирования в ките — обсудить разметку в компонентах.

**Грабли.** Клики слушаются в capture-фазе: `closest` от `event.target` может быть SVG-элементом;
если элемент исчез из DOM до обработчика — событие теряется (допустимо).

**Код.** `src/frontend/lib/clicks.ts`, `src/frontend/lib/optout.ts`,
`src/frontend/features/metrics-tracker/ui/metrics-tracker.tsx`.

## D-010. Технические метрики через core-точки `http:observer` + `request-context` — accepted (2026-09-18)

**Контекст.** Нужны метрики всех HTTP-роутов и корреляция SQL с роутом. Модуль не может
навесить root-хук, который покрыл бы роуты ранних модулей (Fastify инкапсулирует hooks по
порядку регистрации), а ALS из async-`onRequest` не доживает до хендлера.

**Решение.** Core даёт `http:observer` (root-хуки в `createApp` до всех setup) и
`request-context` (ALS, callback-хук `run(context, done)`). Модуль контрибует наблюдателя
и читает `current()` из SQL-обёртки. Подробности и отвергнутые варианты — `notes/platform-core.md` D-006.

**Почему именно так.** Единственный способ гарантировать полное покрытие роутов и живую ALS.

**Грабли.** SQL фоновых задач — `<unattributed>`; unmatched HTTP — `route='<unmatched>'`.

**Код.** `src/backend/collectors/{http-observer,sql-collector}.ts`, `src/backend/setup.ts`.

## D-011. Перцентили — из гистограмм, агрегация — в Postgres, merge — в JS — accepted (2026-09-18)

**Контекст.** Нужны p50/p95/p99 по роутам и SQL на периоде до 7 дней. Точный
`percentile_cont` по сырым наблюдениям дорог и требует хранения каждой выборки; t-digest —
расширение (в закрытом контуре нежелательно).

**Решение.** Коллекторы копят гистограммы в памяти и сбрасывают раз в 10 с
(`MeasurementBuffer` + `MeasurementFlusher`); точки хранятся в `metrics.points`. Запросы
`/routes` и `/sql` суммируют count/sum в Postgres, а `bucketCounts` разворачивают
`cross join lateral jsonb_array_elements_text(...) with ordinality` и сливают в JS,
перцентиль считается линейной интерполяцией (`percentileFromHistogram`).

**Почему именно так.** Одна строка на (серию, окно) вместо каждого наблюдения; merge
бакетов — десятки строк на запрос; границы OTel-дефолтные, точность достаточна для
RED-панелей.

**Отвергнуто.** Точные `percentile_cont` по сырым точкам всей истории (rejected): цена
сортировки. t-digest/расширения (rejected): зависимость в закрытом контуре. Хранить каждое
наблюдение отдельной строкой (rejected): объём ×100.

**Что изменит решение.** Требование точных p99 на больших окнах или SLA-отчёты — t-digest
в роллапах или отдельное хранилище за `MetricsStore`.

**Грабли.** Перцентиль «насыщается» на верхней границе (+Inf-бакет): для задержек > 10 с
интерполяция даёт ~10 с — для RED достаточно, точные значения видны в slow_queries.

**Код.** `src/backend/services/{histogram,measurement-buffer}.ts`,
`src/backend/services/metrics-store.ts` (`routesSummary`, `sqlSummary`),
`src/backend/collectors/measurement-flusher.ts`.

## D-012. SQL-коллектор — обёртка пула, нормализация литералов, tail-samples — accepted (2026-09-18)

**Контекст.** Нужны тексты запросов (какие SQL гоняются), их длительность и корреляция с
роутом; `pg_stat_statements` требует настройки сервера и в закрытых контурах доступен не всегда.

**Решение.** Обёртка `pool.query` и клиентов из `pool.connect` (`SqlCollector`): wall-clock
замер, нормализация литералов (`normalizeSql`: строки/числа → `?`, `IN` сворачивается,
`$n` сохраняются), fingerprint = sha256 нормализованного текста. В измерения идёт
гистограмма по `(fingerprint, route)`, в `metrics.slow_queries` — samples всех медленных
(> `slowSqlThresholdMs`) и ошибочных; тексты fingerprint'ов — в `metrics.sql_fingerprints`.
Запросы самого модуля (`metrics.`) пропускаются, чтобы не было обратной связи.

**Почему именно так.** Работает без прав DBA и без расширений; нормализованный текст не
несёт PII; samples ограничены (≤50 за окно), поэтому объём под контролем.

**Отвергнуто.** Сырой SQL с литералами в метриках (rejected): PII и кардинальность.
Обязательный `pg_stat_statements` (rejected): не всегда доступен; остаётся опцией на будущее.
Инструментирование только медленных (rejected): теряется rate/распределение.

**Что изменит решение.** Разрешение DBA на `pg_stat_statements` — добавить снимок дельт как
дополнительный источник (план, этап 02, опциональная часть); появление `libpg_query` в
зависимостях — заменить regex-нормализацию на парсер.

**Грабли.** Callback-стиль pg не инструментируется (drizzle на промисах). `queryTextOf`
обрабатывает и строку, и `{ text }`. У `rowCount` тип `number | null`.

**Код.** `src/backend/collectors/sql-collector.ts`, `src/backend/services/sql-normalize.ts`,
`src/backend/services/metrics-store.ts` (`writeMeasurements`, `upsertSqlFingerprints`, `insertSlowQueries`).

## D-013. Бизнес-метрики: emit через сервис, определения в core-реестре, панели во frontend-сервисе — accepted (2026-09-18)

**Контекст.** Модулям нужно отдавать свои события (обращения, workflow, обучение) и получать
их на графиках, не зная схемы хранилища и не разрывая опциональность сборки: модуль метрик
может отсутствовать.

**Решение.** Три независимых контура:
1. **emit** — метод сервиса `metrics` (`context.services.resolve`), ленивый resolve с
   `has('metrics')` у потребителя; событие валидируется и уезжает в общий буфер.
2. **Определения** — extension point `metrics:definitions`: модуль контрибует
   `MetricDefinition` из setup, метрики читают `getAll` при запросе (`/definitions`,
   `/definitions/summary`).
3. **Панели** — frontend-сервис `metrics:panels` с модуль-локальным реестром; токен — литерал
   в потребителе, сам реестр живёт в модуле метрик; вкладка «Панели» рендерит графики через
   `/series`.

**Почему именно так.** Все три контура не создают рантайм-зависимости: потребители
импортируют только типы (стираются), а `has()` покрывает отсутствие модуля. Данные и лимиты
остаются на стороне метрик.

**Отвергнуто.** Прямые INSERT в `metrics.events` из модулей (rejected): ломает единую
валидацию/псевдонимизацию. Обязательный runtime-импорт `@amplicada/module-metrics/frontend`
(rejected): билд без метрик падал бы. Определения как документы (rejected): код-контрибуции
проще и не требуют миграций.

**Что изменит решение.** Редактируемые пользователем определения/дашборды (сохранённые
представления) — тогда definitions/panels перейдут в таблицы, а extension point останется
для «заводских» метрик модулей.

**Грабли.** `emit` не бросает и не блокирует; при переполнении буфера вытесняются старые
события — для бизнес-метрик нужен мониторинг self-метрик (пока нет). Перекрёстная проверка
`has('metrics')` ленивая (в момент emit), поэтому порядок setup не важен.

**Код.** `src/backend/services/{metrics-service,event-buffer}.ts`, `src/backend/routes.ts`,
`src/frontend/lib/panel-registry.ts`, пилот — `packages/module-support-chat/src/backend/metrics.ts`.

## D-014. Ошибки группируются по fingerprint (тип + маршрут + кадры стека) — accepted (2026-09-18)

**Контекст.** Нужны issues с Sentry-подобной группировкой: одинаковые ошибки с разными
данными должны объединяться, а сообщения и стеки — не тащить PII.

**Решение.** `errorFingerprint`: sha256(`error.type` + шаблон маршрута + первые 5 кадров),
сообщение в базис не входит. Клиентские источники: `window` (capture), unhandledrejection,
React 19 через `frontendErrors` ядра. Нормализация текстов на клиенте и на сервере:
origin/query, UUID/hex, числа → плейсхолдеры. Инкремент issue идёт только по реально
вставленным событиям (id-дедуп), счётчики не задваиваются.

**Почему именно так.** Тип + кадры стабильнее текста; route разделяет одинаковые ошибки на
разных страницах. Нормализация сохраняет структуру кадров (двойная защита от PII).

**Отвергнуто.** Fingerprint по сообщению (rejected): «Cannot read … reading 42/77» — один
баг, а было бы два issue. Хранить сырые стеки/сообщения (rejected): PII и кардинальность.
Группировка только на клиенте (rejected): обходится, теряет release-контекст.

**Что изменит решение.** Source maps для символизации (сейчас браузерные стеки как есть;
для продакшена — хранить артефакты по релизу). Ручные merge/split issue — когда появятся
ложные группы.

**Грабли.** Живой прогон поймал: валидация атрибутов резала ключи с точкой (`error.type`),
из-за чего issues шли с типом `Error` и пустым шаблоном — `KEY_RE` расширен до точечной
нотации. `createRoot`-хуки требуют правки `apps/web` — репортер ядра сделан отдельным
сервисом (`frontendErrors`), без него модуль ловит только window-ошибки.

**Код.** `src/backend/services/error-fingerprint.ts`, `src/backend/services/metrics-store.ts`
(`upsertErrorIssues`, `listErrorIssues`, `listErrorSamples`), `src/frontend/lib/error-capture.ts`,
`packages/platform-core/src/frontend/lib/error-reporter.ts`.

## D-015. Web Vitals: `web-vitals` + dual write (событие и гистограмма) — accepted (2026-09-18)

**Контекст.** Нужны LCP/INP/CLS/FCP/TTFB и p75, при этом события уже умеют хранить рейтинги
и контекст, а перцентили по истории считаются только из гистограмм.

**Решение.** Библиотека `web-vitals` 6.2.1 (delta-обновления, `navigationType`), события
`web_vital.*`; сервер при приёме дополнительно пишет наблюдение в гистограмму с границами
good/poor (`web_vital.ts`), поэтому вкладка показывает p75/p95 и раскладку рейтингов.

**Почему именно так.** Своя реализация INP/CLS с session windows — источник багов; библиотека
закрывает краевые случаи. Dual write даёт и точечные данные, и дешёвые перцентили.

**Отвергнуто.** Только события + `percentile_cont` (rejected): дорого на истории. Только
гистограммы (rejected): теряются рейтинги/URL/release. Свои PerformanceObserver-ы (rejected):
INP/CLS сложны, а библиотека уже проверена.

**Что изменит решение.** Требование p75 по release/устройству — добавить измерения в
гистограмму (сейчас route и rating). Отказ от dual write — если объём событий станет велик.

**Грабли.** `minimumReleaseAge` не пускает свежие версии: `web-vitals` запиннен на `6.2.1`
(исключения политики не расширяем). В dev StrictMode `observeWebVitals` защищён модульным
флагом от двойной подписки.

**Код.** `src/frontend/lib/vitals.ts`, `src/backend/services/web-vitals.ts`,
`src/backend/services/metrics-service.ts` (`collect`), `src/backend/schemas/measurements.ts`.

## D-016. Выходы: durable outbox + внутренний диспетчер, секреты через core `secrets` — accepted (2026-09-18)

**Контекст.** События нужно отдавать наружу (webhook, позже Яндекс.Метрика) так, чтобы сбой
внешней системы не влиял на запись и не терял данные; в закрытом контуре выходы выключены.

**Решение.** Три контура: контракт `MetricSink` с whitelist настроек (`sanitizeSettings`),
durable-очередь `metrics.outbox` (уникальность `(sink_id, item_id)` — дедуп по id события),
диспетчер внутри модуля с интервалом 15 секунд (backoff 30 с → 1 ч, 6 попыток, 4xx без 429 →
DLQ) и журнал `metrics.sink_deliveries`. Webhook подписывает тело HMAC (`x-metrics-signature`),
секрет — через core `secrets` (`AMPLICADA_METRICS_WEBHOOK_SECRET`), не в БД. Постановка в
очередь — вместе с записью события, только для включённых выходов; выключенный выход события
не теряет, но и не получает.

**Почему именно так.** Синхронная отправка из `collect` задерживала бы клиента и теряла данные
при сбое. Диспетчер интервалом (а не задача task-scheduler) работает сразу после установки, без
настройки cron в админке; ручной прогон есть в API. Секрет в env — продолжение линии D-003.

**Отвергнуто.** Прямая отправка в `persistEvents` (rejected): латентность и потеря при ошибке.
Задачи scheduler'а как единственный триггер (rejected): требуют ручного включения расписания,
а очередь должна разъезжаться сама. Секреты в `sink_configs.settings` (rejected): ключ рядом с
данными. Ретраи без журнала (rejected): нет видимости «почему DLQ».

**Что изменит решение.** Мультипроцессный деплой (`ROLE=worker`): диспетчер стоит запускать
только в worker-роли и/или защитить `FOR UPDATE SKIP LOCKED`, чтобы два процесса не слали
дубли; сейчас — единый процесс.

**Грабли.** `pkill` по имени фонового скрипта приёмника убил собственный шелл — классика,
в workflow уже есть bracket-трюк. Живой прогон: 400 → `dead` с первой попытки, выключение
выхода не создаёт новых строк очереди.

**Код.** `src/backend/sinks/{sink,webhook-sink,outbox-dispatcher}.ts`,
`src/backend/services/{metrics-service,metrics-store}.ts`, `migrations/0004_outputs.sql`.

## D-017. Алерты: чистая машина состояний + интервальный оценщик, доставка через шину — accepted (2026-09-18)

**Контекст.** Нужны пороги «5xx > X», «p95 > Y», «нет данных», без собственного PromQL и без
жёсткой связи с notification-модулем (его ещё нет).

**Решение.** Правила — данные (`metrics.alert_rules`), переходы считает чистая функция
`decideAlertState` (тесты на все ветки), оценщик запускается интервалом 60 с и вручную.
Значения: для событий — count за окно с фильтрами; для измерений — count/avg/p95 из
гистограмм (единицы приводятся к мс). Состояния (`pending`/`firing`) живут в
`metrics.alert_instances` и переживают рестарт; история — `metrics.alert_events` с retention
30 дней. Переходы публикуются в `context.eventBus` событием `metrics.alert` — это контракт
для будущего notification-модуля.

**Почему именно так.** Оценка вне пути записи события (не тормозит ingest и не блокирует
транзакции), состояние отделено от истории (UI видит «сейчас» и «что было»), а доставка —
шина, а не прямой вызов уведомлений (соблюдает опциональность модулей).

**Отвергнуто.** Проверка правил в `persistEvents` (rejected): латентность и повторная
оценка на каждом батче. PromQL-парсер (rejected): преждевременно, subset-правил хватает.
Прямая отправка email/webhook из оценщика (rejected): канал — забота notification/sink.
Хранить состояние только в памяти (rejected): рестарт сбрасывал бы `forMs` и терял firing.

**Что изменит решение.** Группировка по измерению (правило на каждый роут) — добавит
fingerprint и labels; notification-модуль — подписка на `metrics.alert` и silences; SLO
burn-rate — новые виды условий.

**Грабли.** Интервал 60 с сам перевёл firing → resolved во время паузы живой проверки —
это ожидаемое поведение, но при отладке легко принять за баг: ручной `evaluate` уже не
видит состояния. Дефолтные границы гистограмм в `measurementSummary` подтягиваются из
первой серии инструмента (иначе p95 у Web Vitals считался бы по секундным бакетам).

**Код.** `src/backend/alerts/{alert-evaluator,*.test}.ts`,
`src/backend/services/metrics-store.ts` (`eventCount`, `measurementSummary`, CRUD),
`src/backend/services/metrics-service.ts` (`evaluateAlerts`), `migrations/0005_alerts.sql`.

## D-018. Яндекс.Метрика: два серверных канала, токен в `secrets`, без живого прогона — accepted (2026-09-18)

**Контекст.** Нужен онлайн-выход для облачных инсталляций; клиентский скрипт счётчика в
закрытом контуре невозможен, а полноценная интеграция Яндекса требует `ClientID` (его даёт
только клиентский счётчик) и OAuth.

**Решение.** Адаптер `yandex-metrica` с двумя каналами: Measurement Protocol для событий с
атрибутом `yandex.client_id`; Offline Conversions CSV по псевдониму актора (UserId). Маппинг
`goalMap` в настройках, OAuth-токен — `AMPLICADA_METRICS_YANDEX_TOKEN` через core `secrets`.
Событие без обоих идентификаторов не отправляется; пустой `send` возвращает честную ошибку
`no sendable items`, чтобы кнопка «Проверить» не врала.

**Почему именно так.** Оба канала — серверные API без внешнего скрипта; идентификаторы у нас
псевдонимизированы, PII не уходит. Выключен по умолчанию — контур не зависит от интернета.

**Отвергнуто.** Клиентский сниппет как основной канал (rejected для on-prem: внешние скрипты
запрещены, блокировщики). Отправка `actor_hash` без согласия (rejected: только при явно
включённом выходе). OAuth-токен в `sink_configs.settings` (rejected: секрет рядом с данными).

**Что изменит решение.** Живой прогон с реальным счётчиком/токеном (сейчас не проверялся —
это главный пробел); квоты Метрики (30 rps, 5000/сутки) — возможно, понадобится планировщик
отправки; клиентский сбор `yandex.client_id` в трекере — когда появится облачный сценарий.

**Грабли.** MP ограничен 12 часами задним числом, offline-атрибуция — 21 днём: очередь с
большим лагом может получить отказ, это классифицируется как `4xx → DLQ`.

**Код.** `src/backend/sinks/yandex-metrica-sink.ts` (+ тесты), `src/backend/setup.ts`.

## Пробелы

- Яндекс.Метрика не проверена живой отправкой (нет счётчика/OAuth); клиентский сбор
  `yandex.client_id` в трекере не делался.
- Алерты: одна серия на правило (без группировки по измерению), нет silences/inhibition,
  аномалий и burn-rate; история чистится раз в 30 дней задачей maintenance.
- Диспетчер очереди не защищён от мультипроцессного запуска (`SKIP LOCKED`/worker-роль) —
  актуально при `ROLE=worker`.
- Release health (crash-free sessions/users) не считается: релиз у issue есть, сессийной
  модели нет. Source maps не хранятся — стек браузерный.
- Воронки и retention-когорты не реализованы (deferred: сначала накопить данные и панели).
- Панели только `timeseries`, без фильтров/сегментов и сохранённых представлений.
- `pg_stat_statements` как дополнительный источник SQL-метрик не подключён (опция этапа 02).
- Self-метрики модуля (размер буферов, вытеснения) не собираются — задел на эксплуатацию.
- Opt-out — ручной флаг/браузерный сигнал; отдельной страницы «отключить аналитику» нет.
- Нет UI для партиций/размера журнала; task `metrics.maintenance` активна только после
  настройки расписания в админке.
- Каталог — агрегат по `metrics.events` без отдельного реестра определений (`metrics:definitions`),
  он появится вместе с `emit` бизнес-событий (этап 03).
- `module-metrics` — обязательный модуль в `apps/*` (не optional peer): выключение модуля
  из сборки не проверялось, guard `has('metrics')` у потребителей есть.
