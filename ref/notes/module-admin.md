# module-admin — заметки разработчиков

> Не возвращать прямую регистрацию toolbar через глобальный импорт — D-001 (accepted).
> Не давать приложениям админки собственные роуты вместо хоста — D-002 (accepted).
> Не рисовать приложениям админки собственную полосу-шапку — заголовок подставляется в шапку layout'а — D-003 (accepted).
> Не держать ключ объекта в сегменте пути роута — `:key` не матчит слэши, ключ в query — D-004 (accepted).
> Не отдавать preview-роут вложением — `inline` с `Content-Security-Policy: sandbox` для активных типов — D-004 (accepted).
> Не оставлять правку текста включённой по умолчанию — env-флаг `STORAGE_EDIT_ENABLED`, выключенный роут не регистрируется — D-005 (accepted).
> Не делать move переименованием префикса и не копировать через presigned-URL/`UploadPartCopy` — move = copy + delete — D-006 (accepted).
> Не отдавать листинг папки целиком и не строить пагинацию на offset — `cursor`/`nextToken` из S3, sentinel-скролл — D-007 (accepted).

## D-001. Сервис toolbar и optional-интеграция — accepted (2026-09-16)

**Контекст.** Auth должен работать без установки admin.
**Решение.** Типы toolbar вынесены в contracts, реестр стал frontend-сервисом admin:toolbar.
**Почему именно так.** Нет runtime-импортов из optional peer; экземпляры приложений не делят действия.
**Отвергнуто.** Обязательная админка ради одного действия; молчаливый services.has при
выбранном admin, скрывающий ошибку регистрации сервиса.
**Что изменит решение.** Потребность в интеграции после start или взаимных вызовах setup.
**Грабли.** Другие registry admin остаются глобальными; перенос вне этой задачи. registerToolbarAction удалён.
**Код.** `src/frontend/index.tsx:28, src/frontend/lib/toolbar-action-registry.ts:3`.
**Связано.** [ADR-06](../adr/06-module-conventions.md).

**Подробности D-001.** Сравнение прямого импорта и сервиса через контекст, причина
удаления публичного ChangePasswordAction, гарантии порядка и краткие альтернативы
собраны в [application-tools, D-004](application-tools.md). Это пояснение принятого
решения, не новая смена контракта.

## D-002. Режим «Приложения» — сервис admin:apps и общий хост — accepted (2026-09-17)

**Контекст.** Вкладка `apps` в шапке админки была отключённым плейсхолдером: ни роутов,
ни реестра, ни контракта. Нужен способ встраивать приложения (первое — поддержка).
**Решение.** Сервис `admin:apps` (`register/getAll/getById`) по паттерну `admin:toolbar`;
каталог `/admin/apps` и хост `/admin/apps/:appId`, рендерящий `app.component`.
**Почему именно так.** Единый контракт не требует от модуля знания layout'а и даёт
каталог; паттерн уже проверен на toolbar (D-001).
**Отвергнуто.** Собственные роуты модуля для админ-UX (как редактор workflow) — нет
каталога и единой точки входа. Глобальный Map-реестр вместо сервиса — расходится
с принятым решением по toolbar.
**Что изменит решение.** Нужда приложения в своих под-роутах — расширение контракта
полем `path` или вложенными страницами.
**Грабли.** Приложения рендерятся хостом; свой заголовок они подставляют в шапку
админки через `useAdminHeader` (D-003), отдельную полосу внутри контента не рисуют.
**Код.** `src/contracts/apps.ts:3`, `src/frontend/lib/app-registry.ts:3`,
`src/frontend/pages/admin-apps/`, `src/frontend/pages/admin-app-host/`, `src/frontend/index.tsx:32,73`.
**Связано.** [module-support-chat, D-003](module-support-chat.md).

## D-003. Шапка админки — слот подмены и оформление иконок приложений — accepted (2026-09-18)

**Контекст.** Внутри приложения рисовалась собственная полоса с хлебными крошками и
заголовком, а шапка админки продолжала показывать «Администрирование» и вкладки.
Владелец попросил подменять левую часть шапки layout'а.

**Решение.** `AdminHeaderContext` + хук `useAdminHeader(render, deps)` в module-admin:
пока страница смонтирована, layout рендерит её заголовок слева (кнопка «назад», иконка,
название), иначе — заголовок и вкладки по умолчанию. В контракт `AdminApp` добавлен
`iconClass` — tailwind-классы подложки иконки; каталог `/admin/apps` рисует иконку
в цветном квадрате (как статы на `/home`).

**Почему именно так.** Один заголовок в layout'е вместо второй полосы в контенте; API
локальный (module-admin) и не тянет platform-core. Рендер-функция стабилизируется по
`deps`, иначе состояние layout'а зациклилось бы на новом ReactNode каждый рендер.

**Отвергнуто.** Хлебные крошки в хосте приложения (лишняя полоса, крошки — дело самого
приложения); статический `slots.register` из core (нет per-route подмены и очистки);
автоподмена по location без API (приложению нельзя добавить свои действия в шапку).

**Что изменит решение.** Нужда в правой части шапки или нескольких слотах — расширять
API до именованных элементов.

**Грабли.** `useAdminHeader` вызывается безусловно (это хук), `deps` — стабильные;
объект приложения из сервиса стабилен, так что эффект срабатывает один раз.

**Код.** `src/frontend/lib/admin-header.ts`, `src/frontend/layouts/admin-layout.tsx`,
`src/contracts/apps.ts`, `src/frontend/pages/admin-apps/`, `src/frontend/pages/admin-app-host/`.

## D-004. Файловый менеджер `/admin/storage` — листинг по папкам, ключи в query — accepted (2026-09-18)

**Контекст.** Страница показывала плоскую таблицу всех ключей бакета. Владелец попросил
файловый менеджер с предпросмотром. Старые роуты `GET/DELETE /storage/objects/:key`
на вложенных ключах отвечали 404: `:key` в Fastify не матчит сегменты со слэшом — это был
латентный баг, вложенные объекты через UI было не скачать и не удалить.

**Решение.** `GET /admin/storage/objects?prefix=` — листинг одного уровня через
`listObjects(prefix, { delimiter: '/' })` из core (D-006 platform-core); в ответе
`{ prefix, prefixes, objects }`. Ключ объекта — в query (`?key=...`), не в пути; старые
роуты с `:key` заменены, потому что на вложенных ключах не работали. Добавлены
`GET /objects/view` (inline), `DELETE /storage/folder?prefix=`
(рекурсивно через `deletePrefix`, возвращает `{ deleted }`), загрузка принимает `?prefix=`
и пишет потоком (`putObjectStream`, а не `toBuffer()`). Frontend — таблица папок и файлов,
хлебные крошки на query-параметре `prefix`, поиск по текущей папке, диалог превью.

**Почему именно так.** Папка — это query-параметр, а не сегмент пути: `prefix` — строка
произвольной глубины, и путь `/admin/storage/learning/pkg/` потребовал бы ловить `*` и
разбирать сегменты заново. `prefix` нормализуется с `/` на конце, иначе `prefix=foo` захватил
бы `foobar.txt`. Выбор плеера — по расширению, а не `Content-Type`: `ListObjectsV2` тип не
отдаёт, HEAD на каждую строку — N запросов на папку. Текстовое превью читается через
`Range` до 256 КБ, а не целиком.

**Отвергнуто.** Ключ в wildcard-пути (`/objects/*`) — ломает и download, и delete, и
кодирование; query проще и однозначнее. Presigned-URL для превью — хранилище во внутренней
сети, URL браузеру недоступен (та же причина, что в комментарии старого download). Свой
листинг с `toBuffer()` на загрузке — держит файл в памяти (лимит multipart 100 МБ).
Обрезка имени файла до basename на бекенде загрузки — браузер и так шлёт basename, а
обрезка ломает легитимные имена с точками и портит диагностику; вместо этого нормализуется
только `..` и путь. Хранить текущую папку в state компонента — теряется на перезагрузке и
не даёт ссылку на папку; query-параметр даёт и то, и другое.

**Что изменит решение.** Появление прав доступа к объектам (сейчас — только «вошёл»):
фильтрация листинга по правам, отдельные роуты на действие. Постраничный листинг: сейчас
папка отдаётся целиком, для очень больших папок понадобится токен.

**Грабли.** Маркерные объекты папок (`foo/`) бекенд отсеивает из `objects`, но они остаются
в бакете и удаляются вместе с папкой. `DELETE /storage/folder` без `prefix` отвечает 400, а
не сносит бакет: `deletePrefix('')` в core бросает исключение. `alert`/`confirm` — текущий
стиль админки, не менять точечно. `Range` на текстовое превью отвечает `206` — для файлов
меньше лимита сервер вернёт `200` с полным телом, обе формы обрабатываются одинаково.

**Правка текста (дополнение 2026-09-29).** Добавлен `PUT /storage/objects?key=` — JSON
`{ content }`, `bodyLimit` 8 МБ (потолок редактора либы — 5 МБ текста, JSON-тело чуть больше).
Существование объекта проверяется `headObject` (`404`, новый объект не создаётся),
`contentType` сохраняется, при его отсутствии — `text/plain; charset=utf-8`. UI отдаёт это в
`FilePreviewDialog` через `mode="edit"`/`onSave`, сохранение инвалидирует листинг. Редактор
включает сама либа — только для текстовых типов.

**Код.** `src/backend/routes/storage.ts`, `src/frontend/pages/admin-storage/`,
`src/contracts/storage.ts`.
**Связано.** D-006 platform-core (`delimiter`), D-002 (приложения админки),
`ref/notes/file-viewer.md` D-006.

## D-005. Правка текста — env-флаг `STORAGE_EDIT_ENABLED`, по умолчанию выключена — accepted (2026-09-29)

**Контекст.** Правка текста из превью (дополнение к D-004) оказалась включена в любом деплое:
`PUT /storage/objects` регистрировался безусловно, а UI всегда открывал `mode="edit"`. Владелец
попросил запретить по умолчанию и включать флагом.

**Решение.** Возможность задаётся переменной окружения `STORAGE_EDIT_ENABLED` (default `false`).
Флаг читается один раз при регистрации роутов: пока он не `true`, `PUT` **не регистрируется
вовсе** (404), появляется `GET /storage/config` → `{ editEnabled }`, и фронт передаёт
`mode="edit"`/`onSave` только при `true`.

**Почему именно так.** Env — минимальная единица: это возможность деплоя, а не данные, менять
её в рантайме смысла нет. Не регистрировать роут, а не отвечать `403`: выключенная возможность
не должна существовать на поверхности API. Спрятать только кнопку в UI — оставить эндпоинт
открытым любой аутентифицированной сессии. Фронту нужен источник истины — отсюда `/storage/config`.

**Отвергнуто.** Настройка в БД с тумблером в админке по образцу support-chat: таблица,
миграция, GET/PATCH-роут, DTO, UI — несоразмерно для одного булева. UI-only флаг — не закрывает API.

**Что изменит решение.** Потребность переключать правку без рестарта или задавать её на
пользователя/роль — тогда настройка в БД или права доступа (см. «Что изменит решение» D-004).

**Грабли.** Значение влияет только на регистрацию роутов, поэтому тесты выставляют env до
`createStorageRoutes`; в одном процессе значение живёт до конца теста.

**Код.** `src/backend/routes/storage.ts`, `src/contracts/storage.ts`,
`src/frontend/pages/admin-storage/ui/admin-storage.tsx`.

## D-006. Explorer-UI: пакетные операции и move = copy + delete — accepted (2026-09-29)

**Контекст.** Итерация 2 довела `/admin/storage` до файлового менеджера: тулбар, дерево,
адресная строка, мультивыбор, сортировка, плитка, контекстное меню, диалоги. Для этого
понадобились операции, которых в хранилище не было: создать папку, переименовать,
переместить, удалить выбранное пачкой. В S3 нет ни директорий, ни переименования: «папка» —
префикс, а одну операцию move одним запросом не выразить. Пакетность нужна и на удалении:
`deletePrefix` ходил по объектам поштучно.

**Решение.** В core добавлены `copyObject(fromKey, toKey)` (S3 `CopyObject`, `CopySource` —
`"<bucket>/<encodeURIComponent(fromKey)>"`) и `deleteObjects(keys)` (пачки по 1000,
`Quiet: true`, возвращает число ключей; пустой список — no-op); `deletePrefix` переведён на
`deleteObjects` — батчинг живёт в одном месте. В `module-admin` добавлены
`POST /storage/folder` (маркер `${prefix}${name}/` с `application/x-directory`),
`POST /storage/move` (тело `{ keys, destination, name? }` → `{ moved }`; для папки —
копирование поддерева, маркер цели, удаление старого; `name` — переименование одного ключа)
и пакетный `DELETE /storage/objects` с телом `{ keys }` вместо одиночного `?key=`.

**Почему именно так.** Переименовать префикс в S3 одним запросом нельзя — перемещение папки
обязано быть копированием каждого объекта плюс удалением исходных. `CopyObject` делает это
на стороне S3, не прогоняя тело через процесс. `DeleteObjects` снимает тысячи round-trip'ов
на распакованном пакете. Все источники и коллизии проверяются до первого копирования:
транзакций в S3 нет, и частично выполненный перенос хуже отказа до него. Маркер цели при
переносе папки нужен, чтобы пустая папка осталась папкой. Переименование выражено через
move в ту же папку с `name`, а не отдельным роутом: у обеих операций одна механика.

**Отвергнуто.** Переименование префикса как одна операция — S3 такого не умеет. Presigned-URL
на каждый объект и клиентское копирование — хранилище во внутренней сети, браузеру URL
недоступен (та же причина, что в D-004). `UploadPartCopy` (multipart copy) — сложность ради
файлов, которых на платформе нет; `CopyObject` покрывает рабочие размеры. Одиночный
`DELETE ?key=` рядом с пакетным — два роута на одну операцию; прежняя форма удалена.

**Что изменит решение.** Пагинация листинга (`nextToken`) для очень больших папок; права
доступа к объектам; metadata-роут, отдающий `Content-Type`/`etag` (сейчас диалог свойств
показывает `—`, `ListObjectsV2` тип не возвращает); переезд на хранилище с настоящими
директориями.

**Грабли.** `CopySource` кодируется целиком (`encodeURIComponent`): без этого пробелы и
кириллица в ключе делают строку неоднозначной и объект «не находится». `DeleteObjects`
принимает не больше 1000 ключей за запрос — больше режется на пачки. В SeaweedFS вложенные
пустые папки — записи filer, а не объекты листинга: `deletePrefix` добивает только маркер
самого префикса, поэтому такие вложенные папки могут пережить удаление или перенос родителя
(хвост в roadmap). Move папки — последовательные `copyObject`, прогресса нет; ошибка в
середине оставляет частичный перенос (часть объектов уже скопирована, исходные ещё на месте).

**Код.** `packages/platform-core/src/contracts/backend/storage.ts:83,89`,
`packages/platform-core/src/backend/services/storage-service.ts:87,103`;
`src/backend/routes/storage.ts:66,97,161`, `src/contracts/storage.ts:25,30,46`,
`src/frontend/pages/admin-storage/`.

**Связано.** D-004 (листинг и ключи в query), D-005 (флаг правки);
`ref/notes/platform-core.md` D-006 (`delimiter`); `ref/plans/2026-09-29-admin-storage-roadmap.md`
(итерация 2); `ref/plans/2026-09-29-admin-storage-explorer-ui.md`.

## D-007. Листинг хранилища постраничный: `cursor`/`limit` и бесконечный скролл — accepted (2026-09-30)

**Контекст.** D-006 («Что изменит решение») называл пагинацию первым же условием пересмотра:
`GET /storage/objects` отдавал папку целиком, и на десятках тысяч объектов ответ и память
роута раздувались без границ. Core к этому моменту получил постраничный `listObjects`
(`maxKeys`/`nextToken` — `ref/notes/platform-core.md` D-007).

**Решение.** Роут принимает `limit` (дефолт `200`, потолок `1000`, мусор — `400`) и `cursor`
(opaque-токен из `nextToken`; пустая строка или дубль параметра — `400`), отвечает
`{ prefix, prefixes, objects, nextToken? }`. Список страницы перешёл на `useInfiniteQuery`;
sentinel-строка в конце списка/плитки (`IntersectionObserver`, `rootMargin: 200px`) догружает
следующую страницу, пока есть `nextToken`. Дерево папок и диалог перемещения остались
«первой страницей», но с `limit=1000` — курсор им не нужен.

**Почему именно так.** `nextToken` — единственный корректный курсор S3, сервер отдаёт его сам.
Потолок `1000` равен лимиту `ListObjectsV2`: больше одного ответа всё равно не получить.
Sentinel вместо кнопки — привычное поведение файловых менеджеров, а исчерпание токена
(`hasNextPage === false`) гарантированно снимает наблюдателя. Первая страница дерева/диалога
с большим `limit` — компромисс: до 1000 подпапок видно, глубже — нет.

**Отвергнуто.** Offset-пагинация (`?page=`) — на S3-листинге её нечем выразить. Кнопка
«Показать ещё» вместо sentinel — лишний клик на массовом сценарии. Серверный поиск с
курсором — вне рамок: поиск остаётся клиентским по догруженному.

**Что изменит решение.** Серверная фильтрация/поиск или запрос «показать всё» для дерева —
тогда появится отдельный контракт; жалобы на обрезанное дерево при >1000 подпапок — тогда
дереву понадобится собственная ленивая догрузка узлов.

**Грабли.** Активный поиск, не находящий ничего в догруженном, заменяет список пустым
состоянием вместе с sentinel'ом — догрузка останавливается до очистки поиска (совпадения на
дальних страницах не подтянутся). Ошибка запроса следующей страницы заменяет весь листинг
экраном ошибки — уже загруженные строки теряются. Ключи обычной и бесконечной фабрик обязаны
различаться (сегмент `first-page`): под одним ключом React Query не держит две формы данных.
После мутаций загруженные страницы перечитываются по инвалидации общего префикса ключа.
