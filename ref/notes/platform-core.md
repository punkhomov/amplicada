# platform-core — заметки разработчиков

> Стоп-лист: не объявлять SQL-предикат универсальным контрактом поискового провайдера — D-001 (accepted).

## D-001. Первый полнотекстовый поиск и граница провайдера — accepted (2026-09-16)

**Контекст.** Поле поиска списка admin было заглушкой. Списки документов собираются динамическими JOIN по расширениям, поэтому единого столбца для готового GIN-индекса нет.
**Решение.** Первый адаптер строит PostgreSQL FTS по текстовым колонкам зарегистрированного списка. `resolveWhere` объединяет поиск с фильтрами, типом и soft-delete, чтобы count, страница и экспорт совпадали. `ListFieldMeta.searchable` управляет участием отдельных полей.
**Почему именно так.** Работает для существующих типов без схемной миграции, отдельного индекса и фоновой синхронизации. Поиск выполняется в БД до пагинации.
**Отвергнуто.** Поиск только по загруженной странице — пропускает остальные документы и искажает total. Синтетическая OR-группа фильтров — не даёт токенизации и морфологии. Универсальный интерфейс `buildWhere(): SQL` для всех будущих движков — привязывает внешние индексы к Drizzle/PostgreSQL.
**Что изменит решение.** Профилирование на крупных списках либо требование другого движка: тогда нужен отдельный контракт поискового провайдера с полным описанием фильтров, сортировки, пагинации, общего количества и гидратации результатов. Варианты — `ref/plans/2026-09-16-document-search-providers.md`.
**Грабли.** Выражение по JOIN не использует единый GIN-индекс; `russian` не обещает морфологию других языков. Короткий запрос может быть дорогим на большой таблице. Минимальный smoke на временном PostgreSQL 16 прошёл для обычной и customFields-колонки, но полный сценарий приложения и производительность на реальных объёмах ещё не проверены.
