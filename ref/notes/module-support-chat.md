# module-support-chat — заметки

> - Не переводить треды и сообщения на Document System — D-001 (rejected).
> - Не заменять SSE на polling «для простоты» — D-002 (rejected).
> - Не рендерить приложения админки их собственными роутами — D-003 (rejected).
> - Не собирать транскрипт вручную на div'ах вместо MessageScroller — D-004 (rejected).
> - Не делать виджет на Sheet и не подписывать каждое сообщение автором/датой — D-004 (rejected).
> - Не писать AI-сообщения прямым INSERT в обход сервиса `support-chat` — D-005 (rejected).
> - Не хранить файлы в БД и не отдавать их напрямую из S3 — D-006 (rejected).

## D-001. Треды и сообщения — обычные таблицы модуля, не документы — accepted (2026-09-17)

**Контекст.** Первое встроенное приложение админки: обращения пользователей и ответы
поддержки. Данными управляет собственный UI приложения, а не generic-карточка документа.

**Решение.** Схема `support_chat`: `threads` (один тред на пользователя, FK на
`core.identity_user`) и `messages` (FK на тред, каскадное удаление). Document System
не используется, `core.document_index` не задействован.

**Почему именно так.** Прецедент — заявки `module-hr-request` (`hr_requests.requests`
не документы, документом является только тип заявки). Меньше кода и миграций: нет FK
на индекс, нет `allocateDocumentId`, не нужно описывать extension-поля и list-колонки
для UI, которым не пользуются. Фильтры и сортировка — прямые Drizzle-запросы.

**Отвергнуто.** Тред-документ (виден в режиме «Данные», generic card/list бесплатно):
заявки «Данные» и «Приложения» не должны дублировать одну сущность; поля треда
(статус, счётчики прочтения) не редактируются через карточку.

**Что изменит решение.** Потребность в экспорте/импорте обращений через админку или
в унифицированной отчётности по документам.

**Грабли.** `identity_user` — документ, поэтому тестового пользователя в БД нужно
заводить через `core.document_index` + `identity_user` + `password_credential`
(иначе FK). Эти строки не удаляются вместе с тредом.

**Код.** `src/backend/schemas/`, `migrations/0000_init.sql`.

## D-002. Доставка сообщений — SSE + Redis fan-out, а не polling — accepted (2026-09-17)

**Контекст.** Сообщение должно появляться у собеседника без перезагрузки; API может
работать несколькими процессами (`ROLE=web|worker`, реплики), в проекте уже есть
SSE-прецедент для задач админки.

**Решение.** После записи сообщения маршрут публикует событие в Redis-канал
`support-chat:events`; каждый процесс подписан на канал и реэмитит события в локальный
`eventBus`, SSE-маршруты отдают их клиентам (пользователю — только свой тред).
Фронтенд инвалидирует React Query-кэш по событиям; `refetchInterval` 60 c оставлен
страховкой от обрыва соединения.

**Почему именно так.** Прямой `eventBus` без Redis доставлял бы событие только клиентам
своей реплики; polling даёт задержку и лишние запросы. Паттерн повторяет core
`TaskEventBridge`, но на собственном канале модуля (обобщать core не стали — вне задачи).

**Отвергнуто.** Polling раз в 3–5 секунд. WebSocket — избыточен для односторонней доставки.
Обобщение `TaskEventBridge` в core — трогает инфраструктуру задач, отложено.

**Что изменит решение.** Появление обобщённого Redis→eventBus моста в core — модуль
перейдёт на него.

**Грабли.** Подписка создаётся в `setup`, стартует в `start`, снимается в `stop`
до `redis.quit()` (порядок шагов в core `shutdown.ts`). События матчатся по `userId`
из payload; админ-поток не фильтруется — паритет с REST, где прав нет.

**Код.** `src/backend/services/event-bridge.ts`, `src/backend/routes.ts`,
`src/frontend/lib/use-support-chat-events.ts`.

## D-003. Приложения админки — реестр-сервис и общий хост — accepted (2026-09-17)

**Контекст.** В админке заготовлен режим «Приложения» (вкладка `apps`, `disabled: true`),
но ни реестра, ни роутов, ни контракта не было. Приложение — UI, встраиваемый в админку.

**Решение.** `module-admin` регистрирует frontend-сервис `admin:apps` (`register/getAll/getById`),
каталог `/admin/apps` и хост `/admin/apps/:appId`, который рендерит `app.component`
под шапкой админки. Модуль-приложение регистрирует вклад с id, i18n-ключами, иконкой
и компонентом; своих роутов для админ-UX не заводит.

**Почему именно так.** Единый хост — «встроенность» буквально: шапка, хлебные крошки и
навигация админки общие; модулю не нужно знать про `layout: 'admin'` и вкладку.
Контракт и сервис повторяют проверенный паттерн `admin:toolbar` (D-001 в notes module-admin).

**Отвергнуто.** Роуты, регистрируемые самим модулем (как `module-workflow` для редактора):
годится для отдельных страниц, но не даёт каталога и единого места для приложений.
Глобальный реестр-модуль без сервиса — расходится с принятым паттерном admin.

**Что изменит решение.** Потребность приложения в собственных под-роутах или параметрах
в URL — тогда контракт дополнится `path` или вложенными страницами.

**Грабли.** `titleKey`/`descriptionKey` — i18n-ключи с неймспейсом модуля
(`support-chat:app_title`), не готовые строки: setup выполняется до рендера и вне React.
Статические `/admin/apps*` должны регистрироваться до динамического `/admin/:type`
(ранжирование React Router их и так разводит, но порядок читается легче).

**Код.** `packages/module-admin/src/contracts/apps.ts`,
`packages/module-admin/src/frontend/pages/admin-apps/`,
`packages/module-admin/src/frontend/pages/admin-app-host/`.

## D-004. Транскрипты — на вендоренном MessageScroller — accepted (2026-09-17)

**Контекст.** Первая версия чата собирала ленту вручную (`div`'ы + `scrollIntoView`
на каждое сообщение). В UI-ките core уже лежит вендоренный `message-scroller`
(PR #4, `@shadcn/react`), спроектированный ровно под чат: якоря ходов, следование
за live edge только пока читатель там, сохранение позиции, «прыгнуть к последнему».

**Решение.** Виджет и админ-страница используют `MessageScrollerProvider` +
`MessageScroller`/`Viewport`/`Content`/`Item`/`Button`, сообщения рендерит общий
`widgets/chat-transcript`. Подпись автора — только на первом сообщении группы
(подряд идущие сообщения одной роли схлопываются), время — внутри пузыря на последнем
сообщении группы, у входящих групп — аватар (инициал пользователя в админке,
иконка поддержки/AI в виджете), углы пузырей соседних сообщений подрезаны.
Виджет — не Sheet, а карточка снизу-справа (`Card`, `fixed bottom-20 right-4`).
Отправка вызывает `scrollToEnd()` в composer'е (он рендерится внутри провайдера —
только так работает `useMessageScroller`).

**Почему именно так.** Ручной скролл теряет позицию при чтении истории и не умеет
«следовать, пока я внизу»; примитив даёт это бесплатно и живёт в ките, а не в модуле.

**Отвергнуто.** Своя реализация авто-скролла; виртуализация (примитив держит тысячи
строк, см. доки реестра). Виджет на `Sheet` (закрывает пол-экрана, не «мессенджер»)
и подпись «автор сверху + дата снизу» у каждого сообщения — шумно; группировка
и время в пузыре ближе к телеграму.

**Что изменит решение.** Переход на виртуализацию для очень длинных тредов (примитив
оставляет такую возможность через `MessageScrollerViewport`).

**Грабли.** `MessageScrollerProvider` не принимает `className` — обёртка-div нужна
снаружи. Смена треда в админке требует `key` на провайдере, иначе сохраняется позиция
предыдущего треда. Отступы между группами сделаны `mt-*` на `MessageScrollerItem`
(у `MessageScrollerContent` `gap-0`), а не `gap` — иначе не отличить группу от строки.

**Код.** `src/frontend/widgets/chat-transcript/`,
`src/frontend/features/support-chat-widget/ui/`,
`src/frontend/pages/support-chat-admin/ui/support-chat-admin-page.tsx`.

## D-005. Задел под AI: роль `ai` и публичный сервис `support-chat` — accepted (2026-09-17)

**Контекст.** AI-провайдер появится позже, но данные и точки подключения лучше
заложить сразу, чтобы не ломать формат сообщений потом.

**Решение.** Миграция `0001_ai_author`: `author_role` допускает `'ai'`, `author_id`
стал nullable. Модуль регистрирует backend-сервис `support-chat`
(`SupportChatBackendService`): `appendMessage({ threadId, authorRole, body, authorId? })`
и `getThreadMessages(threadId)`. Сервис сам публикует SSE-события, поэтому любой
будущий ответчик (AI-модуль) получает доставку и счётчики бесплатно.
В UI роль `ai` рендерится как входящее сообщение с подписью «ИИ-помощник».

**Почему именно так.** Прямой INSERT из чужого модуля не публикует события и обходит
инварианты треда (updated_at, отметки прочтения). Событийный путь
`support-chat.message.created` уже есть — AI-модулю останется подписаться и ответить.

**Отвергнуто.** Отдельная таблица/тип документа под AI-ответы; ответы от имени
«admin»-пользователя; публикация событий в вызывающем коде (дублирование и рассинхрон).

**Что изменит решение.** Появление реального AI-провайдера: возможно, потребуется
`ai_status` (генерация/ошибка) и стриминг ответа частями.

**Грабли.** Непрочитанные у поддержки считаются только по сообщениям роли `user`
(ответы `ai` не создают очередь на ответ) — при добавлении других ролей правило
нужно пересмотреть. `authorId` в DTO теперь nullable.

**Код.** `migrations/0001_ai_author.sql`, `src/contracts/backend.ts`,
`src/backend/setup.ts`, `src/backend/services/support-chat-service.ts`.

## D-006. Вложения — метаданные в БД, файл в S3-хранилище core — accepted (2026-09-17)

**Контекст.** В чате нужны файлы: скриншоты, документы. В платформе уже есть сервис
`storage` (S3/SeaweedFS) с потоковой загрузкой, presigned URL и лимитами на маршруте.

**Решение.** Одно вложение на сообщение, четыре nullable-колонки в
`support_chat.messages` (`attachment_key/name/mime/size`), миграция `0002`. Поток:
`POST /api/support-chat/attachments` (multipart-часть `file`, лимит 10 МБ, имя
санитизируется, ключ `support-chat/<userId>/<uuid><ext>`, размер — через `headObject`)
→ клиент шлёт `attachment: { key, name, mime, size }` вместе с сообщением.
Загрузка идёт тем же `ApiClient` (он умеет `FormData`), скачивание — через
`GET /api/support-chat/attachments/:messageId`, который стримит объект из `storage`.

**Почему именно так.** Файлы в БД (bytea) раздувают дампы и бэкапы; presigned URL
протекает наружу и живёт своей жизнью; отдельная таблица вложений при одном файле
на сообщение — лишний join. Проверка владения ключом (`isAttachmentKeyAllowed`) не даёт
приложить чужой объект: разрешены только префиксы автора и владельца треда, хвост
обязан быть нашим uuid'ом (формат ключа задаёт `buildAttachmentKey`, тесты — в
`attachments.test.ts`).

**Отвергнуто.** `bytea` в `messages`; presigned URL в DTO (нельзя отозвать, нет проверки
владельца в момент скачивания); отдельная таблица `attachments` (преждевременно);
загрузка файла в одном запросе с текстом (multipart усложняет JSON-API и SSE-ответ).

**Что изменит решение.** Несколько файлов на сообщение, превью-генерация, лимиты по
типам, антивирус — тогда понадобится таблица вложений и очередь обработки.

**Грабли.** `body` остаётся `NOT NULL` — сообщение без текста пишет пустую строку;
сервер принимает пустой текст, только если есть вложение. Публичный `appendMessage`
принимает `attachment` для полноты, но AI-ответы вложений не шлют.

**Код.** `migrations/0002_attachments.sql`, `src/backend/services/attachments.ts`,
`src/backend/routes.ts`, `src/frontend/widgets/chat-composer/`.

## D-007. Карточка виджета и композер — композиция кита, без самодельных кнопок — accepted (2026-09-17)

**Контекст.** Референс shadcn (message-scroller demo): карточка с шапкой, подзаголовком
и empty state; композер с плюсом для файла и маленькой круглой отправкой. Первая
итерация была на `Sheet`, с `Textarea` + текстовой кнопкой «Отправить» и кривым
аватаром (иконка в 32×16 пилюле).

**Решение.** Виджет — `Card` снизу-справа: шапка `CardTitle` + `CardDescription`,
empty state на компонентах `Empty`, транскрипт или спиннер загрузки. Композер —
`widgets/chat-composer`: контейнер `rounded-3xl bg-muted`, `Textarea` без рамки,
слева `+` (`variant="ghost" size="icon-sm" className="rounded-full"`) за скрытым
`<input type="file">`, справа `icon-sm` круглая отправка (`ArrowUpIcon`, `Spinner`
во время отправки). Чип загружаемого файла — вендоренный `Attachment`.
Имя и тег роли — первой строкой внутри пузыря первого сообщения группы (как в
мессенджерах), аватар — `MessageAvatar className="size-8"` (иконка или инициал)
на последнем сообщении группы; на остальных сообщениях — пустой `MessageAvatar`,
который резервирует гуттер и выравнивает пузыри группы по одной границе
(канон из доков `Message`: «render an empty MessageAvatar on the earlier messages»).

**Почему именно так.** Знакомый по референсу паттерн; размер задаётся на аватаре —
раньше иконка 16 px в контейнере `min-w-8` давала вытянутую пилюлю и «съезд» вниз.
Имя и тег вынесены внутрь пузыря (а не `MessageHeader` над ним), потому что подпись
вне пузыря читалась как отдельный, «висящий» элемент, а тег уезжал к краю строки.
Пустой слот аватара убирает горизонтальный разнобой пузырей внутри группы: раньше
сообщение с аватаром сдвигалось вправо относительно остальных. Плюс и стрелка —
те же кнопки кита, что в демо shadcn.

**Отвергнуто.** `Sheet` (перекрывает пол-экрана, не мессенджер); самодельные `<button>`/иконки
вместо `Button`; подпись автора и дата у каждого сообщения; `MessageHeader` над пузырём
для логина и тега.

**Что изменит решение.** Появление дизайн-требования на док-панель, реакции, ответы-цитаты.

**Грабли.** `MessageScrollerProvider` не принимает `className`; при смене треда в админке
нужен `key`; `ChatComposer` обязан рендериться внутри провайдера (иначе нет
`useMessageScroller`).

**Код.** `src/frontend/features/support-chat-widget/`,
`src/frontend/widgets/chat-composer/`, `src/frontend/widgets/chat-transcript/`.
