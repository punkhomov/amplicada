# module-notification-email — заметки разработчиков

> Стоп-лист. Не возвращать без новых фактов:
> - frontend-сторону для меток полей — D-002 (rejected): метки переводит backend-локаль запроса.
> - хранение email в `identity_user` — ADR-04 (rejected): контакты живут в канальном модуле.
> - проверку адреса кодом/токеном внутри модуля — D-003 (deferred): появится в фазе auth.
> - `nodemailer@7` — D-001 (accepted): взяли `^8`; **superseded_by D-005** — теперь `^10`.
> - откат на `nodemailer@8` без причины — D-005: `^10` проходит политику и имеет свои типы.
> - падать на неизвестном имени отправителя — D-006 (accepted): fail-open на `SMTP_FROM`.
> - тянуть вложения в буфер — D-007 (accepted): стрим из storage + `headObject` для лимитов.

## D-001. Версия nodemailer — accepted (2026-09-16)

**Контекст.** План уведомлений (подплан 02) предписывал `nodemailer ^7` и `@types/nodemailer`.
**Решение.** Взяли `nodemailer ^8.0.11` + `@types/nodemailer ^8.0.1`.
**Почему именно так.** На 2026-09-16 актуален nodemailer 10 (собственные типы), но все 10.x
моложе 30 дней и блокируются `minimumReleaseAge: 43200`; 9.x не имеет ни своих типов, ни
свежего `@types` (последние — 8.x). 8.0.11 и `@types` 8.0.1 опубликованы 2026-06-10, то есть
проходят политику и совпадают по мажору. API, который использует модуль
(`createTransport` + `sendMail`), между 7 и 8 не менялся.
**Отвергнуто.** `^10` — не устанавливается под политикой; `^9` — без типов; `^7` — старше
без выгоды.
**Что изменит решение.** Выход типизированного 9/10 из-под 30-дневного окна — тогда переход
на актуальный мажор.
**Код.** `package.json`, `src/backend/services/email-channel.ts`.

## D-002. Backend-only модуль — accepted (2026-09-16)

**Контекст.** План рисовал frontend-сторону с `setup.tsx` «ради locales меток в админке» и
`tailwind.css`.
**Решение.** Frontend-стороны нет: `exports` модуля содержат только `./backend` и `./contracts`.
Метки `notification-email:field_email` / `field_verified_at` живут в `src/backend/locales/` и
переводятся backend-локалью запроса (так же, как `auth-password:field_password_hash`).
**Почему именно так.** Карточка документа приходит с сервера, метки резолвит `tl(t, label)` в
`document-runtime` — frontend-локали для этого не используются. Своих роутов и компонентов у
модуля нет, значит сторона была бы пустой, а `tailwind.css` — мёртвым импортом в composition.
**Отвергнуто.** Пустая frontend-сторона «на будущее» — генератор тянул бы CSS и setup без
содержимого.
**Что изменит решение.** Появление своего UI (например, самостоятельная смена email с
верификацией) — тогда `./frontend` и `tailwind.css` добавятся.
**Код.** `package.json`, `src/backend/locales/index.ts`, `src/backend/documents/user.ts:17`.
**Связано.** [ADR-06](../adr/06-module-conventions.md).

## D-003. Подтверждение адреса — deferred (2026-09-16)

**Контекст.** Самостоятельная смена email пользователем требует подтверждения письмом
(токен, срок, single-use).
**Решение.** Сейчас подтверждение = сохранение админом: `save` проставляет `verified_at = now()`.
Поле `verifiedAt` доступно только для чтения.
**Почему именно так.** Фаза auth (регистрация/сброс пароля) ещё не начата; преждевременный
токен-механизм пришлось бы перепроектировать под rate-limit и user-enumeration-защиту, которых
в проекте пока нет.
**Отвергнуто.** Верификация внутри модуля до появления auth-флоу.
**Что изменит решение.** План регистрации/сброса пароля: пользователь меняет адрес →
`verified_at` сбрасывается → письмо-подтверждение. Схема миграции не потребует.
**Грабли.** Пустой `email` в `save` игнорируется: очистить адрес из карточки нельзя. Это
осознанно (адрес — рабочий контакт), но при появлении UI смены адреса поведение придётся решать.
**Код.** `src/backend/documents/user.ts`, `src/backend/services/email-channel.ts`.

## D-004. Канал не зарегистрирован без SMTP — accepted (2026-09-16)

**Контекст.** Не всякий узел имеет почту; сборка без SMTP должна оставаться рабочей.
**Решение.** Нет `SMTP_HOST` → `setup` логирует `SMTP не сконфигурирован` и не регистрирует
канал. Ядро в этом случае найдёт только каналы, которые адрес не знают, и `send()` вернёт `null`.
**Почему именно так.** Ошибка «узел без почты» не должна валить bootstrap: доставка — не
критический путь бизнес-действия.
**Отвергнуто.** Падать на старте; регистрировать no-op канал (скрыл бы отсутствие почты).
**Что изменит решение.** Появление требования «узел обязан иметь канал» (например, для
второго фактора в проде) — тогда это станет ошибкой конфигурации узла.
**Код.** `src/backend/setup.ts`.
**Связано.** [ADR-04](../adr/04-notifications.md).

## D-005. nodemailer `^10` — accepted (2026-09-30), supersedes D-001

**Контекст.** D-001 держал `^8`, потому что 10.x был младше 30-дневного окна `minimumReleaseAge: 43200`.
**Решение.** Перешли на `nodemailer@^10.0.10`, `@types/nodemailer` удалён (в 10.x свои типы).
**Почему именно так.** Политика узла снижена до 7 дней (`ref/notes/platform-core.md`, D-007): 10.x
проходит окно, типы встроены, мажор актуальный.
**Отвергнуто.** Оставаться на `^8` «по инерции»; `^9` (без своих типов).
**Что изменит решение.** Новый мажор вне окна политики — тогда ждать или пинить с обоснованием.
**Код.** `package.json`, `pnpm-lock.yaml`.
**Связано.** D-001 (superseded), `ref/notes/platform-core.md`.

## D-006. `SMTP_SENDERS`: именованные отправители, fail-open — accepted (2026-09-30)

**Контекст.** Контракт v2 (ADR-07) вводит `sender` — имя отправителя узла; канал резолвит его в
`from`/`replyTo`.
**Решение.** `SMTP_SENDERS` — JSON-карта `имя → { from, replyTo? }`. Известное имя → его адреса;
явный `replyTo` сообщения приоритетнее sender-овского; неизвестное имя → warning + `SMTP_FROM`.
Битый JSON/запись без `from` не роняют узел.
**Почему именно так.** Fail-open: опечатка в имени не должна глушить транзакционные письма
(сброс пароля важнее строгости конфига).
**Отвергнуто.** Ошибка/`null` на неизвестное имя (как при отсутствии канала) — тихая потеря писем.
**Что изменит решение.** Потребность в строгой валидации конфига узла (health-check на старте).
**Грабли.** Карта читается один раз в `setup` — смена env требует рестарта.
**Код.** `src/backend/services/email-channel.ts:readSendersConfig/selectSender`.
**Связано.** [ADR-07](../adr/07-notification-contract-v2.md).

## D-007. Вложения: лимиты и стрим — accepted (2026-09-30)

**Контекст.** Контракт v2 несёт `attachments` (объекты storage); SMTP-провайдеры режут письма по размеру.
**Решение.** Лимиты `NOTIFICATION_ATTACHMENT_LIMITS` (10 МиБ/файл, 20 МиБ/письмо). При отправке
канал делает `headObject` (существование + **реальный** размер; манифесту `size` не верится) и
стримит объект в `sendMail`. Превышение/пропажа — обычная ошибка доставки с `lastError`.
**Почему именно так.** Манифест редактируем через документное API — доверять его полю `size`
нельзя; буфер на больших файлах не нужен.
**Отвергнуто.** Верить `size` из манифеста; читать объект целиком в память; silent skip при
превышении (получатель не узнал бы о проблеме).
**Что изменит решение.** Ограничение конкретного SMTP-провайдера — лимиты станут env-настройкой.
**Грабли.** Сумма считается по фактическим размерам, а не по манифесту; проверка на загрузке
(админ-роут) — только UX-барьер, авторитетная — на отправке.
**Код.** `src/backend/services/email-channel.ts:resolveAttachments`.
**Связано.** [ADR-07](../adr/07-notification-contract-v2.md).
