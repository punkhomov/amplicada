# Application tools — заметки разработчиков

> Подробное сравнение «было → стало», причины и альтернативы — D-004 ниже.
>
> Стоп-лист:
> - Не возвращать общую папку профилей и скрытое переключение через env — D-001 (accepted).
> - Не переносить тестовые конфиги к демоприложениям — D-001 (accepted).
> - Не возвращать списки сторон/CSS/requires в amplicada — D-003 (accepted).
> - Не активировать вложенные пакеты автоматически и не писать пути .pnpm — D-003 (accepted).

## D-001. Композиция без обязательных профилей — accepted (2026-09-15)

**Контекст.** При переходе к discovery остались full/minimal в корне, env-переключатель
с поиском workspace и глобальные входы Turbo. Пользователь попросил убрать эти остатки.
**Решение.** Примеры лежат в `test/fixtures/applications/` и копируются тестом в отдельный
временный проект с фиктивными пакетами. CLI по умолчанию читает dependencies;
`--config` остаётся явной возможностью. Env-переключатель и связанные настройки удалены.
**Почему именно так.** Состав приложения уже выражен его зависимостями; второе описание
не нужно. Проверка генератора не должна зависеть от наличия конкретных модулей в apps.
**Отвергнуто.** Обязательный общий конфиг или автоопределение профиля — добавляют второй
источник состава и мешают сценарию «добавил зависимость, установил, собрал».
**Что изменит решение.** Реальная задача нескольких составов одного приложения,
которую не покрывает явный `--config` или отдельные package.json.
**Грабли.** Обычный build регенерирует imports из dependencies даже после ручного
`--config`. Кэш отдельной задачи с конфигом должен учитывать её inputs. Тесты создают
только фиктивные package.json, ничего не устанавливают. Обязательная политика установки
распространяется на все внешние проверки; её нельзя ослаблять ради прохождения smoke-теста.
**Код.** `packages/application-tools/src/cli.ts:23`,
`packages/application-tools/src/application.test.ts:169`, `turbo.json`.
**Связано.** `ref/adr/05-application-composition.md`, `ref/guides/application-composition.md`.

## D-002. Один граф из package.json — superseded (2026-09-16)

**superseded_by:** D-003.

**Контекст.** Отдельные графы и описание экспортов дублировали пакетную информацию.
Пользователь согласовал включение всей функциональности обязательных модулей, включая
admin у auth и frontend workflow у HR.
**Решение.** Контракт определён [ADR-06](../adr/06-module-conventions.md): boolean-флаг,
фиксированный экспорт module, рекурсивное включение обязательных пакетных зависимостей.
**Почему именно так.** Автор модуля описывает зависимости один раз. Порядок обеих сторон
можно получить из одного графа; стабильные runtime id не зависят от npm-имени.
**Отвергнуто.** Исполнение модулей для discovery; угадывание имён экспортов; отдельный
requires и списки зависимостей сторон; автоматическое включение optional peers.
**Что изменит решение.** Подтверждённая необходимость разных графов сторон, которую
невозможно разумно выразить границами модулей и библиотек.
**Грабли.** Зависимость активирует все доступные стороны. --config задаёт корни, поэтому
не позволяет исключить обязательный модуль. Изолированный вложенный пакет должен быть
импортируем из приложения; CLI выдаёт ошибку вместо абсолютного импорта из .pnpm.
**Код.** `packages/application-tools/src/application.ts`, `packages/module-hr/src/contracts/manifest.ts`.
**Связано.** `ref/adr/06-module-conventions.md`. D-001 продолжает действовать.

## D-003. Явный состав и порядок optional peers — accepted (2026-09-16)

**Контекст.** Внешняя установка auth показала, что pnpm не делает вложенный admin
импортируемым из приложения. Пользователь уточнил: обязательные модули устанавливаются
явно, интеграция auth с admin должна быть необязательной.
**Решение.** ADR-06: discovery выбирает только прямые dependencies. Обязательные
модули проверяются, optional peers добавляют ребро лишь между выбранными модулями.
**Почему именно так.** package.json приложения уже является полным описанием состава;
optional peer одновременно описывает совместимость и порядок доступности сервиса.
**Отвергнуто.** Автоактивация скрытых пакетов, импорты .pnpm и изменение node_modules —
противоречат явному составу. Игнорирование порядка optional peers — гонка setup.
**Что изменит решение.** Необходимость взаимных optional-вызовов в setup: сейчас цикл
явно отвергается; такую интеграцию потребуется вынести в более позднюю фазу.
**Грабли.** pnpm CLI добавляет NODE_PATH, поэтому createRequire.resolve.paths мог
найти пакет, недоступный ESM-импорту приложения. Поиск теперь локальный. Проверка
getById сообщает состав, а не readiness: поставщик должен иметь нужную сторону и
регистрировать вызываемый сервис в setup, а не start.
**Код.** `packages/application-tools/src/application.ts`, `src/application.test.ts`.
**Связано.** [ADR-06](../adr/06-module-conventions.md). Заменяет D-002; D-001 действует.

**Проверка D-003.** 14 тестов генератора, pnpm build/typecheck/test и проверка архивов
в `/tmp/amplicada-module-conventions-optional`: auth без физически установленного admin
и auth+admin. В первом случае admin отсутствует и в списке файлов TypeScript; во втором
проверены порядок, регистрация change-password и изоляция toolbar двух контекстов.
Frontend setup проверен с минимальным document для i18n, без браузерного рендера.
Backend проверен на импорт и состав без подключения БД. Живой вход/смена пароля не проверялись.
Политика установок сохранена: ignoreScripts, blockExoticSubdeps, minimumReleaseAge: 43200.

## D-004. Как и почему изменена композиция модулей — accepted (2026-09-16)

**Контекст.** Пользователь хочет подключать опубликованные модули через package.json
приложения: добавить зависимости, выполнить установку, сборку и запуск. Отдельный
перечень модулей, сторон, имён экспортов и CSS не должен повторять уже имеющиеся данные.
Эта запись подробно объясняет принятый ADR-06; она дополняет D-003, не меняя контракт.

### Было: отдельный манифест поверх пакетного

В состоянии `a5c2ac9` у HR было два описания одной обязательной связи:

```json
{
  "peerDependencies": {
    "@amplicada/module-workflow": "workspace:*"
  },
  "amplicada": {
    "id": "hr",
    "name": "HR Module",
    "requires": [],
    "backend": { "export": "hrModule", "dependencies": ["workflow"] },
    "frontend": { "export": "hrFrontendModule", "dependencies": [] },
    "styles": "./frontend/tailwind.css"
  }
}
```

Фрагмент сокращён: exports и остальные зависимости существовали отдельно.
Peer dependency описывала npm-пакет; backend.dependencies повторяла связь через runtime id.
Для изменения зависимости нужно было согласовать оба списка. Стороны и путь CSS уже
были видны в exports, но повторялись в amplicada. Имена объектов регистрации тоже
приходилось отдельно записывать в метаданные.

`requires` означал требования к составу в целом, а зависимости backend/frontend —
порядок каждой стороны. В наших модулях requires оставался пустым. Наличие пакета в
peerDependencies само по себе не означало, что его setup нужно активировать:
генератор ориентировался на отдельные требования из amplicada.

Порядок setup **уже проверялся и сортировался**. Новая итерация не вводит ещё один
планировщик и не исправляет якобы случайный порядок: она меняет источник графа и
добавляет выбранные optional peers к существующему механизму.

### Стало: один источник для каждого свойства

```json
{
  "peerDependencies": {
    "@amplicada/module-workflow": "workspace:*"
  },
  "amplicada": true
}
```

Exports остаются обычными пакетными exports. Публичный объект регистрации каждой
стороны называется module, например `export { hrModule as module } from './setup.js'`.
В contracts/manifest.ts сохраняются стабильные id/name; version читается из package.json.

| Вопрос | Было | Стало |
|---|---|---|
| Является ли пакет модулем? | Объект amplicada | Boolean amplicada: true |
| Какие стороны доступны? | exports и amplicada.backend/frontend | exports ./backend и ./frontend |
| Как импортировать регистрацию? | Имя в поле export | Фиксированное имя module |
| Откуда взять CSS? | exports и amplicada.styles | Необязательный export ./frontend/tailwind.css |
| Кто нужен раньше? | Отдельные списки runtime id для сторон | dependencies/peers с именами пакетов |
| Где id и отображаемое имя? | amplicada в package.json | Общий код contracts/manifest.ts |
| Как выбрать состав? | Прямые deps плюс требования отдельного манифеста | Полный явный набор модулей в dependencies приложения |
| Как описать необязательную связь? | Пакетная зависимость не управляла такой интеграцией | Optional peer; связь порядка существует лишь при выбранном поставщике |

Приложение явно устанавливает HR и workflow. Генератор проверяет полноту состава,
не дописывает package.json и не подключает скрытые вложенные модули. Обычные библиотеки
без amplicada: true в граф модулей не входят; их дерево зависимостей не обходится.

**Почему именно так.** Состав принадлежит приложению, совместимость зависимостей —
пакетным полям, публичные пути — exports, runtime-идентичность — коду модуля. Автор
не поддерживает второй список тех же связей. Маркер оставлен намеренно: пакет с
экспортами backend/frontend может быть библиотекой и не иметь lifecycle модуля.

### Почему отказались от автоматического включения вложенных модулей

В промежуточном варианте D-002 обсуждалось рекурсивное включение auth → admin.
Проверка архивов вне монорепозитория выявила различие между «пакет установлен для auth»
и «приложение может импортировать пакет по имени». При изоляции pnpm это разные условия.
Монорепозиторий скрывал различие, поскольку приложения уже перечисляли admin напрямую.

Пользователь уточнил желаемую модель: обязательные модули устанавливаются явно.
Поэтому исправлен сам контракт состава: генератор требует прямую dependency приложения.
Решать эту задачу путями внутрь .pnpm, hoisting или изменением node_modules больше не нужно.

Дополнительно обнаружено, что NODE_PATH из pnpm launcher мог расширять видимость CLI,
хотя ESM-импорт сгенерированного приложения так пакет не находил. packageLocation теперь
ищет только в локальных node_modules по цепочке каталогов; тест фиксирует эту границу.

### Auth и admin: от обязательного импорта к optional-сервису

Раньше auth импортировал registerToolbarAction из frontend admin и вызывал его
безусловно. Даже без admin setup реализация пакета была нужна при загрузке auth.
Попытка поставить if вокруг вызова не убрала бы верхнеуровневый импорт.

Теперь package.json auth содержит optional peer и devDependency для разработки:

```json
{
  "peerDependencies": { "@amplicada/module-admin": "workspace:*" },
  "peerDependenciesMeta": { "@amplicada/module-admin": { "optional": true } },
  "devDependencies": { "@amplicada/module-admin": "workspace:*" }
}
```

`workspace:*` — запись внутри монорепозитория; внешний потребитель использует
опубликованные версии, а не workspace-ссылки на наши исходники.

```ts
// Было: runtime-импорт реализации admin.
import { registerToolbarAction } from '@amplicada/module-admin/frontend';
// В setup: registerToolbarAction(action);

// Стало: в JS этого импорта типов нет.
import type { AdminToolbarService } from '@amplicada/module-admin/contracts';
// В setup:
if (context.modules.getById('admin')) {
  context.services.resolve<AdminToolbarService>('admin:toolbar').register(action);
}
```

`action` здесь — существующее описание кнопки; это сравнение фрагментов, не полный файл.
Admin регистрирует admin:toolbar в setup. Toolbar хранится в контексте конкретного
приложения вместо прежнего общего Map. HR-poll также переведён на этот сервис, но
его admin peer остаётся обязательным: у него есть другие импорты реализации admin.

**Почему проверяем модуль, затем resolve.** Отсутствующий optional-модуль — допустимая
конфигурация. Выбранный модуль без обещанного сервиса — дефект интеграции, который должен
вызвать ошибку. services.has с тихим пропуском смешал бы эти два случая.

**Почему отдельно проверили .d.ts.** Import type удаляет runtime-импорт, но публичный
компонент с ToolbarActionProps мог бы оставить ссылку на admin в декларациях auth.
Поэтому ChangePasswordAction стал внутренним: в публичном ./frontend остались module
и LoginPage. Проверка списка файлов TypeScript во внешнем проекте подтвердила, что
admin не нужен публичному графу типов auth.

### Где и когда гарантируется порядок

```text
Сборка: package.json приложения → выбранные модули → проверка связей → generated imports
Запуск: проверка runtime id → регистрация метаданных всех модулей → setup → start
```

Если admin выбран: setup(admin) завершается, затем setup(auth) получает сервис.
Если admin не выбран: ребра нет, setup(auth) пропускает интеграцию.
Optional-связь между двумя выбранными модулями участвует в проверке цикла наравне с
обязательной. «Необязательность» разрешает отсутствие поставщика, но не неопределённый
порядок при его наличии.

Важные границы гарантии: getById сообщает состав, а не готовность; связь должна быть
объявлена; поставщик должен иметь нужную сторону и создавать сервис в setup. Метод
сервиса, которому нужен start, нельзя вызывать раньше start. Порядок setup не управляет
порядком побочных эффектов верхнего уровня ESM: их следует размещать в lifecycle.
При ручной композиции без CLI зависимости нужно передать в runtime самостоятельно.

**Принятый компромисс.** Один пакетный граф используется для обеих сторон. Например,
frontend workflow теперь предшествует frontend HR, хотя прежний отдельный frontend-граф
HR этого не требовал. Это более строгий порядок в обмен на отсутствие второго списка.
Если пакет имеет только одну сторону, генератор фильтрует её и сохраняет зависимости
через промежуточные пакеты; он не создаёт сервисы отсутствующей стороны.

### Альтернативы — кратко

| Вариант | Решение и причина |
|---|---|
| Оставить подробный amplicada-манифест и графы сторон | Отклонено сейчас: дублирование exports и пакетных связей; цена точной настройки пока выше пользы |
| Убрать даже amplicada: true и угадывать модуль по exports | Отклонено: обычные библиотеки тоже могут иметь backend/frontend |
| Искать и подключать модули в runtime | Отклонено: состав нужен при сборке frontend/CSS; выбранная модель отдаёт runtime готовые импорты |
| Рекурсивно активировать все вложенные модули | Отклонено после внешней проверки и уточнения требований: состав должен быть явным |
| Сгенерировать .pnpm-пути, symlink или включить hoisting | Отклонено: зависимость от внутреннего дерева установки либо дополнительная конфигурация приложения |
| Выполнять генерацию в install/postinstall | Отклонено: установка идёт с ignoreScripts; генерация привязана к явной build/dev/typecheck-команде |
| Сделать admin обязательным для auth | Отклонено: вход в систему не требует административного интерфейса |
| Записать admin в optionalDependencies | Не выбранный контракт: это пакетная optional-установка; нам нужна интеграция с модулем, выбранным приложением |
| Оставить статический импорт admin и добавить if | Отклонено: импорт разрешается до setup и ломается при отсутствии пакета |
| Ловить ошибку динамического import admin | Отклонено для этой задачи: усложняет сборку frontend и загрузку; сервис уже доступен через контекст |
| Только extension points для всех optional-связей | Ограничение снято: они остаются для вкладов, но прямому вызову сервиса лучше соответствует optional peer + resolve |
| services.has с молчаливым пропуском | Отклонено для обещанного сервиса выбранного модуля: скрывает ошибки его регистрации |
| Новая DI-система или новая фаза lifecycle | Не понадобились: имеющиеся service locator и последовательный setup покрывают сценарий |

**Что изменит решение.** Реальная потребность в разных графах сторон или взаимных
вызовах optional-модулей, которую нельзя выразить границами пакетов и имеющимися фазами.
API статусов модулей — отдельная будущая задача, пользователь не просил реализовывать
его в этой итерации. Скрыто обходить циклы или объявлять getById проверкой готовности нельзя.

**Грабли и совместимость.** Старый объект amplicada теперь ошибка. Публичное имя
регистрации заменено на module; consumers старых имён должны обновить импорты.
registerToolbarAction и публичный ChangePasswordAction удалены. Runtime id сохранены,
изменений схемы/данных БД нет. Удаление пакета из состава не удаляет его данные.

**Код и проверка.** `packages/application-tools/src/application.ts:54`, `:104`, `:148`;
`packages/platform-core/src/contracts/module-registration.ts:10`;
`packages/platform-core/src/frontend/app.tsx:53`;
`packages/module-auth-password/src/frontend/setup.tsx:19`;
`packages/module-admin/src/frontend/index.tsx:28`. Проверки и их ограничения перечислены
в D-003: внешний package smoke покрывает сборку и setup, но не живой вход с БД.
**Связано.** [ADR-06](../adr/06-module-conventions.md),
[заметки auth](module-auth-password.md), [заметки admin](module-admin.md).
