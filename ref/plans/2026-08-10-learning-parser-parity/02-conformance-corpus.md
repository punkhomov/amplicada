Самый трудоёмкий подплан и самый полезный. Отвечает на вопрос, ради которого затевался весь план:
**полностью ли мы перерабатываем пакет.**

## Зачем

Все 204 теста библиотеки работают на XML, который написан мной же. Каждая фикстура — гипотеза о том,
как выглядят живые пакеты, и тест подтверждает её по построению. Опровергнуть гипотезу может только
то, что выгрузил настоящий авторский инструмент.

Собственных пакетов у нас нет. У образца они есть, и среди них — **корпус ADL CTS**: пакеты,
скопированные дословно из официального SCORM 2004 4th Edition Test Suite, то есть канонический
контракт формата.

## Часть A. Корпус

### Правило отбора

Проверено: `readBytes` во всей библиотеке вызывается **из одного места** —
[`detect.ts:160`](../../../packages/learning-parser/src/formats/detect.ts), внутри
`readDescriptorText`, и только для описателей. Всё остальное — проверка существования файла,
content-type, разрешение точки входа — работает по `source.paths`, то есть по списку имён. Байты
картинок, скриптов и вёрстки не читает ничто.

> **Описатели — дословно. Ассеты — только пути, без содержимого.**

Одно правило на все пять форматов, без исключений по весу. Цифры:

| | Байт |
|---|---|
| Все описатели всех пяти форматов | **1,5 МБ** |
| из них корпус ADL CTS | 1,28 МБ |
| XSD и DTD внутри пакетов (мы их не читаем — см. `03`) | 324 КБ, только в пути |
| Ассеты: 1111 файлов | 0, остаются только имена |

Весь корпус вместе с курсом про гольф весит меньше, чем один только `conformance/` в исходном виде.

### Как хранить «путь без содержимого»

Рядом с каждым пакетом — `files.txt` с полным списком путей; на диске лежат только описатели.
`directorySource` из `01` получает опцию читать список оттуда, а `readBytes` работает по настоящим
файлам.

Альтернатива — пустые файлы-заглушки — отвергнута: 1111 пустых записей будут мусорить в каждом
чекауте, а выгоды ноль. У выбранного варианта есть и юридическое следствие: мы **не распространяем**
картинки, скрипты и вёрстку ADL вовсе, только манифесты, которые и есть предмет разбора. Список имён
— факт о пакете, а не его содержимое.

### Происхождение — по каждому источнику отдельно

Образец под Apache 2.0, но **его `NOTICE` покрывает только его собственный код**. Фикстуры ему не
принадлежат: пакеты CTS скопированы из ADL Test Suite (их собственный `README` это прямо говорит),
курс про гольф — образцовый контент ADL, примеры cmi5 похожи на самплы CATAPULT. Лицензия
репозитория чужой материал не отмывает.

Поэтому `packages/learning-parser/fixtures/PROVENANCE.md` с разделом на корпус: откуда взят, кем
выпущен, на каких условиях, что именно из него оставлено. Приписать материалы ADL Патни было бы
хуже, чем не атрибутировать вовсе.

**Перед копированием** — прочитать условия ADL Test Suite и cmi5-самплов. Риска не ожидается (Test
Suite ровно для этого и распространяется), но проверить надо до, а не после.

### Что берём

| Корпус | Что даёт |
|---|---|
| `conformance/scorm2004/adl-cts` целиком | канонический контракт, только манифесты |
| `aicc/` целиком (`pre-ort`, `multiline-description`, `complex`) | прямо в фазу `05` предыдущего плана и в разбор CSV |
| `xapi/basic_course` | единственный, что есть |
| 2–3 пакета cmi5 | `masteryscore`, `multi_au` |
| 3–4 пакета SCORM 1.2 | `WithMetadata` → LOM, `Prerequisites`, `MalformedXml` → отчёт о находках |
| курс про гольф (SCORM 2004) | самый настоящий из всех, после правила отбора весит как манифест |

### Тест на корпусе

Один параметризованный: каждый пакет прогоняется через `parsePackage`, для CTS ожидание —
**ни одной находки уровня error**. Плюс снимок разбора (формат, точка входа, число пунктов) на
несколько показательных пакетов, чтобы регрессия была видна, а не только падение.

Оговорка из README образца, важная для нас: пакеты CTS **не самодостаточны на диске** — их SCO
собираются из общего депо при развёртывании, часть `href` не резолвится ни во что. Значит правило
`common.file-missing` на этом корпусе даст ложные срабатывания и должно быть выключено. Это первый
живой потребитель опций разбора из `04`; до тех пор — отдельным аргументом теста.

## Часть B. Сверка покрытия

Набор образца — 141 тестовый файл, 29 599 строк. Скопировать нельзя: половина ассертов дёргает
геттеры, которых у нас нет, и написаны они против модели, от которой мы намеренно отошли. Но как
**чек-лист покрытия** он лучший из имеющихся.

### Что отсекается сразу

| Группа | Файлов | Почему |
|---|---|---|
| `impl/access/*` | 11 | их слой доступа к файлам. После `01` у нас свой; сравнивать поштучно нечего |
| Сериализация Jackson | 10 | слоя нет и не нужен — но `DurationIso8601`, `DurationHHMMSS`, `PercentType`, `MeasureType` это **разбор**, а не сериализация, и они в чек-лист входят |
| Исключения | 4 | проверяют, что класс донёс свои поля |
| Фабрики, провайдеры, опции | 4 | DI; у нас одна функция `parsePackage` (кроме опций — они в `04`) |
| Тесты на POJO | ~25 | Lombok-геттеры на классах-данных; у нас `interface`, их проверяет компилятор |

### Что остаётся

Около 70 файлов: 29 по правилам валидации, 11 по LOM, 11 по разборщикам форматов, 5 по опознанию,
sequencing/rollup/objectives, пререквизиты, кодировка, версия схемы, длительности, CTS.

Форма работы: **их файл — сценарий и входные данные, ожидания пишем свои.**

### Артефакт — таблица расхождений

таблице сверки: строка на каждый применимый тест образца, столбец «наш ответ» с
тремя исходами.

| Исход | Что значит | Что делаем |
|---|---|---|
| `есть` | сценарий покрыт, ожидания совпадают по смыслу | ничего |
| `нет` | понятия у нас нет | **настоящий пробел**, заводим работу |
| `иначе` | сделано намеренно по-другому | пишем тест, закрепляющий **наш** выбор, и ссылку на решение |

Третий исход — главный приз, и он неочевиден. Сейчас решения вроде «`.cmp` не читаем», «непонятое
условие открытия оставляет пункт открытым», «отдельного `PathSecurityRule` нет, потому что
`resolveRelativePath` не выпускает за корень» живут только в `ref/`. Ничто не мешает откатить их
случайной правкой. После сверки каждое становится проверяемым утверждением.

Таблица полезна **до** того, как будет дописан последний тест: она и есть ответ на вопрос «полностью
ли», и заполняется по ходу.

## Порядок внутри подплана

1. Условия ADL и cmi5-самплов — прочитать.
2. `PROVENANCE.md`, скрипт отбора (описатели + `files.txt`), копирование.
3. Тест на корпусе CTS.
4. Сверка по ~70 файлам, заполнение таблицы, заведение работы по исходам `нет`.

Шаг 4 может изменить порядок `03`–`05` в родительском плане — на то он и меряет.

## Оценка

Корпус — день. Сверка — основной объём плана; 1 500–2 500 строк тестов, и её осмысленно дробить по
областям (валидация → форматы → LOM → sequencing), фиксируя таблицу после каждой.

## Чего не делаем

- **Полный CTS (189 пакетов).** Берём подобранный образцом срез в 15 — он покрывает все категории
  (CM, CO, CT, RU, OB, SX, MS). Расширять до полного есть смысл, только если срез начнёт что-то
  пропускать.
- **Ассеты байтами.** Кроме одного исключения: когда дойдёт до приёма пакета живьём и раздачи
  контента (подплан `03` плана модуля), понадобится один небольшой **полный** пакет с настоящими
  байтами. Один, а не 195 фотографий поля для гольфа.
- **Прогон чужих ассертов.** См. выше.
