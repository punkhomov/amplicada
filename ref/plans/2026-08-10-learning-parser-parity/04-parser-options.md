# 04 — Опции разбора

> Сделано 2026-08-10, и вышло втрое меньше, чем оценено. Три расхождения — в
> `parse-options`:
>
> - **правку 36 мест делать не пришлось.** Уровень, который ставит правило, — это уже предложение;
>   достаточно было применить политику один раз к собранному списку. План предполагал вскрыть все
>   места вызова, а вскрывать было нечего;
> - **`maxDescriptorBytes` не появился.** Потолок на чтение живёт в источнике (`zipSource`,
>   `directorySource`) — читает он. Две точки настройки одного ограничения означают, что одна из них
>   не работает;
> - **сверх плана — реестр `ISSUE_CODES` и тип `IssueCode`.** Без него `disableRules` нечем
>   проверять; попутно опечатка в самом разборщике стала ошибкой компиляции, а у `README` из
>   подплана `05` появилась готовая таблица кодов.

`parsePackage(source)` — один аргумент, ни одной настройки. Всё зашито: какие находки считать
ошибками, сколько байт читать, какие правила применять.

## Что у образца

```java
public class ParserOptions {
  private boolean strictMode = true;
  private Boolean calculateModuleSize = null;
  private Long maxManifestSize = null;
  public static ParserOptions strict();
  public static ParserOptions lenient();
}
```

Плюс переключатели через системные свойства: `validateFileExists`, `scorm2004.validateXsd`.

## Зачем это нам

Три причины, все с конкретным адресом.

**Первая — корпус CTS уже требует.** Пакеты ADL не самодостаточны на диске (их SCO собираются из
общего депо), поэтому правило `common.file-missing` даст на них ложные срабатывания. У образца ровно
для этого `FileExistenceValidator` выключен по умолчанию. Без опций `02` придётся городить костыль
в тестах.

**Вторая — severity сейчас решается за потребителя.** `issueError` против `issueWarning` вшито в
код правила. Но что считать основанием для отказа — вопрос политики, а не формата, и в рамке
предыдущего плана записано прямо: «библиотека сообщает, что нашла; решает потребитель». Сейчас
библиотека решает за него, разложив находки на две корзины по нашему вкусу.

**Третья — лимит на чтение живёт не там.** `MANIFEST_MAX_BYTES` объявлен в модуле и передаётся в
`archive.readFile`. Потолок на размер описателя — свойство разбора, а не платформы.

## Что делаем

```ts
export interface ParseOptions {
  /**
   * Строгость: какие семейства находок повышаются до error.
   * 'strict'  — всё, что спецификация называет нарушением;
   * 'default' — нынешнее поведение: ошибка только если пакет нечем запустить;
   * 'lenient' — ошибок нет вовсе, всё предупреждения (разбор ради инвентаризации).
   */
  strictness?: 'strict' | 'default' | 'lenient';
  /** Отключить отдельные правила по коду. Корпус CTS выключает `common.file-missing`. */
  disableRules?: readonly string[];
  /** Потолок на чтение одного описателя. По умолчанию 8 МБ. */
  maxDescriptorBytes?: number;
}

export function parsePackage(source: PackageSource, options?: ParseOptions): Promise<ParsedPackage>;
```

Аргумент необязательный, умолчания воспроизводят нынешнее поведение — существующие 204 теста и
модуль не трогаются.

### Как устроена строгость

Не флагом на каждое правило. У каждой находки есть код вида `семейство.что-случилось`; строгость —
это отображение семейства в severity, а правило заводит находку с **предложенной** severity, которую
политика может повысить или понизить. Механизм уже наполовину есть: `buildReport` раскладывает
находки по корзинам, ему и решать по политике, а не `issueError`/`issueWarning` на месте вызова.

Это существенная правка: 36 мест, где сейчас severity вшита. Зато после неё `disableRules` и режимы
получаются одним механизмом, а не тремя.

## Чего сознательно нет

**`calculateModuleSize`.** У образца это опция, потому что подсчёт размера ходит по всем файлам и
стоит денег на S3. У нас размер уже посчитан раньше — `planExtraction` знает `totalBytes`, а список
путей приходит в `PackageSource` готовым. Отдать его наружу надо (`05`), но опцией это делать
незачем: он бесплатен.

**Системные свойства и переменные окружения.** У образца часть переключателей читается из
`System.getProperty`. Для библиотеки это плохой канал: глобальное состояние, невидимое в сигнатуре,
и тесты, которые ставят свойство в `@BeforeEach` и снимают в `@AfterEach`. Всё — через аргумент.

**`ParserOptions.strict()` / `.lenient()` как фабрики.** В TS это объектный литерал.

## Чем проверяем

- умолчания дают ровно нынешний отчёт — на всех существующих тестах, без правок ожиданий;
- `lenient` не даёт ни одной ошибки на пакете, который в `default` отклоняется;
- `strict` повышает предупреждение до ошибки на заранее известном пакете;
- `disableRules: ['common.file-missing']` убирает находку и не трогает остальные;
- неизвестный код в `disableRules` — не молчание: опечатка в имени правила иначе выглядит как
  «правило не сработало».

## Оценка

покажет, какие режимы реально нужны, а какие я придумал.
