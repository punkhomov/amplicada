# `@amplicada/learning-parser` — паритет по пригодности к употреблению

План [`2026-08-09-learning-parser`](../2026-08-09-learning-parser/00-overview.md) закрыт: формат
разбирается в глубину, все пять семейств, шесть фаз, 204 теста. Этот план — про то, чего в нём не
было и не могло быть, потому что мерили не тем.

**Мерили глубиной разбора. Мерить надо было пригодностью к употреблению.**

## Как это вскрылось

Разговор 2026-08-10. На предложение взять тесты и фикстуры образца я дважды ответил, что половина
его набора — машинерия Java и к нам не относится. Формально верно, по существу — способ закрыть
неудобный вопрос. Когда вместо тестов стали сверять **функции**, картина оказалась такая:

| Функция | Образец | У нас |
|---|---|---|
| Способов подать пакет на вход | 7 (`Local`, `Zip`, `Classpath`, `InMemory`, `Cached`, `S3` v1/v2) | **0** |
| Валидация по официальным XSD | есть (SCORM 2004, 16 схем, 88 КБ в ресурсах, включается опцией) | **нет** |
| Опции разбора | `ParserOptions`: `strictMode`, `maxManifestSize`, `calculateModuleSize` | **нет ни одной** |
| Подсчёт размера курса | `ModuleSizeCalculator` | побочно в `intake`, наружу не отдаётся |
| Подключаемые детекторы формата | `ModuleTypeDetectorPlugin` | фиксированный `detect.ts` |
| Прогресс при стриминге | `StreamingProgressListener` | нет |
| Флаг двухформатности (`hasXapiSupport`) | есть | `detect` знает, наружу не отдаёт |
| JSON round-trip | Jackson + тесты | работает, ничем не закреплено |
| Классов правил валидации | 25 | **36 кодов** |
| Глубина разбора формата | — | паритет или глубже |

Итог: **по разбору формата мы впереди, по пригодности к употреблению — позади везде.** Разобрали
глубже всех, а подать пакет, настроить строгость, проверить по схеме и расширить под новый формат
нельзя.

## Диагноз

Границу библиотеки провели по вопросу «что понадобилось модулю», а не «что такое разборщик
пакетов». Отсюда две зеркальные ошибки:

- **Наружу вытекло то, чему место внутри.** `parsePackage` принимает `PackageSource = { paths,
  readBytes }`, а реализаций этого интерфейса библиотека не поставляет. Наша живёт в модуле —
  [`sourceOf`](../../../packages/module-hr-learning/src/backend/services/package-ingest.ts), десять
  строк. Библиотека для разбора учебных пакетов **не умеет открыть zip-файл**.
- **Внутрь затекло то, чему место снаружи.** `intake/` по собственному комментарию — «правила приёма
  **нашего** LMS», и экспортируется наружу (`DEFAULT_ARCHIVE_LIMITS`, `isAllowedPackageFile`).

Причина у первой понятна: платформа читает диапазоны из S3, поэтому абстракции источника всегда
хватало, а открытие архива лежало в модуле ещё до того, как библиотеку из него выделили. Дверь не
переехала вместе со всем остальным.

## Рамка

Продолжение рамки предыдущего плана, не замена: библиотека — для внешних потребителей, рантайма у
неё нет и не будет. Здесь добавляется второй критерий готовности:

> **Всё, что нужно потребителю, чтобы дойти от файла до `PackageMetadata`, должно лежать в
> библиотеке.** Если для этого требуется написать связку — библиотека не готова, сколько бы глубоко
> она ни разбирала манифест.

И ограничение, поставленное пользователем явно: **путь через S3 должен остаться эффективным.**
Ничего в контракте `PackageSource`/`RandomAccessSource` не меняется — новые двери это добавление
реализаций, а не переделка интерфейса. Подробности и обоснование — в `01`.

## Порядок

| # | Подплан | Почему здесь |
|---|---|---|
| `01` | [Входные двери](./01-input-sources.md) | Единственная дыра, из-за которой библиотекой нельзя пользоваться вообще. Плюс даёт обвязку для `02` бесплатно |
| `02` | [Корпус ADL и сверка покрытия](./02-conformance-corpus.md) | Меряем прежде, чем строить дальше: настоящие пакеты и сверка по списку тестов образца покажут, какие из оставшихся пунктов реальны |
| `03` | [Валидация по XSD](./03-xsd-validation.md) | Крупнейшее содержательное расхождение. Есть развилка без очевидного ответа — в Node нет вменяемого XSD-валидатора |
| `04` | [Опции разбора](./04-parser-options.md) | Строгость сейчас зашита намертво; потребитель не может выбрать между «отклонить» и «принять с оговорками» |
| `05` | [Поверхность библиотеки](./05-library-surface.md) | Хвост функций (размер, двухформатность, round-trip, плагины) плюс то, без чего пакет непубликуем |

`02` стоит вторым сознательно. После входных дверей мы впервые сможем прогнать разборщик по
настоящим пакетам, а не по XML, который я написал сам, — и до `03`–`05` будет полезно узнать, что
он на них покажет. Порядок `03`–`05` после этого можно пересмотреть.

## Чего в этом плане нет

- **Рантайма.** Как и раньше: `evaluatePrerequisites` библиотека отдаёт, но не зовёт, sequencing
  разбирает, но не исполняет. Паритет с образцом этого не требует — у него рантайма тоже нет.
- **Копирования кода образца.** Apache 2.0 это позволяет, но их ассерты написаны против модели,
  которой у нас намеренно нет (пререквизиты деревом, `moveOn` на пункте, коды свои). Берём
  **сценарии и входные данные**, ожидания пишем свои — разбор в `02`.
- **Java-машинерии.** Фабрики, DI, POJO-геттеры, слой сериализации Jackson. Здесь это правда: в TS
  модель — структурные типы без поведения, `JSON.stringify` над ней тотален. Единственное, что от
  этой группы переносится, — тест на round-trip (`05`), потому что свойство «модель это простые
  данные» сегодня ничем не закреплено.
- **Трёх механизмов кэширования доступа к файлам** (`fileExistsBatch`, `prefetchCommonFiles`,
  `CachedFileAccess`). Они лечат решение, которого мы не принимали: у них `fileExists` ходит в
  бэкенд на каждый путь, у нас список путей приходит заранее одним перечислением.

## Оценка

Сопоставимо с предыдущим планом по объёму, но иначе распределено: `01` небольшой и разблокирует
остальное, `02` — самый трудоёмкий и самый полезный, `03` может оказаться от 30 строк до
«не делаем» в зависимости от развилки.
