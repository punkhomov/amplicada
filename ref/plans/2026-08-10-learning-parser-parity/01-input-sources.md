# 01 — Входные двери

> Сделано 2026-08-10. Расхождение одно, и оно вылезло на прогоне: **дескриптор нельзя держать
> общим**. Поток, построенный поверх одного fd, закрывает его при `destroy()` — вопреки
> `autoClose: false` и одинаково что у `FileHandle`, что у числового дескриптора. yauzl читает
> диапазон и рвёт поток, поэтому второе чтение падало с `EBADF`. Итог: fd на диапазон, открытый
> `handle` остаётся только чтобы держать файл и давать `close()` смысл. Подробности —
> в `input-sources`.

Библиотека для разбора учебных пакетов не умеет открыть учебный пакет. Это первое, что надо
починить, и оно же разблокирует `02`.

## Что есть сейчас

Лестница от байтов до модели состоит из трёх ступеней, и средняя отсутствует:

| Ступень | Есть? |
|---|---|
| `RandomAccessSource` — чтение по смещению | интерфейс есть, реализация одна: `bufferSource(buffer)` |
| `ZipArchive` — центральный каталог, распаковка записи | есть |
| `PackageSource = { paths, readBytes }` — то, что ест `parsePackage` | **реализаций ноль** |

Чтобы разобрать zip, потребитель обязан склеить вторую ступень с третьей сам. Наша склейка —
[`sourceOf`](../../../packages/module-hr-learning/src/backend/services/package-ingest.ts) в модуле:

```ts
function sourceOf(archive: ZipArchive, plan: ArchivePlan): PackageSource {
  const byPath = new Map(plan.files.map(file => [file.path, file.entry]));
  return { paths: plan.files.map(f => f.path), async readBytes(path) { … } };
}
```

Читать архив с диска нельзя и подавно: `RandomAccessSource` поверх `fs` не существует, значит либо
грузить весь архив в память, либо писать реализацию самому.

## Что добавляем

Три функции, ни одна из которых не трогает существующие контракты.

### `fileSource(path): Promise<RandomAccessSource & { close(): Promise<void> }>`

Чтение по смещению из открытого дескриптора (`fs.promises.open` + `read(buffer, 0, len, position)`).
Закрывать обязан потребитель — отсюда `close()` в возвращаемом типе, а не отдельным аргументом:
дескриптор, который некому закрыть, это утечка, и прятать её за удобством не надо.

Это нижняя ступень; после неё `new ZipArchive(await fileSource('course.zip'))` работает без S3 и без
загрузки гигабайта в память.

### `zipSource(archive: ZipArchive, options?): PackageSource`

Переезд `sourceOf` внутрь, без зависимости от `intake`. Пути берутся из центрального каталога,
нормализуются через `normalizePackagePath`, каталоги и записи вне корня отбрасываются.

`options` нужен ровно для одного: у модуля список файлов уже отфильтрован политикой приёма
(`ArchivePlan`), и повторять фильтрацию незачем.

```ts
interface ZipSourceOptions {
  /** Ограничить набор путей. Модуль передаёт сюда результат `planExtraction`. */
  include?: readonly string[];
  /** Потолок на одно чтение — защита от «манифеста» на 4 ГБ. По умолчанию из ParserOptions (`04`). */
  maxBytes?: number;
}
```

Модуль после этого сокращается: `sourceOf` удаляется, вызов становится
`zipSource(archive, { include: plan.files.map(f => f.path) })`.

### `directorySource(root: string): Promise<PackageSource>`

Распакованный пакет на диске: рекурсивный обход, пути относительно корня, разделители в `/`,
нормализация та же.

Нужна не только внешнему потребителю — это **та самая обвязка под корпус ADL** из `02`. Отдельного
тестового костыля не будет: фикстуры читаются публичной функцией библиотеки, то есть заодно её и
проверяют.

## Почему S3 от этого не страдает

Условие поставлено явно, поэтому фиксирую разбор.

`PackageSource` и `RandomAccessSource` **не меняются**. Всё перечисленное — новые реализации
существующих интерфейсов. Путь через S3 остаётся ровно таким, как сейчас: модуль реализует
`RandomAccessSource` поверх `getObjectStream` с `Range`, `ZipArchive` читает центральный каталог
двумя-тремя запросами и дальше по записи на файл.

Более того, наша форма для S3 лучше, чем у образца, и это стоит зафиксировать, чтобы не «доехать до
паритета» в обратную сторону. У них `FileAccess.fileExists(path)` ходит в бэкенд **на каждый путь**,
и поверх этого навешаны три механизма компенсации: `fileExistsBatch`, `prefetchCommonFiles` и
`CachedFileAccess`. Мы принимаем `paths` списком заранее — одно перечисление, дальше все проверки
существования файла бесплатны и в памяти. **Эти три механизма не переносим.**

Единственное следствие нашей формы: список путей материализуется до начала разбора. Для S3 это уже
так (`planExtraction` строит его из центрального каталога), для `directorySource` — обход при
создании. Пакет с сотней тысяч файлов сделает это дорого, но такой пакет отсекается лимитами приёма
раньше, чем дойдёт до разбора.

## `intake/` — зеркальная половина

`intake/` описан в `index.ts` как «правила приёма **нашего** LMS». Это политика платформы внутри
библиотеки без платформы.

Не выносим — лимиты уже параметризованы (`ArchiveLimits`), а таблица content-type по расширению
общеполезна. Но приводим в порядок:

- `DEFAULT_ARCHIVE_LIMITS` → назвать примером, а не умолчанием, и в комментарии написать, откуда
  взяты числа (наши загрузки), чтобы никто не принял их за требование спецификации;
- убрать «наш LMS» из формулировок — у библиотеки нет своего LMS;
- в `README` (`05`) сказать прямо: это заготовка политики, а не часть формата.

## Чем проверяем

- zip, собранный `makeZip`, читается через `zipSource` и даёт тот же результат, что нынешняя
  ручная связка в тестах;
- `include` сужает набор путей, и файл вне набора не виден `readBytes`;
- `fileSource` читает с произвольного смещения и закрывается; двойной `close()` не бросает;
- `directorySource` на распакованном пакете даёт те же пути, что `zipSource` на нём же
  запакованном, — это же и проверка нормализации разделителей;
- запись с `../` в имени не попадает в `paths` (регрессия на уже найденный дефект).

## Оценка

~150 строк кода, ~120 тестов. Самый маленький подплан из пяти и единственный обязательный: без него
остальные четыре улучшают библиотеку, которой всё ещё нельзя воспользоваться.

## Чего не делаем

- **`CachedFileAccess` и товарищи** — см. выше.
- **`ClasspathFileAccess`** — понятия classpath в Node нет; ближайший аналог, чтение из
  зависимости, покрывается `directorySource`.
- **`StreamingProgressListener`** — прогресс относится к распаковке, а она у нас в модуле
  (`putObjectStream` по файлу). В библиотеке прогрессу нечего показывать: разбор описателя
  занимает миллисекунды.
