# Технический долг — аудит 2026-08-08

Сводка того, что нашлось при сплошном чтении заметок (46 записей) со сверкой каждого
утверждения по коду. Сюда попало только то, **у чего нет своего плана**. Что уже описано в других
планах — перечислено в разделе «Живёт в других планах» без пересказа.

Каждый пункт проверен в коде на 2026-08-08. Где проверить не удалось, это сказано явно.

## Текущая проблема

1. **Код с 2026-07-16 не проверялся против реальной БД.** Двенадцать сессий подряд заканчивались
   формулой «typecheck и build чисты, вживую не прогонялось» — включая полную перестройку документной
   модели, переименование таблиц и типов документов, пять миграций с FK на `document_index`.
2. **Часть заявленных возможностей не реализована**, но объявлена в контрактах: `widget: 'reference'`,
   `FieldMetadata.required`. Пользователь видит их как сломанные, а не как отсутствующие.
3. **Нет автоматических барьеров**: ни CI, ни `drizzle-kit` (расхождения схемы и миграции не ловятся),
   ни тестов выше unit.
4. **Часть документации описывала несуществующий код** — вычищено в этой же сессии, см. «Сделано
   попутно».

## Решение

Разложить найденное на четыре фазы по критерию «что мешает прямо сейчас». Фаза 0 — гейт: пока код не
прогнан на живой БД, любая оценка «работает / не работает» в фазах 1–3 держится на чтении, а не на
факте. Остальные фазы независимы друг от друга.

## 1 — `widget: 'reference'` — виджет выбора документа

🔴 Бьёт по пользователю каждый день.

### Проблема

`FieldMetadata.widget` перечисляет `'reference'`
([documents.ts:132](../../packages/platform-core/src/contracts/documents.ts#L132)), но `FieldWidget` в
`module-admin` не имеет для него ветки
([field-widget.tsx:40-174](../../packages/module-admin/src/frontend/widgets/field-widget/ui/field-widget.tsx#L40-L174))
— поле проваливается в `default` и рендерится обычным текстовым инпутом.

Практически: `parentNodeId`, `headUserId`, `legalEntityNodeId`, `costCenterNodeId`, `templateId`,
`gradeId`, `familyId` на карточках HR задаются **вписыванием UUID руками**. UUID приходится добывать
из URL карточки другого документа.

Побочный эффект шире, чем неудобство: закрыт целый класс решений «сделать связь документом и назначать
через generic-карточку». В [04-course-model](./2026-08-08-module-learning/04-course-model.md)
назначение курса из-за этого пришлось делать своим диалогом вместо generic-поля.

### Что решить до реализации

Виджету нужно знать, **на какой тип документа** ссылается поле — сегодня в `FieldMetadata` этого нет.
Развилка:

- **`referenceType: string` в `FieldMetadata`** — просто, но тип задаётся строкой без проверки;
- **вывести из FK Drizzle-схемы** — не требует новых полей, но `ext.schema` есть не у всех расширений
  (у пяти hr-типов `load`/`save` кастомные), и связь «колонка → тип документа» не выражена: FK ведёт
  на таблицу, а типов документов на одной таблице может быть несколько.

Рекомендация — первое: явное поле, потому что второе не покрывает ровно те пять типов, ради которых
всё затевается.

Дальше — как искать. Нужен эндпоинт «список документов типа X с поиском по подстроке», и он почти
есть: `DocumentRuntime.list` уже умеет фильтры и пагинацию. Открытый вопрос — что показывать в строке
выбора (`code`? `name`? первое текстовое поле?) и откуда брать это правило.

**Обновление 2026-09-16:** у `list` появился полнотекстовый `search` для страницы админки.
Он ищет слова с морфологией PostgreSQL, а не подстроку, поэтому для reference-combobox
ещё нужно проверить сценарий частичного ввода и выбрать правило подписи результата.

### Что делать

- [ ] Решить, как поле объявляет свой тип документа (см. развилку)
- [ ] Добавить в `FieldMetadata` то, что решили
- [ ] Эндпоинт поиска документов по типу (или переиспользовать `list` с параметром поиска)
- [ ] Ветка `case 'reference'` в `FieldWidget`: combobox с поиском, отображение выбранного, очистка
- [ ] Проставить тип у полей-ссылок в `module-hr` (7 полей) и `module-hr-request`
- [ ] Перепроверить, не упрощает ли это `04-course-model` — собственный диалог назначения может стать
      не нужен

### Связанное

`FieldMetadata.required` — та же болезнь: объявлен, расставлен по документам, **не читается никем**
(ни валидации на бэкенде, ни маркера на фронтенде). Живёт в
[08-model-gaps](./2026-08-05-document-model/08-model-gaps.md), здесь только отмечено, чтобы виднелась
закономерность: контракт обрастает полями быстрее, чем рантайм их читает.

## 2 — `exportData` не отдаёт `id`

🟡 Тихая порча данных при переносе между окружениями.

### Проблема

Импорт и экспорт разъехались:

- `importData` **умеет** сохранять id — берёт его из item'а через `findItemId`, резервирует
  `indexCreated`, отвечает 409 на чужой тип и на удалённый документ
  ([document-runtime.ts:853-885](../../packages/platform-core/src/backend/services/document-runtime.ts#L853-L885));
- `exportData` этот id **не отдаёт** — `loadExtension` вырезает `idColumn` из результата
  ([document-runtime.ts:347](../../packages/platform-core/src/backend/services/document-runtime.ts#L347)).

Значит round-trip «выгрузить → загрузить» по-прежнему создаёт новые строки. Для `module-hr` это
особенно плохо: FK-поля (`departmentNodeId`, `parentNodeId`, `legalEntityNodeId`, `costCenterNodeId`,
`templateId`) после реимпорта укажут на неверные id — молча, без единой ошибки.

### Что делать

- [ ] Решить: добавляем `id` в выгрузку — или объявляем, что экспорт это дамп для переноса, а не бэкап
- [ ] Если добавляем: `id` в `items` у `exportData`, колонка `id` в CSV-выгрузке, проверка на импорте
- [ ] Отдельно: `exportData`/`importData` держат свой гейт `if (ext.load || ext.schema)`, из-за чего
      **кастомные поля** (`customFields: true`) в экспорт не попадают, хотя в импорт попадают
      бесплатно через общий `saveExtensionData`. Асимметрия осознанная, но её стоит закрыть заодно

## 3 — `drizzle-kit` и дрейф схемы

🟡 Ошибки этого класса не ловятся ничем.

### Проблема

`drizzle-kit` в проект **не подключён** — его нет ни в одном `package.json`. SQL-файлы миграций и
записи в `migrations/meta/_journal.json` пишутся руками; применяет их рантайм-мигратор drizzle
(`migrate()` из `drizzle-orm/node-postgres/migrator`) при бутстрапе.

Следствие: расхождение между Drizzle-схемой и миграцией не обнаруживается ничем, кроме чтения. Такие
расхождения уже есть:

| Констрейнт | Есть в | Нет в |
|---|---|---|
| `UNIQUE(family_id, code)` | `module-hr/migrations/0001_hr_data_model.sql:28` | `hr-position-grade.ts` |
| `UNIQUE(department_node_id, code)` | `module-hr/migrations/0001_hr_data_model.sql:163` | `hr-staff-unit-node.ts` |
| FK на `department_node`/`staff_unit_node` у junction-таблиц тегов | — | обе стороны: нет нигде, допускает orphan-ссылки |

Пока живём на одноразовой БД, цена низкая. Она вырастет ровно в тот момент, когда появится продакшен —
то есть когда чинить будет дороже всего.

### Что делать

- [ ] Подключить `drizzle-kit` и `drizzle.config.ts` (по пакету — у каждого своя папка миграций и свой
      `_journal.json`)
- [ ] Прогнать `generate` на текущих схемах и **сравнить с тем, что в миграциях** — это и есть
      инвентаризация дрейфа, других способов её получить нет
- [ ] Довести схемы до миграций (или наоборот, где миграция неправа)
- [ ] Решить, генерируем ли миграции дальше автоматически или продолжаем руками, а `drizzle-kit`
      используем только как детектор расхождений. Второе дешевле: миграции в проекте часто содержат
      бэкфиллы и `EXCLUDE USING gist`, которых генератор не напишет

**Зависит от пункта 0**: менять что-либо в миграциях, пока текущие не прогнаны на живой БД, значит
отлаживать две вещи разом.
