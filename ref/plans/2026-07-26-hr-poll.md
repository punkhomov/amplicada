# module-hr-poll — движок опросов

## Текущая проблема

1. В платформе нет механизма для сбора структурированной обратной связи от пользователей (опросы, пульс-checks, NPS).
2. Ближайший по духу модуль — `module-hr-request`: тип сущности конфигурируется админом через Document System (декларативный список полей в jsonb), рендерится generic-компонентом на портале. Опрос — по сути то же самое (декларативный список вопросов вместо полей формы), но без workflow вокруг (заявка проходит согласование по нодам, опрос — разовый ввод данных).
3. Для «действия над документом, а не над полем» (например «Опубликовать») в `module-admin` уже есть общий механизм — toolbar action на карточке документа (`registerToolbarAction`, см. `module-auth-password` → «Сменить пароль» на карточке `user`). Им и стоит воспользоваться вместо кастомной admin-страницы.

## Решение

Новый модуль `module-hr-poll`: админ создаёт опросы через Document System (как `hr-request-type`), пользователь отвечает на портале через **отдельные страницы** — `/polls` (список) и `/polls/:id` (прохождение), по образцу `module-hr-request` (`/requests`, `/requests/:id`). Никакой глобальной модалки/плеера — опрос ничем не отличается от заявки с точки зрения навигации.

Без workflow: опрос — не многошаговый процесс, а разовая форма. Ответ пишется одной транзакцией, ре-открытие/маршрутизация не нужны.

### Версионность — явное действие «Опубликовать», без полной цепочки версий

В `module-workflow` версионирование полноценное: отдельная таблица `workflow_versions`, `currentVersionId` на `workflows`, `loadFrozenConfig(versionId)` — потому что инстанс процесса живёт неделями, проходит по нодам, и разные инстансы могут физически работать по разным версиям графа одновременно.

У опроса такой одновременности версий нет — в моменте существует только одна схема вопросов. Поэтому вместо цепочки версий — **одноразовый переход состояния**, без множественных версий и без `versionId` на ответе:

- `hr_poll_polls.status`: `'draft' | 'published'`. Создаётся в `draft` — админ свободно редактирует вопросы.
- Явное действие **«Опубликовать»** (`POST /api/hr-polls/:id/publish`) переводит `draft → published`. Переход необратим (обратно в `draft` — нет; нужна правка вопросов — дублируй в новый `hr_poll_polls` с новым `code`).
- Пока `status = 'draft'` — опрос не виден на портале (в список `/polls` не попадает), сколько бы ответов ни было (их не может быть, отвечать можно только на опубликованный).
- После `status = 'published'` — backend отклоняет (`400`) любое изменение `questions` независимо от того, есть ли уже ответы (0 или 1000 — не важно, схема заморожена с момента публикации, а не с момента первого ответа). Остальные поля (`title`, `description`, `startsAt`/`endsAt`, `active`, `allowRepeat`, `anonymous`) остаются редактируемыми и после публикации — они не влияют на интерпретацию уже собранных `answers`.

Это даёт ту же гарантию, что и `frozen config` в workflow (ответ всегда интерпретируется по одной и только одной неизменной схеме вопросов), но без таблицы версий и без денормализованного `versionId` на каждой строке ответа — потому что версия ровно одна за всю жизнь опубликованного опроса.

## Архитектура

### Данные

```
hr_poll_polls
  id            uuid pk
  code          varchar unique      -- человекочитаемый код
  title         varchar
  description   varchar nullable
  questions     jsonb  PollQuestion[]   -- иммутабельно после публикации
  status        varchar 'draft' | 'published'   -- default 'draft', переход только draft -> published
  active        boolean default true    -- показывать ли сейчас (пауза сбора без разблокировки схемы)
  startsAt      timestamp nullable  -- окно показа, null = без ограничения
  endsAt        timestamp nullable
  allowRepeat   boolean default false   -- допускать повторные ответы того же пользователя
  anonymous     boolean default false   -- не писать userId в response
  createdAt     timestamp
  deletedAt     timestamp nullable  -- soft-delete (Document System)

hr_poll_responses
  id                uuid pk
  pollId            uuid fk -> hr_poll_polls.id
  userId            uuid nullable fk -> identity_user.id   -- null если anonymous
  answers           jsonb  Record<questionKey, unknown>
  createdAt         timestamp
```

Проверка «уже отвечал» — на уровне приложения (SELECT перед INSERT в транзакции), без БД-constraint: `allowRepeat` переключается per-опрос, партиционировать уникальный индекс под это не стоит усложнения ради v1.

### Контракты (`contracts/index.ts`)

```ts
export type PollQuestionType = 'single-choice' | 'multi-choice' | 'text' | 'textarea' | 'rating' | 'nps';

export interface PollQuestion {
  key: string;
  label: string;
  type: PollQuestionType;
  required?: boolean;
  helpText?: string;
  options?: { label: string; value: string }[]; // single-choice / multi-choice
}

/** Статус опроса относительно текущего пользователя — вычисляемый, как RequestStatus в hr-request. */
export type PollUserStatus = 'available' | 'answered' | 'closed';

export interface PollListItem {
  id: string;
  code: string;
  title: string;
  description: string | null;
  status: PollUserStatus;
}

export interface PollDetail {
  id: string;
  title: string;
  description: string | null;
  questions: PollQuestion[];
  /** Не null, если уже отвечал и allowRepeat=false — форма рендерится readonly поверх этих ответов. */
  myAnswers: Record<string, unknown> | null;
  canSubmit: boolean;
}

/** id-константы Document System для документа «Опрос». */
export const HrPollDocuments = { POLL: 'hr-poll' } as const;
export const HrPollGroups = { QUESTIONS: 'hr-poll-questions' } as const;
```

### Backend

- `documents/poll.ts` — `registerPollDocuments(docs)`, копия паттерна `hr-request-type`:
  - группа мета-полей (`code`, `title`, `description`, `status` readonly-вывод, `active`, `startsAt`, `endsAt`, `allowRepeat`, `anonymous`)
  - группа вопросов с кастомным компонентом `poll-questions-editor`; `save` проверяет `status === 'published'` → `400` (нельзя менять `questions`), независимо от наличия ответов.
- `routes.ts`, префикс `/api/hr-polls`, все роуты за `preHandler` auth-check (как в hr-requests):
  - `GET /` — список опросов, релевантных текущему пользователю (`published`, `active`, в окне `startsAt/endsAt`, либо уже отвеченные — чтобы не пропадали из истории) → `PollListItem[]` с вычисленным `status`
  - `GET /:id` — `PollDetail`: вопросы + `myAnswers` (если уже отвечал) + `canSubmit`
  - `POST /:id/responses` — body `{ answers }`; проверяет `status='published'`, окно, `allowRepeat`, required-вопросы; insert
  - `POST /:id/publish` (admin-only) — `draft → published`; `409`, если уже `published`
  - Агрегация результатов для админа (сводные графики по ответам) — **вне scope v1**, отдельная задача.
- `setup.ts` — `context.migrations.register`, `registerPollDocuments`, роуты за auth-hook (`/:id/publish` дополнительно за admin-check, как остальные admin-роуты). Без `services.resolve` на другие модули — `module-hr-poll` не имеет обязательных зависимостей (`moduleManifest.dependencies: []`).

### Frontend

Полностью по образцу `module-hr-request`, без модалок:

- `widgets/generic-poll-form/` — рендерер по `PollQuestion[]`, аналог `GenericRequestForm`, плюс контролы для `rating` (звёзды 1–5) и `nps` (шкала 0–10). Умеет readonly-режим (уже отвеченный опрос без `allowRepeat`).
- `widgets/poll-questions-editor/` — админ-редактор вопросов, аналог `RequestTypeFieldsEditor`; `registerComponent('poll-questions-editor', PollQuestionsEditor)`. Дизейблится (readonly), если `status === 'published'` (проп из карточки документа) — так же нельзя добавить/убрать/переименовать вопрос, ошибка сохранения не нужна, чтобы её словить, если UI и так блокирует.
- `features/publish-poll/` — `PublishPollAction`: `registerToolbarAction({ id: 'poll-publish', label: 'Опубликовать', documentType: HrPollDocuments.POLL, component: PublishPollAction })`. Кнопка на тулбаре карточки документа (рядом с «Сохранить», как «Сменить пароль» у `module-auth-password`). Активна только при `status === 'draft'` и отсутствии несохранённых правок; жмёт `POST /api/hr-polls/:id/publish`, инвалидирует query карточки документа. Подтверждение через `AlertDialog` (необратимое действие).
- `pages/polls-list/` — `/polls`: список `PollListItem[]` (доступные + пройденные), клик → `/polls/:id`. Аналог `requests-list-page`.
- `pages/poll-take/` — `/polls/:id`: `GenericPollForm` в readonly, если `myAnswers` есть и `!allowRepeat`, иначе editable + кнопка «Отправить» → `POST /:id/responses`. Аналог `request-card-page`, но без `submit`-в-два-приёма (заявка сначала черновик, потом submit) — у опроса один шаг: заполнил → отправил.
- `setup.tsx` — `registerComponent('poll-questions-editor', ...)`, `registerToolbarAction(...)`, `context.routes.register('/polls', ...)`, `context.routes.register('/polls/:id', ...)`, `context.navigation.register({ id: 'hr-polls', label: 'Опросы', path: '/polls' })`.

## Зависимости

Новых npm-пакетов не требуется. `peerDependencies`/`devDependencies` по образцу `module-hr-request`, но без `@amplicada/module-workflow`:

| Пакет | Зачем |
|---|---|
| `@amplicada/platform-core` | Document System, extension points, UI-кит |
| `@amplicada/module-admin` | `registerComponent` для кастомных редакторов на карточке документа |

`moduleManifest.dependencies: []` — модуль ничего не резолвит из service locator при старте, порядок бутстрапа не важен (в отличие от `hr-requests`, которому нужен `workflow` раньше).

## Проверка

1. `pnpm --filter @amplicada/module-hr-poll typecheck && pnpm build`.
2. В админке: создать опрос (2–3 вопроса разных типов, `status=draft`) — убедиться, что на портале в `/polls` он не появляется.
3. Нажать «Опубликовать» — `status` становится `published`; попытка отредактировать вопросы после этого — заблокирована и в UI, и на backend (`400` при прямом запросе).
4. На портале под обычным пользователем: `/polls` показывает опрос, `/polls/:id` — форма, отправка работает.
5. Повторный заход на `/polls/:id` без `allowRepeat` — форма в readonly с уже отправленными ответами; с `allowRepeat=true` — можно отправить снова.
6. Окно `startsAt`/`endsAt` вне текущего момента — опрос не должен быть доступен для ответа (`canSubmit=false` / `400` на backend).
