# 02 — валидация как отчёт

Разбор падает на первом же изъяне: `throw new PackageParseError(...)` и наружу одна строка. Дальше
первой проблемы никто не смотрит.

## Зачем

Две причины, и вторая важнее.

**Админу.** Пакет чинится по одной ошибке за загрузку: залил — «нет точки входа», починил — «файл
отсутствует», починил — «ссылка в никуда». Каждый круг это перезаливка гигабайтного архива и минуты
распаковки.

**Библиотеке.** Решение «принимать или нет» принимает потребитель — это записано рамкой в
[`00-overview`](./00-overview.md). Но `throw` за него уже всё решил: разбор оборвался, метаданных
нет, выбирать не из чего. Пока библиотека бросает, никакой потребитель не сможет сказать «осиротевший
ресурс меня не смущает, а отсутствующий файл смущает».

Ещё эта фаза вторая, а не пятая, потому что меняет **форму результата**. Чем больше кода накопится
поверх старой формы, тем дороже переделка.

## Граница между «бросить» и «сообщить»

Единственная, и провести её надо ровно один раз:

- **Бросаем `PackageParseError`**, когда не можем сказать, *что это за пакет*: описателя нет, он не
  разбирается как XML, корневой элемент не тот. Отчёт тут не о чем составлять — объекта нет.
- **Сообщаем issue**, когда пакет описан, но описан плохо. Метаданные при этом строятся: у
  `PackageMetadata` и так `entryPoint`/`entryUrl` нулевые по типу, а `activities` бывает пустым.

Практическое следствие: **«нет ни одного запускаемого ресурса» перестаёт быть исключением** и
становится issue уровня `error`. Сейчас это `throw`, и он-то и не даёт потребителю решать.

## Форма

Новый слой `validation/` — правила поверх модели.

> **Поправка по факту реализации.** Планировалось «`validation/` зависит от `formats/`». Вышло
> наоборот: правила смотрят на `PackageMetadata`, а не на разобранный XML, поэтому `validation/`
> лежит **под** форматами, и `formats/detect.ts` их вызывает. А `issue.ts` вообще уехал в корень
> пакета к `errors.ts`: тип находки понадобился и в `xml/`, и в `model/`, и в `formats/` — это лист,
> а не часть какого-то слоя.

```ts
export type Severity = 'error' | 'warning';

export interface ValidationIssue {
  severity: Severity;
  /** Стабильный машинный код: по нему потребитель решает, а не по тексту. */
  code: string;
  /** Текст для человека, по-русски — его увидит админ на карточке курса. */
  message: string;
  /** Где именно: `imsmanifest.xml#item:lesson_1`, `course.au#A1`. */
  location: string;
  /** Что сделать. Необязательно: осмысленный совет есть не всегда. */
  fix?: string;
}

export interface ValidationReport {
  issues: ValidationIssue[];
  errors: ValidationIssue[];
  warnings: ValidationIssue[];
  ok: boolean;
}
```

`parsePackage` возвращает `ParsedPackage { metadata, report }` вместо голых метаданных.

Коды — пространством имён через точку: `scorm.resource-ref-dangling`, `common.duplicate-identifier`,
`cmi5.launch-url-missing`. У образца это `SCORM12_MISSING_RESOURCE_REF`; смысл тот же, но точка
разделяет формат и суть, а не подчёркивание, которое уже внутри обеих частей.

**Severity значит ровно одно:** `error` — проиграть нельзя, `warning` — можно, но автор пакета
что-то напутал. Никаких «info»: третий уровень, который никто не читает, только размывает первые два.

## Правила

За основу взят перечень образца (32 файла в `validators/rules/`), но не механически: часть его правил
проверяет то, что у нас невыразимо до фазы `04`, часть — то, что у нас уже проверено типами.

### Общие — по `PackageMetadata` и списку файлов пакета

| Код | Severity | Что ловит |
|---|---|---|
| `common.no-launchable` | error | Ни одной запускаемой активности. Раньше — `throw` |
| `common.entry-missing` | error | Точка входа есть в описании, но не в архиве. **Переезжает из `package-ingest`** |
| `common.file-missing` | error | Файл, объявленный в описателе, отсутствует в архиве (`FileExistenceValidator` образца) |
| `common.duplicate-identifier` | warning | Два пункта с одним `identifier`. Ломает привязку попытки к пункту |
| `common.title-missing` | warning | У пакета нет названия — в каталоге он будет безымянным |
| `common.external-launch` | warning | Запуск с чужого сервера. Для нас это отказ, но решает потребитель |

`PathSecurityRule` образца отдельным правилом не нужен: `resolveRelativePath` уже не выпускает за
корень пакета, а `planExtraction` режет zip-slip на входе. Дублировать проверку ради строчки в
отчёте — заводить второе место, которое разойдётся с первым.

### SCORM — по манифесту

| Код | Severity | Что ловит |
|---|---|---|
| `scorm.resource-ref-dangling` | warning | `identifierref` ведёт на несуществующий ресурс |
| `scorm.resource-href-missing` | warning | Ресурс `scormtype="sco"` без `href` |
| `scorm.orphaned-resource` | warning | Ресурс, на который не ссылается ни один пункт |
| `scorm.organizations-missing` | warning | Нет `<organizations>` — оглавления не будет |
| `scorm.default-organization-invalid` | warning | `organizations/@default` указывает в никуда |
| `scorm.manifest-identifier-missing` | warning | У манифеста нет `identifier` |

### cmi5 / xAPI / AICC

| Код | Severity | Что ловит |
|---|---|---|
| `cmi5.course-missing` | warning | Нет `<course>` |
| `cmi5.launch-url-missing` | error | Ни у одной `<au>` нет `<url>` |
| `xapi.activities-missing` | error | Нет `<activities>` |
| `xapi.launch-url-missing` | error | Ни у одной активности нет `<launch>` |
| `aicc.au-missing` | error | Нет `.au` |
| `aicc.launch-url-missing` | error | Ни у одной единицы нет `file_name` |

Правила `*_MISSING_TITLE` образца сведены в общее `common.title-missing`: отсутствие названия — не
особенность формата.

## Где правила живут

Пополам, и деление не произвольное:

- **Правила по манифесту живут в формате.** `scorm.orphaned-resource` нужно знать, какие ресурсы
  объявлены, — а это XML, которого в `PackageMetadata` нет и не будет до фазы `04`. Парсер копит
  issue по ходу разбора, тем же приёмом, что `failures` в фазе `01`.
- **Правила по метаданным и файлам живут в `validation/rules/`.** Они одинаковы для всех форматов и
  выполняются в `parsePackage` после разбора, когда есть и метаданные, и `source.paths`.

Соблазн вынести все правила в отдельный слой есть, но он потребовал бы отдать наружу разобранный
XML — то есть построить `details` из фазы `04` раньше времени и без потребителя.

## Список файлов пакета

`common.file-missing` и `common.entry-missing` требуют знать, что в архиве. `PackageSource` уже
отдаёт `paths` — этого достаточно, ничего нового в интерфейс не добавляется.

Сравнение путей — по нормализованному виду, как в инвентаре. Иначе `Content/Index.html` из манифеста
не совпадёт с `content/index.html` из архива на регистро-зависимом сравнении, и правило начнёт
ругаться на исправные пакеты. **Регистр: сверять без учёта**, потому что архив и манифест пишут
разные инструменты, а раздаём мы по инвентарю.

## Что ломается у потребителя

- **`parsePackage` меняет тип возврата** — `ParsedPackage` вместо `PackageMetadata`.
- **`package-ingest` теряет две свои проверки** (точка входа в архиве, внешний запуск): они
  становятся правилами. Модуль вместо них смотрит на `report.errors`.
- **`packages.error` меняет форму**: сейчас одна строка, станет список с кодами. Это **миграция** —
  `error` → JSONB либо отдельная таблица issue'ов. Правка на стороне модуля; выбор между колонкой и
  таблицей делать там же, по тому, нужна ли выборка «все пакеты с таким кодом».

Данные не жалеем — база одноразовая, но схемную миграцию пишем.

## Чем проверяем

- каждое правило — свой тест: срабатывает там, где должно, и **не срабатывает на исправном пакете**
  (второе важнее: правило, ругающееся на всё, выключат целиком);
- пакет с тремя разными изъянами даёт три issue, а не одну — это и есть смысл фазы;
- `error` и `warning` не путаются местами: пакет только с warning'ами остаётся `ok`;
- `common.file-missing` не ругается на разный регистр и на `./` в путях;
- фатальное остаётся фатальным: не-XML, чужой корень, отсутствие описателя по-прежнему бросают;
- существующие тесты форматов, ожидающие `throw` на «нечего запускать», переписываются на проверку
  issue — и это ровно тот список, который показывает, что поменялось в поведении.

## Оценка

Порядка 400 строк: модель отчёта, десяток правил, сборка в `parsePackage`. Плюс переделка тестов
форматов, ожидающих исключений, плюс правка `package-ingest`.

## Чего не делаем

- **`ArchiveRejected` в issue не превращаем.** Лимиты архива, whitelist расширений и zip-slip — это
  `intake/`, наша политика приёма, а не валидность формата. Смешать их значило бы отдать наружу
  отчёт, половина которого про чужие правила.
- **Правила sequencing SCORM 2004** — фаза `04`, там же появится, что проверять.
- **XSD-валидацию** — решено в `00-overview`: тянуть схемы ради `cvc-complex-type.2.4.a` вместо
  внятного текста.
