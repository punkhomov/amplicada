# Метрики: свой закрытый стек

Зонтичная папка по модулю метрик (`module-metrics`). Исследование возможности и направления:
что измерять, как хранить внутри платформы, как отдавать наружу и как расширять новыми выходами
без переделки ядра. Это черновик для обсуждения, не решение; формат данных и код не менялись.

**Решения владельца (2026-09-18):**

1. Слои метрик: **продуктовые клиентские + бизнес-события модулей + технические** (роуты, SQL,
   ошибки). Технические — не «потом», а полноправный слой.
2. Контракты закладываем **шире текущей реализации**, чтобы новый выход/потребитель добавлялся
   адаптером, а не переделкой.
3. Реализация — **свой закрытый оффлайн-стек**: по умолчанию ноль внешних вызовов. Абстракция
   хранилища сразу (Postgres — первая реализация, ClickHouse — потом за тем же контрактом).
4. Онлайн-провайдеры (Яндекс.Метрика) — **адаптер за контрактом выхода**, выключены по умолчанию.
5. SQL-метрики: инструментация приложения + **опционально** `pg_stat_statements` (без обязательных
   требований к DBA).
6. Алерты: **правила + контракт доставки**, UI/доставка — когда появится notification-модуль.
7. Реалтайм не нужен: дашборды обновляются периодически.
8. Масштаб: **> 5000 пользователей** — роллапы, сэмплирование, партиционирование, путь к
   отдельному аналитическому хранилищу.
9. Приватность: **псевдонимизация** (хеш с секретом, без логина/IP/UA), 152-ФЗ-совместимость.

## Что уже есть и чего нет

Проверено по коду и `ref/`:

- **Нет** ни одного модуля/плана/ADR про аналитику и метрики; нет внешних счётчиков (Метрика, GA4,
  PostHog, Matomo, Sentry) ни в коде, ни в зависимостях.
- **Нет** отдельного хранилища: только Postgres 16, Redis 7, SeaweedFS (`docker-compose.infra.yaml`).
- **Нет** generic-журнала событий/аудита: есть доменные аудиты (`workflow.audit_log`, `core.auth_log`,
  версии HR), логи запусков задач (`scheduled_task_run_logs`) и лишь точечные агрегаты вроде
  непрочитанных в support-chat.
- **Нет** исходящего HTTP-клиента в модулях, ретраев, очередей; **нет** config-сервиса (модули не
  читают env — читают только core и точки входа приложений); **нет** helmet/CSP.
- Шина событий — **in-process** (`event-bus.ts`), Redis используется как pub/sub только для SSE;
  фронтовая шина не имеет ни одного эмиттера.
- **Есть готовые кирпичи:** `ui/chart` + `recharts@3.10.1` (вендорены и никем не используются, Vite
  уже режет `vendor-charts`), apps mode в `module-admin` + слот шапки, паттерн настроек-синглтона
  (`support_chat.settings`), task-scheduler (регистрация задач из кода, cron — данными), документный
  каркас, S3-хранилище, ALS в `platform-logger`.

Мотивация из соседних планов: support-chat AI-first уже ждёт метрики (этап 3: deflection, время до
первого ответа, reopen rate, доля инцидентов), notifications — алерты по `failed`-событиям outbox,
hr-learning — отчётность по курсам, workflow — внешние отчёты по `node.code`.

## Рамка решения

### Три слоя, один конвейер

```
           Источники (collectors)                 Платформа (offline)                  Выходы (sinks)
  ┌────────────────────────────────┐   ┌───────────────────────────────────┐   ┌────────────────────────┐
  │ client tracker (SPA, RUM, err) │   │ ingest API → pсевдонимизация →    │   │ admin app (дашборды)   │
  │ http observer (роуты)          │──▶│ sampling → кардинальные лимиты →   │──▶│ alerts evaluator       │
  │ sql wrapper (pg-пул)           │   │ стор (Postgres: events+rollups)   │   │ sinks: yandex/webhook/…│
  │ tasks / event bus (воркеры)    │   │ query layer (AST-подмножество)    │   │ exports (CSV/Parquet)  │
  │ business emit (модули)         │   └───────────────────────────────────┘   └────────────────────────┘
  │ pg_stat_statements (опция)     │                     ▲                                   ▲
  └────────────────────────────────┘            contracts (01)                      contracts (01)
```

Ключевой принцип: **стор — источник правды, выходы — подписчики**. Внешние провайдеры не влияют на
сбор и не являются обязательным звеном; в закрытом контуре их просто нет.

### Два класса данных (почему не один)

| | События (`MetricEvent`) | Измерения (`Measurement`) |
|---|---|---|
| Что | семантика: «пользователь сделал X», «ошибка Y», «инцидент Z» | числа: длительность роута, SQL, Web Vitals, счётчики |
| Единица | штука (событие) | значение + инструмент (counter/gauge/histogram) |
| Отвечает на | воронки, retention, пути, каталог событий | p50/p95/p99, rate, распределения, алерты |
| Пример | `page.view`, `support.thread.opened` | `http.server.request.duration`, `db.query.duration` |
| Хранение | `metrics.events` (партиции) | `metrics.series` + `metrics.points` (партиции) |

Так делает индустрия: product analytics (PostHog/Plausible/Umami) и метрики (OTel/Prometheus) — разные
модели с разной ценой записи и разными запросами. Смешивать в одну таблицу — потерять и то и другое
(см. отвергнутое в `01-contracts.md`).

### Offline-first, online — опционально

- По умолчанию **никаких исходящих вызовов**: включён только встроенный выход `store` (он же стор).
- Яндекс.Метрика и прочие внешние сервисы — адаптеры `MetricSink`, включаются в настройках вручную;
  в закрытом контуре недоступны по определению, поэтому UI этого не требует.
- События хранятся локально и могут «переигрываться» в новый sink (журнал доставки + at-least-once).

## Каталог контрактов (эскиз)

Полные сигнатуры и семантика — в `01-contracts.md`. Здесь — карта:

| Контракт | Роль | Кто реализует | Расширение |
|---|---|---|---|
| `MetricEvent`, `Measurement` | канонический конверт данных | модуль | новая версия схемы |
| `MetricSource` / коллекторы | сбор из точки | модуль | core-точки + extension points |
| `MetricsStore` | запись, запросы, роллапы, retention | Postgres сейчас, ClickHouse потом | новая реализация сервиса |
| `MetricsQuery` | AST-подмножество запросов | store | новые операторы |
| `MetricDefinition` (реестр) | бизнес-смысл: что такое метрика | модули | extension point `metrics:definitions` |
| `MetricPanel` / `MetricDashboard` | представление | модули + пользователь | extension point `metrics:panels` |
| `MetricSink` (+ capabilities) | выход наружу/в файл | адаптер | extension point `metrics:sinks` |
| `MetricAlertRule` / `MetricAlertEvent` | правила и события алертов | админ + evaluator | delivery через event bus/notification |
| `MetricsSettings` | настройки-синглтон | админ | миграции |

Принцип «новый выход = адаптер»: sink объявляет свои лимиты (`maxBatchBytes`, `maxEvents`,
`rateLimit`, `supportsBackfill`, `requiredIdentifiers`, `allowedPaths`), ядро модуля даёт durable
outbox с ретраями, маппинг и дедуп по `eventId`. Яндекс.Метрика, webhook, CSV, будущие OTLP/remote-write
и Prometheus-совместимый API — всё это независимые адаптеры.

## Что делать и в каком порядке

Нумерация — порядок реализации. Этапы 0–2 дают ценность без единого внешнего вызова; 5 — выходы.

| Этап | Содержание | Критерий готовности |
|---|---|---|
| **00** | Пакет `module-metrics`: контракты, миграции (settings, events, series/points, outbox), скелет сбора, псевдонимизация, настройки | Событие с клиента доходит до Postgres; `GET /api/metrics/events` отдаёт ленту |
| **01** | Ingestion (клиентский трекер + collect API), партиции, retention, эксплорер сырых событий, дефинишены | Pageviews и клики видны в админ-приложении; события не теряются при перезагрузке вкладки |
| **02** | Технические коллекторы: HTTP-роуты, SQL (обёртка пула + опция `pg_stat_statements`), задачи, ошибки сервера; панели Route RED и Slow SQL | p95 роутов и топ-N SQL по времени видны в админке; алерты пока не нужны |
| **03** | Бизнес-события: emit API для модулей, реестр определений, панели; воронки/retention | Метрики поддержки (AI-first, этап 3), workflow, обучения появляются как панели |
| **04** | Клиентские ошибки и RUM: группировка, release health, Web Vitals | Ошибка из браузера появляется в issues с fingerprint и контекстом |
| **05** | Выходы: outbox, адаптеры Яндекс.Метрики (Measurement Protocol + Offline Conversions), webhook, CSV; алерты-правила и evaluator | В облаке события уходят в Метрику; в закрытом контуре всё работает с `store` и без сети |
| **06** | Документация, приватность (opt-out, k-anonymity), эксплуатация (кардинальные лимиты, бюджеты), путь на ClickHouse | Потребительская дока по Diátaxis + `ref/notes/module-metrics.md` |

## Потребители и сценарии

| Потребитель | Что смотрит | Как работает |
|---|---|---|
| Админ/эксплуатация | Route RED, Slow SQL, ошибки, задачи, алерты | Эксплорер → панель → дашборд; алерт приходит в event bus/вебхук |
| Продукт | страницы, воронки, retention, каталог событий | События + предметные панели модулей |
| Бизнес-владелец (HR, поддержка) | «сколько обращений», «время ответа», отчёты по курсам | Панели, объявленные модулями через `metrics:definitions` |
| Модули-разработчики | `metrics:emit`, `metrics:definitions`, `metrics:panels` | Одна точка входа — не зависят от хранилища и UI метрик |
| Внешние системы | Яндекс.Метрика, вебхуки, файлы | Sinks с журналом доставки, выключены по умолчанию |

## Открытые вопросы

1. **Секреты/соль псевдонимизации.** Рекомендация: минимальный core-сервис `config`/`secrets`
   (чтение env с префиксом), модуль берёт соль оттуда. Альтернативы и обоснование — в `02-offline-stack.md`.
2. **HTTP-observer в core.** Рекомендация: одна root-точка `http:observer` в `createApp`, чтобы модуль
   видел все роуты, включая уже зарегистрированные соседями. Без неё — `onRoute` с хрупким порядком.
3. **React-ошибки корневого рендера.** `onUncaughtError` живёт в `createRoot` (apps/web) — нужна
   маленькая точка в core (`createFrontendApp`/`FrontendProvider`), либо best-effort из модуля.
4. **Зависимость `web-vitals`** (~3 КБ, Apache-2.0) для LCP/INP/CLS — писать своё не советует никто;
   подтвердить добавление.
5. **Дефолты:** raw-события 30 дней, роллапы 13 месяцев, сэмплирование pageviews 100%, клики 10%,
   cap серий на метрику 2000 (как в OTel). Зафиксировать при реализации.
6. **Права доступа** к метрикам (RBAC пока нет): до этапа 03 — только admin-layout, дальше — решить.
7. **Часовые пояса** бакетов: хранить UTC, отображать в TZ узла; `date_bin` от фиксированного origin.
8. **ClickHouse**: контейнер в reference-развёртывании не добавляем, пока Postgres держит нагрузку;
   триггеры перехода — в `02-offline-stack.md`, раздел «Масштаб».
