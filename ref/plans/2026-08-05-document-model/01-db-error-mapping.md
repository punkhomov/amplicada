# 01 — Понятные ошибки БД вместо сырого SQL

> Реализовано 2026-08-06, см. entry.
> `packages/platform-core/src/backend/services/db-errors.ts` + `db-errors.test.ts`.

## Проблема

Создать документ с уже занятым `code`/`login` → 500 с текстом
`duplicate key value violates unique constraint "hr_department_node_code_key"`.
Удалить используемый тег → 500 с текстом нарушения внешнего ключа.

Во всём проекте обрабатывается **ровно один** код ошибки Postgres — `23P01` (пересечение версий), и
только внутри hr-версионирования
([versioning.ts:3](../../../packages/module-hr/src/backend/services/versioning.ts#L3)). Ни `23505`
(unique_violation), ни `23503` (foreign_key_violation) не ловит никто. `setErrorHandler` в module-admin
делает `error.statusCode ?? 500`, а у ошибок драйвера `pg` есть `.code`, но нет `.statusCode`.

**Частота высокая.** `UNIQUE`-констрейнтов в миграциях больше десятка: `code` у отдела, ЦФО, юрлица,
штатной единицы, опроса, типа заявки; `login` у пользователя; составные `(family_id, code)` и
`(department_node_id, code)`. Ошибиться кодом при создании — рядовое действие пользователя.

**Про FK отдельно.** `hr-tag` — единственный тип, у которого одновременно `deletable: true` и нет
`deletedAt` (то есть удаление жёсткое), при этом на `hr_tag` ссылаются три таблицы через
`NOT NULL REFERENCES` без `ON DELETE`. Удаление используемого тега гарантированно даёт 23503.

## Решение

Единая трансляция кодов драйвера `pg` в `DocumentRuntimeError`:

| Код | Смысл | Ответ |
|-----|-------|-------|
| `23505` | unique_violation | 409 + «запись с таким значением уже существует» |
| `23503` | foreign_key_violation | 409 + «запись используется и не может быть удалена» |

**Где ставить.** В `DocumentRuntime`, оборачивая транзакции `create`/`update`/`delete`, а не в
`setErrorHandler` module-admin. Причина: у рантайма есть потребители помимо admin-роутов
(`module-hr-request`, `module-hr-poll` со своими роутами, а по
[08-model-gaps](./08-model-gaps.md) появятся и не-HTTP), и им нужны те же осмысленные ошибки.

**Осторожно с 23P01.** Его уже перехватывает `versioning.ts` и превращает в `VersionOverlapError`
(у которой есть `statusCode`). Общий маппинг не должен его перекрывать — либо не трогать 23P01 вовсе,
либо убедиться, что более специфичный обработчик отрабатывает первым.

## Что вскрылось при реализации: код лежит не там, где его искали

drizzle 0.45 оборачивает **любую** ошибку запроса в `DrizzleQueryError`
(`pg-core/session.js`, шесть точек в `queryWithCache`), а тот кладёт оригинал в `cause` и своего
`code` не имеет. Значит проверка вида

```ts
'code' in err && err.code === '23P01'
```

не срабатывает никогда — то есть перехват `23P01` в `versioning.ts` был **мёртвым**, и
`VersionOverlapError` до пользователя не доходила ни разу: вместо неё уходил сырой 500.

Поэтому распознавание вынесено в `findPgError`, который идёт по цепочке `cause` (с ограничителем
глубины против самоссылающихся ошибок), а `versioning.ts` переведён на общий `isPgErrorCode`.
23P01 при этом по-прежнему **не** маппится в общий 409 — он должен доставаться версионному
обработчику, который знает доменную формулировку.

## Сверх минимума

У ошибки `pg` есть поле `constraint` с именем констрейнта — по нему можно вернуть, какое именно поле
конфликтует, и подсветить его в карточке. Требует сопоставления имён констрейнтов с полями; в
минимальную версию не входит.

## Тесты

Юнит без БД: подсунуть объект с `code: '23505'` и проверить, что наружу выходит
`DocumentRuntimeError(409)`, а `23P01` по-прежнему достаётся `VersionOverlapError`.
