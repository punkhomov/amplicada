# 08 — Пробелы модели

Не дефекты, а недостающие части. Все три упираются в форму модели, поэтому идут после
[06-index-primary](./06-index-primary.md).

---

## Валидация: `required` ничего не делает

`FieldMetadata.required` объявлен в контракте и расставлен по документам, но **не читается нигде** — ни
валидации на бэкенде, ни визуального маркера на фронтенде (совпадения в grep относятся к другим
структурам: `PollQuestion.required` в опросах и полям заявок).

Шире: `DocumentRuntime` не валидирует значения полей вообще. Клиент может прислать что угодно в любое
поле любого расширения; единственная защита — типы колонок и констрейнты БД, а они после
[01-db-error-mapping](./01-db-error-mapping.md) хотя бы отвечают понятной ошибкой.

**Решить:** где живёт валидация — в рантайме по `FieldMetadata` (обязательность, тип, `options`) или в
схеме Fastify per-route. Первое даёт единообразие всем типам бесплатно, второе — точнее сообщения.

До этого решения `required` стоит пометить в контракте как декоративный, чтобы он не создавал ложного
ощущения гарантии.

## Оптимистичная блокировка

Двое редактируют один документ — молча побеждает последний сохранивший. Карточка считает `isDirty`
локально и не знает, что состояние на сервере ушло вперёд.

Токен для этого уже есть — `document_index.updatedAt` (появился вместе с actor-трекингом). Достаточно
принимать его в `PUT` и отклонять запрос при расхождении (409).

Стоит делать после [06](./06-index-primary.md): там индекс становится первичным, и `updatedAt` из
удобного поля превращается в естественный атрибут документа.

## Программный API документов

Сегодня для кода доступно ровно то же, чем пользуется HTTP-слой: `create(type, body)` /
`update(type, id, body)`, где `body` — нетипизированный `Record<string, unknown>` формы
`{ module: { key: { field } } }`. Для чтения есть типизированный `extract(doc, ns)`, симметричной записи
нет. Плюс `getAnyById` всегда грузит **все** расширения (отдельный запрос на каждое), даже если нужно одно.

Напрашивается пара к `extract` и точечная загрузка:

```ts
const dept = await documents.get(id, HR_DEPARTMENT_NS);        // одно расширение, один запрос
await documents.patch(id, HR_DEPARTMENT_NS, { name: 'X' });    // типизированный патч
const id  = await documents.create('hr-department', [[HR_DEPARTMENT_NS, { code: 'D-1' }]]);
```

`NamespaceKey<T>` под это готов (после multikey адресует пару `module` + `key`) — не хватает
write-стороны и загрузки по одному namespace.

**Почему после 06:** форма `get(id, ns)` зависит от того, осталось ли понятие базовой таблицы. До
этапа 3 спроектируем дважды.

**Держать в голове:** не все данные проекта обязаны быть документами (см.
[00-overview](./00-overview.md)). API должен оставлять явным, где начинается документная модель, а где
обычная таблица модуля, — а не подталкивать заворачивать в документы всё.

## Наблюдения (влияют на решения, но чинить нечего)

**Покрытие soft-delete неполное.** `deletedAt` есть только у `identity_user`, `user_groups`, `poll` и
`hr_request_types`. Все hr-справочники, `scheduled_tasks`, `workflows`, `process_instances` удаляются
жёстко, с каскадом extension-данных. Прикрыто тем, что у hr-справочников выставлен `deletable: false` —
у всех, кроме `hr-tag`, что и даёт FK-сценарий из
[01-db-error-mapping](./01-db-error-mapping.md).

**Бутстрап без advisory-лока.** Миграции применяются в `app.ts:200-216` без блокировки, при том что
проект рассчитан на несколько инстансов (есть `TaskLock`, Redis, `workerId`). Сериализует ли
drizzle-миграции внутри себя — не проверял, утверждать не берусь; перед запуском нескольких реплик это
стоит выяснить. `reconcileFixtures` при этом детерминирован от кода и безопасен. Вне документной
модели, но рядом.

> После этапа 1 [06-index-primary](./06-index-primary.md) `backfillIndex` из бутстрапа удалён —
> разовый бэкфилл переехал в миграции, по одной на модуль.
