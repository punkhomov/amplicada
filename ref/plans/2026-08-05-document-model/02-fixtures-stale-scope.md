# 02 — Скоуп stale-разметки в fixtures

> Реализовано 2026-08-06, см. entry.
> Индексный `UPDATE ... RETURNING id` теперь и есть источник списка id для базовой таблицы —
> отдельного вычисления скоупа не понадобилось.

## Проблема

`reconcileFixtures` метит устаревшие fixture-строки в двух местах, и разметка базовой таблицы —
**без фильтра по fixture**, в отличие от индексной:

```ts
// индекс — со скоупом
and(eq(documentIndex.type, type), eq(documentIndex.fixture, true), notInArray(documentIndex.id, seenIds))

// базовая таблица — без него
db.update(doc.schema).set({ stale: true }).where(notInArray(idCol, seenIds))
```

Комментарий в коде допущение признаёт: «предполагается, что все её строки — fixtures».

Сегодня оно выполняется: единственный fixture-тип — `scheduled-task`, объявлен `creatable: false`
(единственное объявление фикстур — [app.ts:229](../../../packages/platform-core/src/backend/app.ts#L229)).
Но защиты нет: fixture-тип с колонкой `stale` и разрешённым созданием получит массовую пометку
пользовательских строк на каждом бутстрапе.

## Решение

Размечать базовую таблицу по списку fixture-id из индекса, а не «все строки таблицы» — то есть тем же
скоупом, что уже применён к индексу. Правка на пару строк.

## Что НЕ здесь

Само дублирование `stale` между индексом и базовой таблицей — в
[06-index-primary, этап 2](./06-index-primary.md), вместе с `deletedAt`: это одна и та же операция, и
делать её порознь бессмысленно. Контекст для этого решения:

- **Индексная копия мертва.** `documentIndex.stale` не читает никто. `documentIndex.fixture` читается
  только самим `reconcileFixtures`. Под неиспользуемую копию заведён отдельный частичный индекс
  `idx_document_index_stale ON (type) WHERE stale`
  ([0000_init.sql:100](../../../packages/platform-core/migrations/0000_init.sql#L100)), обслуживающий
  ноль запросов.
- **Работает базовая копия.** Приложение читает `scheduledTasks.stale` — роут
  [tasks.ts:37](../../../packages/module-admin/src/backend/routes/tasks.ts#L37) и UI карточки задачи
  (баннер + блокировка кнопки «запустить»).

Направление схлопывания — в индекс: он generic и не требует от каждого типа заводить свою колонку;
мёртвый частичный индекс при этом начнёт работать, а роут задач будет читать индекс.

## Смежная деталь для этапа 2

`indexCreated` в conflict-ветке всегда выставляет `deletedAt: null`, базовую таблицу не трогая. Для
fixture-типа с soft-delete это дало бы прямое расхождение копий: индекс считает документ живым,
базовая таблица — удалённым. Сегодня недостижимо (`scheduled_tasks` без `deletedAt`), но это ровно тот
сценарий, ради которого копию и надо убирать.
