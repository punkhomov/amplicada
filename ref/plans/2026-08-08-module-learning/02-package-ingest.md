# 02 — приём и распаковка пакета

Путь от «админ выбрал ZIP» до `packages.status = 'ready'` с разложенными в бакет файлами и
заполненным инвентарём. Зависит от `04` (таблицы) и от `01` (стриминг — см. ниже, он нужен не только
для раздачи).

## Лимит загрузки — не блокер и не правка core

В [00-overview](./00-overview.md) это числилось третьим блокером. **Оказалось, менять `platform-core`
не нужно**: `@fastify/multipart` разрешает переопределять лимит на месте вызова, в том числе вверх
относительно глобального —

```ts
const file = await request.file({ limits: { fileSize: PACKAGE_MAX_BYTES } });
```

Глобальные `fileSize: 100 MB` в [`createApp`](../../../packages/platform-core/src/backend/app.ts#L93)
остаются как есть и продолжают защищать все прочие роуты.

## Распаковка без чтения архива в память

Наивная реализация — `storage.getObject()` в Buffer, затем распаковка — на пакете с видео съедает
гигабайты RAM. Не нужна и промежуточная запись на диск.

ZIP читается с произвольным доступом: central directory лежит в конце файла, дальше каждая запись
достаётся по смещению. Это ровно то, что даёт `getObjectStream(key, { range })` из `01` — то есть
блокер `01` обслуживает не только раздачу, но и распаковку. Стриминговые библиотеки (`unzipper`
через `Open.custom`, `yauzl` через `fromRandomAccessReader`) принимают такой источник; **точный API
проверить при реализации** — здесь зафиксирован только принцип: читаем по диапазонам, пишем в S3
пофайлово, целиком в памяти не держим ни архив, ни отдельный крупный файл.

`adm-zip` не годится — он разбирает архив только целиком в памяти.

## Поток обработки

```
POST /api/learning/courses/:courseId/packages   (multipart, admin)
  │  request.file({ limits: { fileSize: PACKAGE_MAX_BYTES } })
  │  → S3: learning/_incoming/<packageId>.zip
  │  → INSERT packages (version = max+1, status='pending', source_key)
  │  → redis.publish(RUN_NOW_CHANNEL, 'learning-package-ingest')   -- eager
  └─ 202 { packageId, status: 'pending' }

           воркер: задача learning-package-ingest
  ┌─────────────────────────────────────────────────────────────┐
  │ claim: UPDATE packages SET status='processing'              │
  │        WHERE id = (SELECT id FROM packages                  │
  │                    WHERE status='pending' ORDER BY created_at│
  │                    FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING │
  │ ↓                                                            │
  │ валидация → распаковка в learning/<packageId>/<path>         │
  │ → INSERT package_files (path, content_type, size)            │
  │ → парсинг imsmanifest.xml → entry_point, title, scorm_version│
  │ ↓                                                            │
  │ status='ready'  |  status='failed' + error + cleanup         │
  └─────────────────────────────────────────────────────────────┘
```

**Eager-диспатч плюс расписание как фолбэк** — тот же приём, что в
[workflow async-task](../2026-07-21-workflow-async-task.md). `redis.publish(RUN_NOW_CHANNEL, code)`
будит воркер сразу (механизм уже есть: так работает кнопка «Запустить» в админке задач,
[tasks.ts:128](../../../packages/module-admin/src/backend/routes/tasks.ts#L128)), а cron-расписание
подбирает пакеты, чей publish потерялся из-за перезапуска.

**Claim через `FOR UPDATE SKIP LOCKED`** — иначе два воркера возьмут один пакет. Задача в цикле
разбирает всё, что есть в `pending`, и завершается, когда claim ничего не вернул.

`ROLE` по умолчанию `'all'` ([role.ts](../../../packages/platform-core/src/backend/role.ts)), так что
в dev тот же процесс и принимает загрузку, и обрабатывает.

## Валидация до записи в бакет

| Проверка | Почему |
|---|---|
| **zip-slip**: нормализованный путь не выходит за корень, нет абсолютных путей и `..` | Запись в чужой префикс бакета |
| **Лимит числа файлов** и **суммарного распакованного размера** | Zip-bomb: 40 KB архива разворачиваются в терабайты |
| **Коэффициент сжатия** отдельной записи | Тот же zip-bomb, но одним файлом |
| **Whitelist расширений** | Отсекает исполняемое и неожиданное до попадания в бакет |
| **Наличие `imsmanifest.xml`** (для `kind='scorm12'`) | Иначе это не SCORM-пакет |
| **Entry point из манифеста существует в архиве** | Иначе `ready`-пакет открывается 404 |

Всё падает в `status='failed'` с текстом в `error` — админ видит причину на карточке курса, а не
пустой пакет.

## Content-Type — считается здесь, один раз

Тип каждого файла определяется при распаковке по расширению и пишется в `package_files.content_type`.
Раздача (`03`) берёт его оттуда и **никогда не сниффит**. Это то, что снимает классическую причину
«SCORM не работает» — в прокси-режиме MIME задаём мы, а не настройки бакета.

Неизвестное расширение → `application/octet-stream` (и `03` отдаёт такой файл как вложение, а не
инлайном).

## Парсинг `imsmanifest.xml`

`fast-xml-parser`. Достаём:

- `<organizations><organization><title>` → `packages.title`;
- ресурс, на который ссылается первый `<item>` (или `<resource adlcp:scormtype="sco">`), его `href` →
  `entry_point`;
- `<metadata><schemaversion>` → `scorm_version`.

Манифесты в природе кривые: неймспейсы то есть, то нет; `href` бывает с query-строкой
(`index.html?foo=1`) — при резолве в инвентаре её нужно отбросить. Разбор терпимый к отсутствию
необязательного, жёсткий к отсутствию entry point.

## `kind: 'file'`

Тот же роут, но без распаковки: файл кладётся как единственная запись инвентаря,
`entry_point` = его имя, `status='ready'` сразу. Отдельная ветка на 20 строк, не отдельный конвейер.

## Мусор и удаление

- `failed` → удалить всё, что успели записать под `learning/<packageId>/`, и исходник из `_incoming/`.
- Успешный `ready` → исходный ZIP из `_incoming/` тоже удаляется: он больше не нужен, а место занимает.
- Удаление пакета/курса → удаление префикса. Здесь и пригодилась пагинация `listObjects` из `01`:
  распакованный пакет легко больше 1000 объектов.
- Сверка «объекты в бакете без строки в `package_files`» — отдельная задача-уборщик, **в v1 не делаем**,
  записать как долг.

## Формат пакета — отдельный пакет `@amplicada/learning-parser`

Всё, что описывает **формат**, а не нашу платформу, вынесено из модуля: чтение ZIP, разбор
манифеста, нормализация путей, карта MIME, правила приёма. У этой части нет ни Fastify, ни Drizzle,
ни S3 — только чистые функции и абстракция «дай поток на диапазон байт», поэтому она целиком
покрывается тестами без инфраструктуры.

`packages/learning-parser` — **обычная библиотека, а не модуль платформы**: один экспорт `.`, без
`backend/frontend/contracts`. Отступление от общей раскладки пакетов осознанное — раскладка описывает
модули, а это не модуль.

Раскладка — слоями, в порядке зависимости. Обратных рёбер нет: ни один слой не импортирует из тех,
что ниже в таблице.

| Слой | Что внутри |
|---|---|
| `src/archive/` | пакет как набор файлов: `paths` (пути внутри пакета), `zip` (`ZipArchive` поверх `RandomAccessSource`, yauzl), `layout` (поиск описателя и корня), `text` (декодирование в строку) |
| `src/xml/` | `parser` (настройка fast-xml-parser, отдаётся формату) и `nodes` (навигация по дереву) |
| `src/model/` | результат разбора: `metadata`, `launch` (цель запуска), `score` (шкала проходного балла) |
| `src/formats/` | `descriptors` (имена описателей, **без единого импорта**), `detect` (`parsePackage`), `scorm/`, `cmi5/`, `xapi/`, `aicc/` (`course` + `ini` + `csv`) |
| `src/intake/` | правила приёма нашего LMS: `inspect` (`planExtraction`), `content-types` (MIME + whitelist) |
| `src/testing/` | сборка ZIP в памяти для тестов, включая намеренно кривые |

Раскладка выбрана под то, что придёт с расширением разбора: sequencing SCORM 2004 и LOM ложатся в
`formats/scorm/`, дерево оглавления — в `model/`, определение кодировки — в `archive/text.ts`,
валидаторы с правилами — отдельным слоем над `formats/`.

Три склейки разрезаны намеренно, а не для красоты:

- **`intake` больше не тянет парсеры.** Имя описателя нужно знать до того, как что-то прочитано —
  каталог описателя и есть корень пакета. Раньше `planExtraction` импортировал `isDescriptorName` из
  модуля разбора и через него утаскивал все пять форматов ради сравнения строки.
- **Список «всегда массив» переехал к форматам.** Он был один общий, и `<description>` в SCORM
  становился массивом только потому, что так нужно xAPI. С приездом sequencing SCORM 2004 (десятки
  повторяемых элементов) соседние форматы стали бы разбираться иначе без единой правки в своём коде.
- **`launch.ts` держал три несвязанные вещи**: цель запуска, поиск описателя и шкалу балла. Разошлись
  по `model/launch`, `archive/layout` и `model/score`.

## Распознаём пять форматов, проигрываем один

Опознание — по файлу-описателю, как в любом LMS: `imsmanifest.xml` → SCORM, `cmi5.xml` → cmi5,
`tincan.xml` → xAPI, `*.crs` с секцией `[Course]` → AICC. Порядок проверки не случаен: сборщики
вроде Articulate публикуют курс сразу в двух форматах, кладя `imsmanifest.xml` и `tincan.xml` рядом,
и первым должно идти то, что мы умеем проигрывать.

**Всё, кроме SCORM 1.2, отклоняется на приёме** с текстом «Пакет распознан как …, а проигрывать мы
умеем только SCORM 1.2». Причина отказа — не парсер, а рантайм:

| Формат | Что нужно для проигрывания |
|---|---|
| SCORM 2004 | Тот же рантайм другой формы: `API_1484_11`, `completion_status` + `success_status` вместо одного `lesson_status`. Ближайший по стоимости |
| cmi5, xAPI | **LRS**: приём statement'ов, хранилище, State API для `LMS.LaunchData`, авторизация launch-токенами. Отдельная подсистема, крупнее подплана `05` |
| AICC | **HACP**: form-encoded POST'ы с session-ключом и командами `GetParam`/`PutParam`. Третий протокол |

Разобрать чужой формат дёшево (полторы-две сотни строк), проиграть — нет. Принятый, но
непроигрываемый пакет хуже отказа: админ видит «Готов», учащийся видит пустой экран.

Побочно распознавание даёт то, чего не было: **внешний адрес запуска**. У xAPI/cmi5/AICC контент
часто живёт на чужом сервере, да и SCORM-манифест вправе указать `href="https://…"`. Такой пакет
теперь отклоняется явно, а не превращается в бессмысленный путь `http:/vendor.example/…`, который
ищется в инвентаре.

## Ещё две правки в core, которых не было в списке блокеров

Обнаружились при реализации — без них «не держим в памяти» остаётся лозунгом:

- **`putObjectStream(key, body, options?)`.** `putObject` принимает готовый `Buffer`, то есть файл
  из пакета всё равно оказался бы в памяти целиком. С известной длиной (она есть в оглавлении ZIP)
  уходит одним `PUT`; без длины (тело multipart-запроса) — multipart-загрузкой через
  `@aws-sdk/lib-storage`. Новая зависимость core.
- **`deletePrefix(prefix)`.** Уборка неудавшегося пакета поштучно — это тысячи round-trip'ов.
  `DeleteObjects` берёт по 1000 ключей за раз; пустой префикс отвергается, иначе опечатка в сборке
  ключа снесла бы бакет.

## Проверка

1. Залить настоящий SCORM 1.2 пакет (iSpring/Articulate) → `status` доходит до `ready`, в
   `package_files` столько же строк, сколько файлов в архиве, `entry_point` указывает на
   существующую запись.
2. Пакет без `imsmanifest.xml` → `failed` с внятным текстом, в бакете ничего не осталось.
3. Архив с `../` в пути → `failed`, ни один файл не записан.
4. Пакет заметно больше глобальных 100 MB → проходит (per-route лимит работает), при этом обычная
   загрузка в админке «Хранилище» по-прежнему ограничена сотней мегабайт.
5. Два быстрых перезалива подряд → две строки `packages` с разными `version`, обе обработаны, ни одна
   не взята дважды.
6. Убить процесс во время обработки → пакет висит в `processing`; через `STALE_PROCESSING_MS`
   (30 минут) расписание забирает его снова и доводит до конца.
7. Пакет, зазипованный вместе с внешней папкой → принимается, префикс папки отрезан, пути в
   инвентаре начинаются от `imsmanifest.xml`.

## Решённые вопросы

1. **Зависшие `processing`** — колонка `packages.claimed_at` (миграция `0001`) и таймаут
   `STALE_PROCESSING_MS`. Heartbeat не понадобился: распаковка либо укладывается в полчаса, либо
   считается потерянной и начинается заново — она идемпотентна (инвентарь пакета переписывается
   целиком, объекты в бакете перезаписываются по тем же ключам).
2. **Библиотека распаковки** — `yauzl`. `fromRandomAccessReader(reader, size, …)` принимает наш
   источник как есть, реализовать нужно один метод `_readStreamForRange(start, end)`. Проверено
   тестом: на открытие архива уходит меньше половины его размера, а не весь файл. Бонусом yauzl сам
   отвергает записи с `../` и абсолютными путями — наша проверка стала вторым рубежом, а не единственным.
3. **Claim** — не `FOR UPDATE SKIP LOCKED`, а «SELECT кандидата + условный UPDATE», как в
   `WorkflowAutomationWorker`. Гарантия та же (строку получает ровно один воркер), выражается
   типизированным drizzle без сырого SQL. Проигравший гонку берёт следующего кандидата, а не
   выходит из цикла.

## Открытые вопросы

1. **Конкретные лимиты** (`PACKAGE_MAX_BYTES` 2 ГБ, 10 000 файлов, коэффициент 200) взяты с потолка
   и ждут встречи с реальными пакетами. Про коэффициент сжатия важно помнить: у HTML/JS он
   доходит до нескольких десятков, так что низкий порог отвергал бы нормальные курсы.
2. **Кодировка манифеста.** Убирается BOM, дальше читаем как UTF-8. Манифест в windows-1251
   развалится; встретится — добавить определение кодировки по XML-декларации.
3. **Уборщик осиротевших объектов** («в бакете есть, в `package_files` нет») — по-прежнему не
   делаем. Теперь у него появился второй источник мусора: пакет, чья заливка оборвалась после
   записи в бакет, но до `ready`.
