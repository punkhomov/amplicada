# module-hr-learning — курсы и плеер

Зонтичная папка. Этот файл — верхнеуровневая рамка: что строим, из каких кусков, в каком порядке,
и какие решения ещё не приняты. Детализация и разбиение на фазы — в подпланах `01`–`07`
(пока их нет, нумерация задаёт порядок работ).

Исходный материал — [99-ai-chat-qwen.md](./99-ai-chat-qwen.md) (общий обзор индустрии: SCORM/xAPI/cmi5,
S3, библиотеки). Половина его рекомендаций к нам **не применима** — см. «Чем мы отличаемся от типовой
схемы».

## Что строим

Модуль `packages/module-hr-learning` (сейчас — пустая npm-оболочка, кода нет):

- **Админ** заводит курс, грузит SCORM-пакет (ZIP), назначает его людям.
- **Пользователь** видит доступные курсы на портале (страница `/learning`), открывает плеер, проходит,
  прогресс сохраняется и переживает перезаход.
- **Контент раздаётся только через бекенд-прокси.** Presigned URL не используем — это уже принятое
  решение по хранилищу (см. entry S3): `S3_ENDPOINT` —
  внутренний docker-хост, из браузера недостижим, а presigned-ссылка вдобавок обходит сессионную
  авторизацию.

## Чем мы отличаемся от типовой схемы

Прокси-режим убирает три классические проблемы из общего обзора и добавляет две свои.

| Тема | Типовая схема (S3 напрямую) | У нас |
|---|---|---|
| MIME-типы | главная причина «SCORM не работает» — надо настраивать в бакете | **не проблема**: `Content-Type` ставит наш роут, по карте расширений при распаковке |
| CORS на бакете | обязателен для iframe | **не нужен**: контент отдаётся с origin приложения (`/api/...`, в dev через vite-прокси) |
| Относительные пути в пакете | ломают presigned-ссылки, требуют CloudFront | **не проблема**: `GET /api/learning/content/:packageId/*` — обычный путь, относительные ссылки резолвятся сами |
| Трафик | уходит мимо приложения на CDN | **весь через Fastify** — нужен стриминг и Range, иначе видео не перематывается и жрёт RAM |
| Изоляция чужого JS | контент на отдельном домене бакета — сам по себе другой origin | **контент на нашем origin** — по умолчанию чужой JS равен сессии платформы. Это главный риск, см. `03` |

## Блокеры в core — первая фаза этого плана

Модуль без них не поедет, поэтому это **не фоновый долг и не отдельная задача**: работы в
`platform-core` входят в объём плана и делаются первыми, до кода самого модуля. Все три — подплан `01`.

| Что сломано | Где | Почему блокирует | Статус |
|---|---|---|---|
| `getObject(key): Promise<Buffer>` — объект читается целиком в память, `Range` не поддерживается | contracts/backend/storage.ts, backend/services/storage-service.ts | браузер не получит `206 Partial Content` → видео без перемотки; каждый зритель — это файл целиком в RAM процесса API | ✅ 2026-08-08: `getObjectStream(key, { range })`, `Range` уходит в S3 как есть, наружу `Readable` + `ContentRange`/`ContentLength`; диапазон вне размера → `416` |
| `listObjects` не пагинируется — `ListObjectsV2` отдаёт максимум 1000 ключей, continuation token не прокидывается | backend/services/storage-service.ts | распакованный SCORM-пакет легко больше 1000 файлов → выдача молча обрезается (удаление пакета оставит мусор в бакете) | ✅ 2026-08-08: дочитывание по `ContinuationToken` |
| ~~Глобальный `fileSize: 100 MB` у `@fastify/multipart`~~ | [app.ts:93](../../../packages/platform-core/src/backend/app.ts#L93) | — | ❌ **блокером не является**: `request.file({ limits: { fileSize } })` переопределяет глобальный лимит, в том числе вверх. Первые два сделаны сразу — у них уже есть живой потребитель, админка «Хранилище»

## Архитектура

```
                 ┌─────────────────────────────────────────────┐
   админ ─────►  │ POST /api/learning/packages  (ZIP, multipart)│
                 └───────────────┬─────────────────────────────┘
                                 ▼
                    сырой ZIP в S3, строка packages(status=pending)
                                 ▼   фоновая задача (TaskScheduler)
                    распаковка → валидация → раскладка в S3
                    learning/<packageId>/<path>, Content-Type по расширению
                    парсинг imsmanifest.xml → entryPoint, title, scormVersion
                                 ▼
                              status=ready

  пользователь ─► /learning (каталог) ─► /learning/:id ─► /learning/:id/play
                                                              │
                                            ┌─────────────────▼──────────────────┐
                                            │ <iframe sandbox src=/api/learning/ │
                                            │        content/:pkg/index.html>    │
                                            │  ↑ прокси инжектит scorm-again +   │
                                            │    стартовое cmi-состояние         │
                                            └─────────────────┬──────────────────┘
                                    commit → POST /api/learning/attempts/:id/commit
                                    postMessage → родитель обновляет прогресс-бар
```

### Данные (эскиз, уточняется в `04`)

| Таблица | Назначение |
|---|---|
| `learning_courses` | карточка курса: код, название, описание, категория, обложка, `active`. **Документ** Document System — админский CRUD, списки и фильтры получаем даром (как `hr-poll`) |
| `learning_packages` | версия контента курса: `kind` (`scorm12`/…), `status` (`pending`/`ready`/`failed`), `entryPoint`, `error`, размер, кто загрузил |
| `learning_package_files` | инвентарь распакованного: путь → размер, `contentType`. Нужен для отдачи без обращения к `listObjects` и для удаления пакета |
| `learning_enrollments` | назначение: `userId` × `courseId`, источник (самозапись/назначено/по правилу), `dueAt`, статус |
| `learning_attempts` | попытка прохождения: сырое `cmi`-состояние (jsonb) + нормализованные `completion`, `success`, `score`, `totalTime`. **Документ** — read-only карточка и список для админа |

Документы — курс и попытка. Пакеты, файлы пакета и назначения — обычные таблицы со своим API
(принцип из документной модели: [«не все данные проекта обязаны быть
документами»](../2026-08-05-document-model/00-overview.md)).

**Попытка как документ — по образцу `poll-response`** ([код](../../../packages/module-hr-poll/src/backend/documents/poll-response.ts)):
`creatable: false`, все поля `readonly`, object-extension **без `schema`** (тогда `saveExtensionData`
пропускает сохранение целиком — гарантия, что попытку не отредактировать прямым `PUT` в обход UI),
`deletable: true` с явным `remove` (своей таблицы у типа документа больше нет, без `remove` строка
попытки пережила бы удаление документа, а `document_index` не удалился бы вовсе — на него FK).

Из этого следуют два требования к путям записи, и они не бесплатны:

- **Создание попытки обязано идти через `documentRuntime.allocateDocumentId('learning-attempt', tx)`**
  до вставки строки: `learning_attempts.id` ссылается на `core.document_index(id)` внешним ключом,
  проверка немедленная. Метод для того и есть в контракте — «для участия в чужой транзакции»
  ([document-runtime.ts:102](../../../packages/platform-core/src/contracts/backend/document-runtime.ts#L102)),
  так уже делают `WorkflowEngine.startProcess()` и `HrStructureService.create*()`.
- **Коммиты `cmi` идут `UPDATE`'ом по таблице напрямую**, а не через `DocumentRuntime.update()`:
  SCORM-контент коммитит часто (autocommit каждые N секунд), а `update()` — это транзакция с
  прогоном всех расширений. Побочный эффект: `updated_at`/`updated_by_user_id` в индексе останутся
  от момента создания. Мириться с этим или трогать индекс на коммите — решается в `04`.

### Изоляция контента: чужой JS на нашем origin (детали в `03`)

SCORM-пакет — это произвольный чужой JS. Отдавая его с `/api/...`, мы запускаем его на origin
платформы: он может дёргать наш API от имени пользователя, читать `localStorage`, скриптовать
родительскую страницу. Фактически self-XSS, разрешённый по конструкции.

`httpOnly: true` на сессионной cookie ([app.ts:80](../../../packages/platform-core/src/backend/app.ts#L80))
тут не помогает: курсу не нужно её *читать* — достаточно сделать `fetch('/api/...')`, и браузер
приложит её сам.

#### Ловушка: атрибут `sandbox` на iframe — не защита

Атрибут работает, только когда документ грузим мы. Ссылка `/api/learning/content/<pkg>/evil.html`,
открытая прямо в адресной строке или встроенная чужим сайтом, отрендерится на нашем origin без всякой
песочницы — с cookie и доступом к API.

Основной механизм — **заголовок ответа** `Content-Security-Policy: sandbox allow-scripts`: он
применяется к документу независимо от способа открытия. Атрибут на iframe ставим тоже, но вторым
слоем, а не основным.

#### Набор мер

| Слой | Что |
|---|---|
| Заголовки контента | `CSP: sandbox allow-scripts allow-modals` (`allow-forms`/`allow-popups` — только когда реальный пакет сломается, не авансом). **Никогда `allow-same-origin` вместе с `allow-scripts`** — пара самоотменяющаяся, документ снимает с себя песочницу. `X-Content-Type-Options: nosniff`. `Referrer-Policy: no-referrer` — иначе токен утечёт в `Referer` по внешней ссылке из курса. CSP на исходящий трафик (`default-src`/`connect-src` с явным origin приложения, **не** `'self'` — в opaque origin его семантика мутная), чтобы курс не звонил домой |
| Авторизация | Opaque origin ⇒ `Origin: null` ⇒ `SameSite=Lax` cookie не уходит, сессии у контента нет по построению. Свой короткоживущий HMAC-токен, привязанный к (`userId`, `packageId`, `attemptId`), **в префиксе пути, не в query**: `/api/learning/content/<token>/<pkg>/index.html` — тогда относительные ссылки внутри пакета (`./js/main.js`, `../media/v.mp4`) тащат его сами, переписывать HTML не нужно. Принимается только контент- и commit-роутами, на отдельном ключе, не на `SESSION_SECRET` напрямую |
| Резолв пути | Путь запроса ищется строкой в `learning_package_files`, нет строки → 404. Никакой конкатенации пути в S3-ключ. Одним движением закрывает traversal, «курс читает соседние объекты бакета» и даёт `Content-Type` из той же строки (не из сниффинга и не из запроса; неизвестное расширение → `application/octet-stream` + `Content-Disposition: attachment`) |
| iframe | те же sandbox-флаги атрибутом + `allow="fullscreen"` для видео, без `allow-top-navigation` |

#### Следствие, определяющее весь рантайм плеера

Из opaque-origin iframe нельзя достучаться до `window.parent.API`, а SCORM API **синхронный**
(`LMSGetValue` обязан вернуть строку сразу) — поверх асинхронного `postMessage` его честно не
реализовать. Значит `scorm-again` живёт **внутри iframe**, а не в родителе (в отличие от схемы из
обзора): прокси инжектит в entry-HTML пакета скрипт с уже подставленным стартовым `cmi`-состоянием,
чтение идёт синхронно из локальной копии, а `SetValue`/`Commit` асинхронно летят на наш API. Родителю
через `postMessage` остаются только UI-события: процент, «курс завершён», «закрыть».

#### Чего это не закрывает

1. **Фишинг внутри фрейма** — курс рисует «сессия истекла, введите пароль». Opaque origin не мешает.
   Лечится только UX: хром плеера всегда виден, iframe не разворачивается на весь экран без рамки.
2. **Расход ресурсов** — майнер, бесконечный цикл. Принимаем.
3. **SCORM клиент-авторитетен по спецификации.** `LMSSetValue('cmi.core.score.raw', '100')` — норма
   протокола, любой учащийся накрутит балл через консоль. Это ограничение SCORM, не нашей схемы.
   Практический вывод: **нужны доверенные баллы — тест делается на нашей стороне (как в `hr-poll`), а
   не внутри пакета.** Пакету можно верить ровно настолько, насколько верим самому учащемуся.

#### Отдельный origin для контента — не делаем

`content.<host>` сделал бы изоляцию структурной, а не зависящей от того, что заголовок не забыли, и
позволил бы убрать токен из URL (cookie на том origin). Цена — DNS, TLS, reverse proxy; сейчас не
берём. Но код не должен генерировать абсолютные URL к контенту, и вся раздача живёт под одним
префиксом — тогда переезд, если понадобится, останется конфигом.

### Что должно быть провалидировано при распаковке (`02`)

zip-slip (`../` в путях), лимит числа файлов и суммарного распакованного размера (zip-bomb),
белый список расширений, наличие `imsmanifest.xml`, наличие entry-точки из манифеста. Плюс: пакет
может быть больше текущего multipart-лимита, а распаковка гигабайтного архива не должна блокировать
event loop — отсюда фоновая задача поверх уже существующего `TaskScheduler` в core.

## Принятые решения

**Формат в v1 — SCORM 1.2** (плюс `kind: 'file'`, см. ниже): готовый корпоративный контент
выпускается именно в нём (iSpring, Articulate, Captivate), а свой конструктор — отдельный большой
UI-проект, во многом повторяющий редактор вопросов из `module-hr-poll`. Поле `kind` в модели пакета
оставляет место «нативному курсу» позже.
Решено 2026-08-08: попытка — отдельный документ (см. «Данные»); виджет не делаем, только страница;
изоляция контента — sandbox через **заголовок** `CSP`, токен в префиксе пути, отдельный origin
не заводим (см. «Изоляция контента»). Версии пакета — **история** (попытка привязана к `packageId`);
`kind: 'file'` берём в v1; доступ — **назначение и самозапись**. Детали в
[04](./04-course-model.md).

## Открытые вопросы

Найдены при разборе, старт `01`/`04` не блокируют — решаются при детализации подпланов. Рекомендации
записаны, чтобы не передумывать заново.

### Модели прав в проекте нет — пропускаем сознательно

`module-admin` гейтит всё одним `preHandler`: залогинен → пускаем
([index.ts:33](../../../packages/module-admin/src/backend/index.ts#L33)). `ProcessRole` — это
`web`/`worker`, роль процесса, не пользователя. Таблица `core.document_access` (`level`, `owner`,
`role`, `groupId`) объявлена, но **у неё ноль потребителей**: ничего в неё не пишет и ничего не читает.

Остальным модулям это сходило — справочники HR и типы заявок не персональные данные. Обучение
первым ломает допущение: **попытка — персональные данные**, а «попытка» у нас документ, то есть по
умолчанию видна в админке любому залогиненному.

RBAC ради этого модуля не строим. Фиксируем три вещи:

- загрузка пакетов и назначение — за общим admin-гейтом, консистентно с проектом;
- портальные роуты проверяют `userId` сами, не полагаясь на гейт: своя попытка — да, чужая — 404;
- **`07` без модели прав честно не делается** — «руководитель видит прохождение подчинённых» и есть
  разграничение доступа. Это зависимость подплана, а не то, что выяснится на середине.

Точка возврата: когда модель прав появится, `document_access` — готовое место, а обучение — первый
реальный потребитель, на котором её стоит проверять.

### Одна попытка — одна активная сессия

SCORM предполагает одну сессию на попытку. Две открытые вкладки → коммиты перетирают весь `cmi` blob
целиком, last-write-wins, прогресс теряется молча. Классический LMS-баг: вылезает у пользователей, не
в тестах.

Предложение — lease без блокировок в БД: при старте плеера выдаём `sessionId`, зашиваем в токен,
commit принимается только с текущим. Вторая вкладка перевыпускает lease, первая получает `409` и
показывает «курс открыт в другом окне».

### Нормализация статуса и политика попыток

`cmi.core.lesson_status` ∈ {`passed`, `completed`, `failed`, `incomplete`, `browsed`, `not attempted`}
→ наши `completion`/`success`. Правило записать явно, оно не самоочевидно. Плюс:

- **Пакеты, которые никогда не шлют финальный статус, — норма, а не исключение.** Нужен ручной
  override админом («отметить пройденным»), иначе поддержка будет ходить в БД руками.
- **Resume vs restart**: `cmi.core.entry='resume'` + `cmi.suspend_data`. Предложение на v1 — одна
  незавершённая попытка, всегда resume, «пройти заново» отдельным действием.
- **Ограничить размер `suspend_data`**: курсы складывают туда всё своё состояние, без лимита пакет
  будет слать мегабайты на каждом автокоммите.

### Кэширование против токена в пути

Прямое следствие принятой схемы. Файлы пакета иммутабельны по построению (префикс содержит
`packageId`) — идеальный кандидат на `Cache-Control: immutable`. Но токен в префиксе пути меняет URL
при каждом заходе, и межсессионный кэш промахивается.

Внутри одной сессии кэш работает, а это и есть основная нагрузка — сотни мелких файлов на старте
курса. Предложение: смириться в v1 и назвать явно, чтобы не выглядело недосмотром. Альтернатива
(cookie `SameSite=None; Secure` на путь контента, стабильный URL) не работает в dev по http.

### Жизненный цикл пакета

- Перезалив вырывает файлы из-под ног у того, кто сейчас проходит. Новая версия = новый префикс,
  старая живёт, пока на ней есть незавершённые попытки. Связано с открытым вопросом 2 выше.
- Провалившаяся распаковка оставляет частично залитые объекты → cleanup по `status='failed'` и
  сверка «объекты в бакете без строки в инвентаре». Ещё один аргумент за пагинацию `listObjects`.

### `kind: 'file'` — взять в v1

PDF/видео/ссылка как «курс» с отметкой «ознакомлен» — почти бесплатно поверх той же инфраструктуры
(инвентарь, прокси, назначения), но не требует SCORM-контента, которого на старте может не быть.
Это то, чем модуль полезен в первый день, а не после того, как методисты соберут первый пакет.

### Не забыть

- **i18n** — модуль сразу заводит `locales/ru.json` + `en.json` и ключи `hr-learning:...`, как
  `module-hr-poll`. В остальном тексте плана не отражено.
- **Токен попадает в access-логи Fastify** — редактировать префикс пути в логгере.
- **Эталонный SCORM-пакет как фикстура** — иначе `05` нечем проверять.

## Вне scope v1

xAPI и LRS, cmi5, сертификаты о прохождении, свой конструктор курсов и тесты вне SCORM, CDN и
presigned-режим раздачи, отдельный origin для контента, назначение курсов через `module-workflow`
(согласование обучения),
аналитика и дашборды по обучению, виджет «Мои курсы» и точка расширения `dashboard` под него,
модель прав (её нет во всём проекте — обучение живёт по общему правилу «залогинен = админка целиком»,
см. «Открытые вопросы»).

## Зависимости

| Пакет | Зачем | Тип |
|---|---|---|
| `@amplicada/platform-core` | storage, Document System, TaskScheduler, UI-кит | обязательная |
| `@amplicada/module-admin` | `registerComponent` / `registerToolbarAction` на карточке курса | обязательная |
| `@amplicada/module-hr` | назначение по подразделению/должности | **опциональная**, через extension point, не в `dependencies` |

Новые npm-пакеты (кандидаты, проверяются в своих подпланах): распаковка ZIP — стриминговая
(`unzipper`/`yauzl`, **не** `adm-zip`: он держит архив в памяти); `fast-xml-parser` для манифеста;
`scorm-again` как реализация SCORM-рантайма. Версии и API проверить перед фиксацией — здесь они не
подтверждены.

## Проверка (общая рамка)

Детальные чек-листы — в подпланах. Сквозной сценарий, которым закрывается модуль: залить реальный
SCORM 1.2 пакет с видео → дождаться `ready` → назначить пользователю → пройти наполовину, закрыть
вкладку → зайти снова и убедиться, что продолжается с того же места → домотать до конца → увидеть
«Пройдено» в каталоге и у админа. Отдельно — перемотка видео (должен уходить `206`, а не полный файл)
и попытка открыть контент чужого/неназначенного курса напрямую по URL.
