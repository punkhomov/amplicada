# 05 — SCORM-рантайм и прогресс

> **Сделано 2026-08-11** вместе с `03`.
> Три расхождения с написанным ниже, все в пользу простоты:
> - **SCORM 2004 сделан сразу**, а не «вне v1»: `scorm-again` умеет обе модели, разбор читал 2004
>   изначально. Вторая таблица соответствий — в `cmi-normalize.ts`. Sequencing при этом **не**
>   сделан: запускается одна точка входа.
> - **Колонка «итог на начало сессии» не нужна.** Накопление `total_time` делает рантайм: получает
>   прошлый итог при запуске, прибавляет сессию, присылает готовый. Мы только читаем.
> - **Отдельного `finish` нет.** `scorm-again` шлёт завершающий коммит на тот же `lmsCommitUrl`
>   (через `sendBeacon`), различать его незачем — статус виден в самом `cmi`.
>
> Не сделано: ручной override как действие админа, лимит на `suspend_data`, UI для потерянного lease.

Сделать так, чтобы курс видел `window.API`, его вызовы доезжали до нашей БД, а из сырого `cmi`
получался осмысленный статус прохождения. Зависит от `03` (инжект, токен) и `04` (`attempts`).

## Почему рантайм внутри iframe, а не в родителе

Типовая схема (и исходный обзор) кладут `scorm-again` в родительское приложение, а курс достаёт
`window.parent.API`. У нас так нельзя: iframe с opaque origin не имеет доступа к родителю.

Обойти через `postMessage` не получится по фундаментальной причине: **SCORM API синхронный**.
`LMSGetValue('cmi.core.lesson_status')` обязан вернуть строку немедленно, а `postMessage`
асинхронен — честной реализации не существует, только подделки с фиктивными значениями.

Решение снимает проблему целиком: рантайм живёт **внутри** iframe, вместе с курсом.

```html
<!-- инжектится в entry-HTML на лету (03) -->
<script>window.__LEARNING__ = { token: "...", attemptId: "...", cmi: { /* стартовое состояние */ } };</script>
<script src="/api/learning/runtime/scorm-again.js"></script>
<script>/* конфигурация: подставить cmi, включить autocommit, задать lmsCommitUrl */</script>
```

- **Чтение синхронно** — `LMSGetValue` отвечает из локальной копии `cmi`, которую мы вшили в страницу
  при отдаче. Никаких запросов.
- **Запись асинхронна** — `LMSSetValue` меняет локальную копию, `LMSCommit`/autocommit отправляет её
  на наш API. Ровно так `scorm-again` и устроен (`lmsCommitUrl` + `autocommit`), это его штатный режим.
- Файл рантайма отдаётся **нашим** роутом, а не из пакета: он часть платформы, а не контента.

Родителю через `postMessage` уходят только UI-события: процент/статус для шапки плеера, «курс
завершён», «закрыть». Родитель им доверяет ровно настолько, насколько нужно для отрисовки — источник
правды всё равно БД.

## Эндпоинты рантайма

Отдельный скоуп, авторизация тем же токеном, что и контент (`03`), **без сессии**:

| Метод | Что делает |
|---|---|
| `POST /api/learning/runtime/commit` | Тело — `cmi` целиком. Обновляет `attempts.cmi`, нормализует статус, двигает `updated_at` |
| `POST /api/learning/runtime/finish` | `LMSFinish`: тот же commit + закрытие сессии |
| `POST /api/learning/runtime/acknowledge` | Для `kind='file'`: «ознакомлен», `completion='completed'` |
| `GET /api/learning/runtime/scorm-again.js` | Файл рантайма |

**`attemptId` берётся только из токена**, никогда из тела запроса — иначе учащийся закрывал бы чужие
попытки.

## Одна попытка — одна активная сессия

Две открытые вкладки коммитят одну попытку и перетирают `cmi` целиком, last-write-wins: прогресс
теряется молча. Классический LMS-баг, вылезает у людей, а не в тестах.

Lease без блокировок в БД:

1. Открытие плеера выпускает `sessionId` (uuid), пишет его в `attempts.session_id` и вшивает в токен.
2. `commit` принимается, только если `session_id` в токене совпадает с текущим в строке.
3. Вторая вкладка при открытии перевыпускает `session_id` — первая начинает получать `409` и
   показывает «Курс открыт в другом окне», без попыток дописать своё поверх.

## Нормализация `cmi` в прогресс

Сырое состояние остаётся в `attempts.cmi` как есть — оно источник правды и его нельзя терять. Рядом
пишутся производные поля, по которым строятся списки и отчёты:

| `cmi.core.lesson_status` | `completion` | `success` |
|---|---|---|
| `passed` | `completed` | `passed` |
| `completed` | `completed` | — |
| `failed` | `completed` | `failed` |
| `incomplete`, `browsed` | `in_progress` | — |
| `not attempted`, пусто | `not_started` | — |

- `score` ← `cmi.core.score.raw`, строкой произвольного вида: парсить терпимо, при мусоре оставлять
  `null`, а не ронять commit.
- `total_time_seconds` — **накапливает LMS, а не курс.** По спецификации контент выставляет
  `cmi.core.session_time` (длительность текущей сессии целиком, не дельту), а `total_time`
  пересчитывается как «итог на начало сессии + session_time». Наивное
  `total += session_time` на каждом автокоммите задваивает время в разы.
  Формат — CMITimespan `HHHH:MM:SS.SS`, часов до четырёх знаков.

  **Следствие для схемы, которого не было в `04`:** чтобы так считать, нужен «итог на начало
  сессии». Либо колонка `session_base_time_seconds` рядом с `session_id` (снимок при выдаче lease),
  либо хранить его внутри токена сессии. Решить при реализации — колонка добавляется миграцией
  `0001`.
- `completed_at` проставляется при первом переходе в `completed` и больше не двигается.

**Ручной override.** Пакеты, которые никогда не шлют финальный статус, — норма, а не исключение
(кривая сборка, курс без явного завершения). Действие админа «Отметить пройденным» ставит
`manual_override = true` и `completion='completed'`, не трогая `cmi`. Без этого поддержка будет
ходить в БД руками.

## Границы, которые надо знать

**SCORM клиент-авторитетен по спецификации.** `LMSSetValue('cmi.core.score.raw', '100')` из консоли —
это норма протокола, а не дыра в нашей реализации. Валидировать «правильность» присланного `cmi` мы
не можем: только он и есть результат. Практический вывод: **нужны доверенные баллы — тест делается
на нашей стороне** (как в `module-hr-poll`), а не внутри пакета. Записать это в UI отчётности, чтобы
цифры не читали как проверенные.

**Лимит на `suspend_data`.** Курсы складывают туда всё своё состояние. Без ограничения один пакет
будет слать мегабайты на каждом автокоммите. Спека SCORM 1.2 обещает 4096 символов, но реальные
пакеты пишут больше — рубить по спеке нельзя, ограничить сверху (десятки-сотни КБ) нужно, при
превышении — `413` и запись в лог, а не молчаливое обрезание.

## Проверка

1. Реальный SCORM 1.2 пакет: пройти наполовину, закрыть вкладку, зайти снова — курс продолжается с
   того же места (`cmi.core.entry='resume'`, `suspend_data` доехал).
2. Домотать до конца → `completion='completed'`, в каталоге курс уходит в «Пройдено».
3. Открыть тот же курс во второй вкладке → первая при следующем коммите получает `409` и говорит об
   этом, прогресс второй не затирается первой.
4. Подставить чужой `attemptId` в тело commit → не влияет ни на что (берётся из токена).
5. Пакет, который не шлёт финальный статус → админ отмечает вручную, `manual_override=true`, в
   отчётности видно, что статус проставлен руками.
6. `suspend_data` в мегабайт → `413`, попытка не испорчена.

1. ~~**`scorm-again` — API не проверен.**~~ Проверен: `loadFromJSON` принимает `{ cmi: { ... } }` в
   том же виде, в каком приходит коммит, и обязан вызываться **до** `Initialize`; `lmsCommitUrl` +
   `autocommitSeconds` работают как заявлено; `dist/scorm-again.min.js` — самодостаточный IIFE,
   кладущий `window.Scorm12API` и `window.Scorm2004API`, и годится для отдачи одним файлом
   (`require.resolve('scorm-again/min')` — у пакета карта экспортов, и по условию `import` она отдаёт
   ESM). Свой API писать не пришлось.
2. ~~**SCORM 2004** — вне v1~~ — сделан сразу, см. врезку сверху.
3. **Что считать «в процессе» для `kind='file'`** — открыл ≠ прочитал. Сделано как и предполагалось:
   `not_started` → `completed` по кнопке «Ознакомлен», без промежуточного состояния.
4. **Sequencing SCORM 2004** — новый вопрос, которого в плане не было. Запускается одна точка входа;

   (`settings.sequencing` с деревом активностей), дерево и правила есть у нашего разбора —
   не соединено.
