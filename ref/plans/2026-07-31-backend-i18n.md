# План: backend i18n — перевод ошибок

**Статус (2026-07-31):** Фаза A реализована, но **сузили скоуп по факту** — только `platform-core`, без Фазы B (перевод ошибок). Модули (`module-hr`, `module-auth-password` и т.д.) пока не декларируют `locales.backend` — инфраструктура готова их принять, когда дойдёт очередь; сейчас `request.t` существует на каждом запросе, но им никто не пользуется.

Фаза 5 из `ref/plans/2026-07-13-i18n.md` ("Backend i18n — опционально, отдельным планом"), детализирована здесь.

## Текущая проблема

- Backend возвращает ошибки как сырую, уже отформатированную прозу (`{ error: error.message }`) — русский и местами английский вперемешку, без понятия "код ошибки" отдельно от текста.
- Три независимых per-module `setErrorHandler` (`module-admin`, `module-hr-poll`, `module-workflow`) + дефолтный Fastify-хендлер (`module-auth-password`, `module-hr-request` — свой) — каждый форвардит `error.message` как есть, без учёта языка клиента.
- `Accept-Language` нигде не читается.

## Решение

Два независимых слоя:

**(A) Инфраструктура** — request-scoped `t()` на бэкенде через `i18next.getFixedT(lang)`, собранные из модулей `locales/backend/*.json` (зеркало фронтенд-механизма), Fastify-хук, декорирующий `request.t`. Этот слой самодостаточен и стоит собрать независимо от охвата ошибок.

**(B) Перевод конкретных ошибок** — не "весь бэкенд разом". Ошибки в проекте делятся на два принципиально разных случая, и это выяснилось только при чтении реальных call site'ов (см. таблицу охвата ниже):

1. **Ошибки со стабильным статическим текстом** (класс ошибки ⇒ одно и то же сообщение всегда, без дефолтного текста, переопределяемого на вызове) — `error.name` уже работает как код без единой правки call site'ов, достаточно таблицы переводов.
2. **Ошибки с динамически интерполированным текстом** (id/label/count вшиты в строку прямо в момент `throw`) — таких большинство в `module-workflow/services/engine.ts` (~40 мест). Для них `error.name`-подход **бесполезен**: `error.name === 'WorkflowNotFoundError'` для любого из полутора десятков разных `throw new WorkflowNotFoundError(...)`, но текст каждый раз свой, готового шаблона с плейсхолдерами не существует — перевод потребовал бы сначала переписать сами throw-сайты на `throw new WorkflowNotFoundError('workflow_not_found', { workflowCode })`, то есть отдельный, более инвазивный рефакторинг ~40 мест в одном файле. **Вне скоупа этого плана.**

## Ключевое архитектурное решение: request-scoped `t()`, не глобальный instance

На фронтенде `i18n` — один глобальный инстанс с мутируемым текущим языком (`changeLanguage()`), это безопасно: один браузерный таб = один пользователь. На бэкенде один Node-процесс обслуживает много параллельных запросов с потенциально разными `Accept-Language` — глобальный мутируемый язык был бы гонкой (язык запроса A мог бы просочиться в `t()`-вызовы запроса B).

`i18next` для этого специально даёт `i18n.getFixedT(lang)` — функция `t`, привязанная к конкретному языку, безопасная для использования per-request без мутации глобального состояния. Инстанс `i18next`, созданный на бэкенде, после загрузки ресурсов **больше никогда не мутируется** — только читается через `getFixedT`.

### Ключевые интерфейсы

#### backend/lib/i18n.ts

```ts
// packages/platform-core/src/backend/lib/i18n.ts
import i18next, { type TFunction } from 'i18next';

export type LocaleResources = Record<string, Record<string, Record<string, string>>>;

let i18n: typeof i18next | null = null;

export async function createI18n(resources: LocaleResources): Promise<typeof i18next> {
  const firstLang = Object.keys(resources)[0];
  const instance = i18next.createInstance();
  await instance.init({
    fallbackLng: 'ru',
    resources,
    ns: firstLang ? Object.keys(resources[firstLang]) : [],
    defaultNS: 'core',
    interpolation: { escapeValue: false },
  });
  i18n = instance;
  return instance;
}

/** lang — уже разобранный из Accept-Language код языка ('ru' | 'en'), см. resolveLanguage(). */
export function getFixedT(lang: string): TFunction {
  if (!i18n) throw new Error('createI18n() must be called before getFixedT()');
  return i18n.getFixedT(lang);
}

const SUPPORTED = ['ru', 'en'];

/** Простейший разбор Accept-Language: берёт первый поддерживаемый базовый язык ('ru-RU' -> 'ru'), иначе fallback. */
export function resolveLanguage(acceptLanguage: string | undefined): string {
  if (!acceptLanguage) return 'ru';
  const tags = acceptLanguage.split(',').map(t => t.split(';')[0].trim().split('-')[0].toLowerCase());
  return tags.find(t => SUPPORTED.includes(t)) ?? 'ru';
}
```

Почему `i18next.createInstance()`, а не голый модульный singleton, как на фронтенде: на бэкенде тестовые прогоны/несколько `createApp()` в одном процессе (например в тестах) не должны делить состояние — на фронтенде это неважно (один инстанс на вкладку), на бэкенде — важно.

#### FastifyRequest.t — type augmentation

```ts
// packages/platform-core/src/backend/types/fastify.d.ts
import 'fastify';
import type { TFunction } from 'i18next';

declare module 'fastify' {
  interface FastifyRequest {
    t: TFunction;
  }
}
```

(Паттерн 1:1 повторяет уже существующий `packages/platform-core/src/backend/session.d.ts`.)

#### app.ts — сбор locales + хук

```ts
// packages/platform-core/src/backend/app.ts, внутри bootstrap(), до регистрации routes

const resources: LocaleResources = {};
for (const mod of modules) {
  if (mod.locales?.backend) {
    for (const [lang, strings] of Object.entries(mod.locales.backend)) {
      resources[lang] ??= {};
      resources[lang][mod.id] = strings;
    }
  }
}
for (const [lang, strings] of Object.entries(coreLocales)) {
  resources[lang] ??= {};
  resources[lang].core = strings;
}
await createI18n(resources);

app.addHook('onRequest', async request => {
  request.t = getFixedT(resolveLanguage(request.headers['accept-language']));
});
```

#### BackendModule — новое поле locales

```ts
// packages/platform-core/src/contracts/backend/module.ts
export interface BackendModule {
  id: string;
  name: string;
  version: string;
  dependencies?: string[];
  locales?: {
    backend?: Record<string, Record<string, string>>; // { "ru": { "key": "value" } }
  };
  setup(context: BackendSetupContext, app?: FastifyInstance): void | Promise<void>;
  start?(): void | Promise<void>;
  stop?(): void | Promise<void>;
}
```

#### setErrorHandler — пример на module-hr (охват типа 1, статический текст)

```ts
// packages/module-hr/... где сейчас generic-фолбэк в module-admin ловит error.statusCode ?? 500
fastify.setErrorHandler((err, request, reply) => {
  const error = err as Error & { statusCode?: number };
  const statusCode = error.statusCode ?? 500;
  reply.code(statusCode).send({ error: request.t(`hr:${error.name}`, { defaultValue: error.message }) });
});
```

`defaultValue` — встроенный механизм i18next: если ключ `hr:VersionOverlapError` не найден в загруженных ресурсах, `t()` просто возвращает `error.message` как сегодня. Значит внедрение **не ломает** ни одну необработанную ошибку — они продолжают отдавать текущий (нередко русский) текст без перевода, пока для них не появится запись в locale-файле.
