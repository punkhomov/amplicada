# workflow — детерминированность условий Gateway и параллельные ветки

Два независимых открытых вопроса по движку `module-workflow`, всплывших при обсуждении текущей
реализации. Изначально собран только контекст без решения; 2026-07-22 оба вопроса решены —
Вопрос 1 реализован здесь же (минимальный фикс), Вопрос 2 выделен в отдельный план
[2026-07-22-workflow-parallel-gateway.md](2026-07-22-workflow-parallel-gateway.md) — слишком большой
объём, чтобы жить в одном файле с Вопросом 1.

## Вопрос 1 — порядок вычисления условий Gateway

### Проблема

`WorkflowEngine.pickGatewayEdge()` (`packages/module-workflow/src/backend/services/engine.ts:270-279`)
выбирает первое ребро, чьё условие совпало, перебирая исходящие рёбра gateway по порядку массива
`config.edges`:

```ts
private pickGatewayEdge(config: WorkflowVersionConfig, nodeId: string, ctx: DelegateContext): WorkflowEdge {
  const edges = config.edges.filter(e => e.source === nodeId);
  for (const edge of edges) {
    if (edge.isDefault || !edge.condition) continue;
    if (evaluateCondition(edge.condition, ctx)) return edge;
  }
  const fallback = edges.find(e => e.isDefault);
  if (!fallback) throw new WorkflowValidationError([`Gateway "${nodeId}": ни одно условие не совпало и нет default-ребра`]);
  return fallback;
}
```

Если условия на соседних рёбрах не строго взаимоисключающие (например `payload.a > 10` и
`payload.a > 100` вместо аккуратно разбитых на диапазоны `payload.a > 10 && payload.a <= 100` /
`payload.a > 100`), результат зависит от порядка рёбер в массиве — то есть от того, в каком порядке
админ их нарисовал. Ошибиться легко, а на канвасе это никак не видно.

### Контекст / текущая реализация

**Чем определяется порядок `config.edges`:**
- `flowToConfig()` (`packages/module-workflow/src/frontend/lib/graph-mapping.ts:118-127`) строит
  массив прямым `.map()` по React Flow edges-состоянию — порядок сохраняется как есть, без сортировки.
- Новое ребро добавляется через `onConnect` → `addEdge` (`@xyflow/react`), под капотом —
  `edges.concat(edge)`, всегда в конец массива (`workflow-editor-page.tsx:91-96`).
- Редактирование условия существующего ребра (`onEdgePatch`, `workflow-editor-page.tsx:140-152`) —
  `.map()`, позицию не меняет.
- Reconnect-функциональности (перетащить конец ребра на другой узел) в редакторе нет вообще — ноль
  упоминаний `onReconnect` в пакете. Изменить порядок можно только удалив ребро и нарисовав заново
  (попадёт в конец).

Итог: порядок вычисления = порядок рисования рёбер на канвасе, персистится через публикацию версии
как есть.

**Видимость порядка в UI: отсутствует.**
- `properties-panel.tsx` → `EdgeForm` показывает свойства только одного выбранного ребра: label,
  `isDefault`-переключатель, `ConditionBuilder` (плоский AND) или read-only JSON для сложных условий.
- Нет ни индекса/приоритета, ни списка «все исходящие рёбра gateway по порядку», ни drag-to-reorder.
- Единственное визуальное упорядочивание — пространственное положение рёбер на канвасе React Flow,
  которое не гарантированно соответствует порядку массива и нигде не документировано как значащее.

**Валидация** (`packages/module-workflow/src/backend/validation.ts:141-153`) проверяет только:
- ровно одно `isDefault`-ребро;
- у каждого не-default ребра есть структурно валидный `condition` (`validateConditionRule` — whitelist
  операторов JSONLogic, рекурсивно, без семантики).

Проверки пересечения условий между соседними рёбрами, исчерпывающего покрытия сверх обязательного
default, или предупреждения о неоднозначном порядке — нет.

**Документация:** формула «первое совпавшее, иначе default» зафиксирована как исходный дизайн в
`ref/plans/2026-07-14-workflow/02-engine-and-versioning.md:91-92` — совпадает с текущим кодом. Больше
нигде (ADR, последующие планы) риск неоднозначности порядка не обсуждался — это было осознанное
решение с самого начала, но его последствия для UX редактора не прорабатывались.

### Решение (2026-07-22)

Минимальный фикс — сделать порядок вычисления **видимым**, не меняя семантику «первое совпавшее,
иначе default» и не добавляя детекцию пересечения условий (для произвольного JSONLogic это в общем
случае неразрешимо; отклонено как отдельная задача, не часть этого фикса). Реордер рёбер (drag or
up/down) тоже не добавлен — по-прежнему только удалить и перерисовать (попадёт в конец); если
неудобство станет ощутимым на практике, это отдельная небольшая доработка поверх того же
`withGatewayEdgeOrder`.

Реализовано:

- `graph-mapping.ts`: `withGatewayEdgeOrder(edges, nodes)` — чисто отображательная функция, вычисляет
  порядковый номер (1, 2, 3…) для каждого не-default ребра gateway в том же порядке, в котором его
  проходит `pickGatewayEdge` (по позиции в массиве, default-рёбра не считаются — они и так всегда
  проверяются последними). Возвращает новый массив, не мутирует `edges`-state.
- `workflow-editor-page.tsx`: `renderEdges = useMemo(() => withGatewayEdgeOrder(edges, nodes), ...)`
  передаётся в `<ReactFlow edges={renderEdges}>` — **только** для рендера канваса. `edges`-state
  (source of truth для `flowToConfig`/`onEdgePatch`/`PropertiesPanel`) не тронут: номер не попадёт
  ни в `WorkflowEdge.label`, ни в публикуемый конфиг.

Итог: на канвасе перед подписью каждого не-default исходящего ребра gateway теперь виден номер
приоритета («1. amount > 100», «2. amount > 10», …) — админ сразу видит порядок вычисления и может
перерисовать граф так, чтобы он совпадал с намерением, без обращения к API или логам.

## Вопрос 2 — параллельная работа над процессом (AND/OR)

### Проблема

Нужно понять, поддерживает ли текущий движок сценарии вида «заявка продолжится, если её одобрят
ВСЕ подчинённые текущего сотрудника (И)» либо «если её одобрит ХОТЯ БЫ ОДИН подчинённый (ИЛИ)».

### Контекст / текущая реализация

Модель движка целиком построена вокруг одного текущего узла на инстанс процесса — параллелизма нет
ни на одном уровне:

- `NodeType` (`packages/module-workflow/src/contracts/graph.ts:1`) —
  `'start' | 'userTask' | 'gateway' | 'serviceTask' | 'asyncTask' | 'end'`. Нет
  `parallelGateway`/`joinGateway`/inclusive-варианта. `GatewayNode` не содержит собственных полей —
  вся ветвящаяся логика на рёбрах, `pickGatewayEdge` всегда возвращает ровно одно ребро.
- `process_instances.current_state` (`packages/module-workflow/src/backend/schemas/process-instances.ts:11`)
  — одиночный `varchar`, не массив/jsonb. `advance()` водит один `current`-узел через граф, `settle()`
  пишет одно значение `currentState` одним `UPDATE`.
- `executeAction()` (`packages/module-workflow/src/backend/services/engine.ts:176-179`) при
  выполнении действия завершает ВСЕ pending-задачи инстанса одним
  `UPDATE ... WHERE processInstanceId=... AND status='pending'` — без `taskId`, рассчитано на то,
  что pending-задача ровно одна.
- `loadPendingTask()` (`engine.ts:225-233`) — явный `.limit(1)`, возвращает одну задачу, контракт
  API singular.
- `workflow_tasks` (`packages/module-workflow/src/backend/schemas/workflow-tasks.ts`) — нет
  уникального/частичного индекса, запрещающего несколько pending-задач на инстанс. Инвариант «одна
  pending-задача» держится только поведением движка (один `settle()` = одна вставка), не
  ограничением БД.
- `AssigneeProvider.resolve()` (`packages/module-workflow/src/contracts/registry.ts:16-18`)
  возвращает `Promise<string>` — один пользователь. Фан-аута «на каждого резолвленного пользователя
  — своя задача» нигде нет.

**Что есть в module-hr/module-hr-request как приближение** (всё — последовательное, не
параллельное):
- `fixedAssigneeProvider` (`packages/module-hr/src/backend/workflow-delegates.ts`) резолвит одного
  захардкоженного пользователя; комментарий в коде явно откладывает реальный org-chart-делегат
  «руководитель» — в `hr_user_profile` пока нет поля `managerId`.
- Пример графа согласования обучения (`ref/plans/2026-07-18-hr-requests.md:211-225`): Start →
  согласование у руководителя → Gateway по `cost` → согласование HR (одна из двух веток) → End —
  строго последовательная цепочка одного согласующего за шаг.

**Что зафиксировано в документации как задел, но не реализовано и не спроектировано:**
- Единственное упоминание — исходном обсуждении, обоснование
  выноса `workflow_tasks` в отдельную таблицу: «...плюс задел под будущие параллельные шаги
  (несколько task на одно состояние)» — имя/форма таблицы выбраны с оглядкой на возможное будущее,
  но это не спроектированная функциональность.
- Ни в одном плане, ADR или исходном ТЗ (`ref/plans/2026-07-14-workflow/out-00-overview.md`)
  параллельные/inclusive-гейтвеи или multi-approver паттерн не упоминаются вообще. (Тогда в этот
  список входил и сводный `ref/plans/2026-07-13-future-plans.md` — он удалён 2026-08-08 как
  разошедшийся с реальностью, всё его содержимое покрыто ADR и профильными планами.)
