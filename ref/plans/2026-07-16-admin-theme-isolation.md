# Изоляция темы админки от кастомизации портала

## Текущая проблема

1. **Единое CSS-пространство** — `base.css` в `platform-core` определяет глобальные CSS-переменные (`:root`, `.dark`) для `--primary`, `--radius`, `--background` и т.д.

2. **Все модули используют одни переменные** — admin layout (`admin-layout.tsx:54-104`) использует Tailwind-классы `bg-background`, `text-foreground`, `border-border`, которые ссылаются на эти глобальные переменные.

3. **Кастомизация через `index.css`** — клиент переопределяет CSS-переменные после импорта `base.css`:
   ```css
   @import "@amplicada/platform-core/frontend/styles/base.css";
   :root {
     --primary: oklch(0.5 0.2 250);   /* бренд клиента */
     --radius: 0rem;                   /* без скруглений */
   }
   ```

4. **Нет изоляции** — кастомные переменные apply ко всему приложению, включая админку.

5. **Требование** — админка должна всегда быть "как есть", независимо от бренд-кастомизации клиента.

## Решение

Открыто. Рассматриваемые варианты:

### Вариант 1: CSS-скейпинг через `.admin-root`

- Админ layout добавляет `className="admin-root"` на корневой `div`
- CSS в admin-модуле переопределяет переменные внутри `.admin-root` обратно к дефолтам
- Портал использует кастомные переменные, админка — дефолтные

**Плюсы**: одно приложение,简单实现
**Минусы**: хрупко — нужно синхронизировать переменные, CSS-override может ломаться

### Вариант 2: Разделение приложений

- Два SPA: `apps/web` (портал) и `apps/admin` (админка)
- Каждый свой `index.css` со своими переменными

**Плюсы**: полная изоляция, чисто
**Минусы**: два приложения, два билда, сложнее деплой, сессии/авторизация

### Вариант 3: Admin namespace

- Админка определяет собственные CSS-переменные `--admin-primary`, `--admin-radius`
- Компоненты админки используют только `--admin-*`

**Плюсы**: полная изоляция
**Минусы**: дублирование переменных, admin-компоненты не могут использовать通用 UI

## Статус

Решение пока не принято. Нужно определиться с подходом перед реализацией.
