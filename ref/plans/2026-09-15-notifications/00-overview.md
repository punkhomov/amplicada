# Уведомления: ядро маршрутизирует, каналы доставляют

Зонтичная папка для фундамента уведомлений: outbox-сервис в ядре, канальные модули (почта первым),
админ-видимость доставок. Это разблокирует расширение `module-auth-password` (регистрация, сброс
пароля, второй фактор), уведомления workflow и learning, а также висящий `task.alert`.

Нумерация файлов = **порядок реализации**.

## Проблема

1. **Канала уведомлений в проекте нет вообще.** Ни SMTP-библиотеки, ни сервиса, ни таблиц. Это
   зафиксировано ещё в `plans/2026-07-14-task-scheduler/04-reliability.md` («Канала уведомлений
   в проекте нет») и в `plans/2026-08-08-module-learning/07-assignment-reporting.md`.
2. `task.alert` эмитится при падении задачи, но слушатель только пишет в лог — доставки нет.
3. `module-auth-password` умеет только логин: без почты нельзя сделать ни подтверждение регистрации,
   ни сброс пароля, ни email-OTP. Это блокер для следующего этапа развития авторизации.
4. В core-тасках нет ретраев (одна попытка, см. `plans/2026-07-14-task-scheduler/`), значит
   надёжная доставка требует собственного механизма — outbox.

## Решение

**Ядро владеет маршрутизацией и надёжностью, модули — транспортом и адресными книгами.**

- Core-сервис `notification` (токен `notification`, обязательный по ADR-02) принимает
  `{ userId, kind, subject, body, html?, channel? }`, резолвит адрес через зарегистрированный канал
  и пишет строку в `core.notification_outbox`.
- **Адресная книга живёт в канальном модуле.** `module-notification-email` знает email пользователя
  (`notification_email.user_email`, редактируется в карточке пользователя), `module-notification-sms`
  в будущем — телефон. Отправитель (auth, workflow, learning) не знает ни адреса, ни канала: только
  `userId` и `kind`. Поэтому `module-auth-password` не зависит от почтового модуля.
- Доставка: eager-попытка в процессе, который вызвал `send()`; периодический диспетчер на
  `isWorkerRole()` добирает pending/failed с бэкоффом и чинит зависшие `sending` (краш).
- Письма — plain text + опциональный HTML, оба варианта рендерит отправитель; ядро хранит снапшот
  (при ретрае контент не перерендеривается).
- Админ-лог доставок с ручным «Повторить» — без него ретраи слепые.

## Что дальше (отдельными планами, не в этой папке)

Порядок после фундамента — по нарастанию:

1. **`module-auth-password`: регистрация и per-user состояние.** Режим регистрации настраивается
   (`disabled | invite | open | allowlist`), email-адрес уже даёт почтовый модуль, создание
   пользователя — через `document-runtime.create('user', …)`. Флаги (`email_verified_at`,
   `disabled_at`, `must_change_password`) — в БД, не в env. Env — только node-level.
2. **Сброс пароля.** Токены в отдельной таблице (hash + expiry + single-use), ответ всегда 200
   (без user enumeration), ссылка — через `notification.send`. Плюс rate-limit на публичные auth-роуты
   (в проекте его нет вообще).
3. **Второй фактор.** Core extension point `auth:challenge` + pending-login состояние в core
   `auth-service`; `module-auth-totp` хранит секреты/recovery-коды. Email-OTP — вторым, поверх
   notification.
4. **Долги авторизации**: инвалидация всех сессий при смене пароля (индекс user→sessions или
   sessionVersion), роли/получатели для `task.alert` (сейчас ролей нет — алерт пока некому слать).

## Сквозные принципы

- **Outbox, а не прямой вызов SMTP из обработчика.** Хендлер пишет строку и возвращает ответ; сеть
  и ретраи — забота диспетчера.
- **Канал владеет адресом.** Ядро не знает, что такое email; `resolveAddress` — обязанность канала.
- **Не всё через документы.** Outbox — обычная таблица со своим API и страницей; документная модель
  тут не нужна (см. сквозной принцип `plans/2026-08-05-document-model/00-overview.md`).
- **ADR-04 обязателен**: решение меняет архитектуру (новый core-сервис, граница «транспорт в модулях»),
  фиксируется до/вместе с реализацией — см. [04](./04-dev-infra-and-adr.md).
