# Провайдеры поиска документов

Первый работающий вариант — PostgreSQL FTS по колонкам списка (`packages/platform-core/src/backend/services/document-search.ts`). Он использует существующие JOIN и общие правила фильтрации, поэтому данные свежие сразу после записи. Цена — вычисление вектора на запросе без общего GIN-индекса. Требуется живой прогон и `EXPLAIN ANALYZE` на типичных и больших списках.

## Варианты

| Провайдер | Выигрыш | Цена |
|---|---|---|
| PostgreSQL напрямую (сейчас) | Не нужна новая инфраструктура, транзакционно актуальные данные | Сканирование и векторизация JOIN при каждом запросе |
| PostgreSQL с поисковой проекцией | GIN по отдельному `tsvector`, всё ещё одна БД | Таблица проекции, обновление при изменении каждого extension, миграция и бэкфилл |
| Внешний индекс (например OpenSearch/Meilisearch) | Масштабирование поиска, собственное ранжирование и анализаторы | Доставка изменений через outbox, задержка индексации, повторение фильтров/сортировки и контроль доступа |

## Граница для следующей итерации

Конфигурация должна выбирать один провайдер на тип документа с общим значением по умолчанию. Провайдер получает тип, строку поиска, описание доступных полей, дерево фильтров, сортировку и параметры страницы; возвращает упорядоченные ID, общее количество и при необходимости оценку релевантности. `DocumentRuntime` гидратирует ID для ответа списка. Экспорт должен обходить все страницы того же результата с той же семантикой. Выбор провайдера делается при создании приложения до первого запроса, а не в UI.

Это **не текущий контракт**: прежде нужно решить, какие фильтры и сортировки обязан поддерживать внешний индекс, как соблюдать видимость/soft-delete и что показывать до завершения индексации. Отдавать провайдеру только `SQL` или только массив всех совпавших ID нельзя: первое исключает внешние системы, второе ломает масштабируемую пагинацию. Фоновая синхронизация внешнего индекса должна иметь повторяемый бэкфилл и надёжную доставку изменений; локальный EventBus для этого недостаточен.

Данные и схема БД в текущем изменении не меняются, миграций нет. Для поисковой проекции позднее потребуется схемная миграция; для внешнего индекса — процедура бэкфилла. Разрыва формата пользовательских данных сейчас нет.
