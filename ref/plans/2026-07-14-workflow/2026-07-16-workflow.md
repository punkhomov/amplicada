# module-workflow — движок бизнес-процессов (BPM-Light)

Верхнеуровневый план. Детали реализации — в подпланах этой папки, разбитых по фазам. Исходное ТЗ,
из которого выросли решения ниже — [out-00-overview.md](out-00-overview.md) (черновик, писался
ИИ, не во всём финален — расхождения с этим документом ниже приоритетнее, см. `ref/README.md`).
История обсуждения и снятых развилок отражена в плане.

## Текущая проблема

1. Нет инфраструктуры для процессов, которые должны проходить через определённые этапы
   согласования (заявки, HR-процессы) — каждый такой процесс сейчас пришлось бы кодировать
   вручную, с нуля, для каждого нового кейса.
2. Набор статусов и переходов не должен быть зашит в код — бизнес-пользователи (админы) должны
   уметь проектировать процесс визуально, без разработчика.
3. Первый потребитель — HR (заявки, согласования), но заведомо не последний (в будущем — оценка
   персонала). Нужна инфраструктура, которая не завязана на HR-домен изнутри.
4. Нет visibility — нельзя посмотреть список процессов, историю переходов, кто на каком этапе
   завис.

## Решение

Добавить пакет `@amplicada/module-workflow`:
- Ядро (registry, интерпретатор графа, версионирование) **не знает ни об одном домене** — только
  плагинный реестр (`AssigneeProvider`/`ValidatorProvider`/`ServiceTaskProvider`), в который
  доменные модули (`module-hr` и далее) регистрируют свои делегаты
- Схема процесса (`nodes`/`edges`) — JSON-конфиг, версионируемый и immutable после публикации;
  активные заявки продолжают работать по старой версии
- Переход по графу — либо явное действие пользователя (`POST /actions/:action`), либо
  автоматическое ветвление по условию (Gateway, JSONLogic-подобный формат условия)
- Графический редактор (React Flow) — отдельная страница в самом модуле, публикует новую версию
- Отображение в админке — через уже существующий Document System (`DocumentPage.linkTemplate`),
  без бесплатного CRUD

## Архитектурный принцип: направление зависимости

**`module-workflow` не знает о существовании `module-hr`** (и любого другого доменного модуля).
Plugin Registry — точка расширения, которую движок объявляет и которой не интересуется, кто в неё
что положил; `module-hr` — потребитель, который зависит от `module-workflow`, чтобы туда что-то
зарегистрировать (по аналогии с ADR-02: producer/consumer через `contribute()`/`getAll()`, только
владелец точки расширения здесь не `platform-core`, а `module-workflow`).

```
platform-core → module-auth-password → module-workflow → module-hr
```

Это делает движок настолько же domain-agnostic, насколько был бы в `platform-core` — просто он
физически отдельный npm-пакет, а не часть core (решение — не городить абстракцию под
гипотетического второго потребителя типа module-assessment, которого пока нет; когда он появится,
перенос в core станет тривиальным рефактором, т.к. зависимостей переносить не придётся).

Проверяемый инвариант (по аналогии с `platform-core`/`module-admin` у task-scheduler): **ни один
файл в `packages/module-workflow/**` не должен импортировать что-либо из `packages/module-hr/**`**.
Обратное — можно.

Второе следствие того же принципа: и API, и admin-UI движка живут **внутри `module-workflow`**, не
в `module-admin` — модуль остаётся вертикальным срезом. (У task-scheduler это не так — его
admin-часть физически лежит в `module-admin`, что сам пользователь считает известной ошибкой,
которую поправят позже, но не в рамках этой сессии. Не повторять для `module-workflow`.)

## Модель графа

```typescript
type NodeType = 'start' | 'userTask' | 'gateway' | 'serviceTask' | 'end';
```

`serviceTask` — узел, отсутствующий в палитре исходного ТЗ (4.2.1: Start/User Task/End/Gateway),
но необходимый как node type для уже объявленного в ТЗ `ServiceTaskProvider` — иначе этому
делегату негде выполняться. Ведёт себя как Gateway (транзитный узел, не требует человека,
проходится синхронно в рамках того же запроса) — только не ветвит, а выполняет побочное действие
и идёт по единственному исходящему ребру. Решение принято в рамках этой разбивки (не отдельно
согласовано с пользователем) — минимальная добавка, т.к. интерпретатору всё равно нужна логика
"пройти транзитный узел автоматически" для Gateway.

```
Start ──> UserTask ──action:approve──> Gateway ──cond:amount>100000──> UserTask (CFO) ──> End
              │                          │
              └──action:reject──> End    └──default──> ServiceTask (notify) ──> End
```

- **UserTask** — ребро выбирает человек, вызывая именованный `action`. Создаёт `workflow_tasks`.
- **Gateway** — ребро выбирает движок автоматически, по JSONLogic-условию над `payload`/`context`.
  Обязателен `isDefault`-edge (fallback, иначе заявка может застрять).
- **ServiceTask** — движок автоматически выполняет `ServiceTaskProvider.execute(payload)`, дальше
  по единственному ребру.
- Ни Gateway, ни ServiceTask не становятся `process_instances.current_state` — это транзитные
  узлы, `current_state` — всегда UserTask/End.

## Зависимости (сводно)

| Пакет | Зачем | Новый? |
|-------|-------|--------|
| `json-logic-js` (или аналог) | Эвалуатор условий Gateway — маленькая библиотека, JSON-дерево, без eval/парсера выражений | Да |
| `reactflow` (React Flow) | Canvas графического редактора | Да |
| `zod` | Валидация JSON-конфига версии перед публикацией | Уже используется в других модулях (`shared/validators.ts`) |

xstate осознанно не используется — конфиг полностью динамический (JSONB из БД), типобезопасность
xstate не работает в этом сценарии; ручной интерпретатор проще и прозрачнее для дебага (ADR-02).

## Отложено (не в этой разбивке)

- **Портальный фронтенд** (инбокс, карточка заявки для рядового пользователя) — явно вне скоупа
  текущей итерации по словам пользователя, будущая работа
- **Эскалация зависших задач** (boundary timer event) и **периодический автозапуск процессов** —
  оба естественно лягут на уже существующий `context.tasks` (TaskScheduler) как консьюмер, когда
  понадобятся; не проектируются сейчас
- **Система прав** — авторизация действий в v1 жёстко ограничена "только assignee"; общая система
  прав уровня `platform-core` (упомянута пользователем как идея) — тема отдельного ADR в будущем
- **Параллельные шаги** (несколько `workflow_tasks` на одно состояние) — модель `workflow_tasks`
  уже это не исключает на уровне схемы, но интерпретатор в v1 не создаёт больше одной задачи на
  переход
