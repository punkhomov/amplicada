# Интеграция с корпоративной инфраструктурой

## Проблема

Корпоративные заказчики уже используют существующие HR-системы:

| Система | Тип | Хранение данных | Авторизация |
|---------|-----|-----------------|-------------|
| 1С: ЗУП / 1С: ERP | ERP | Собственная БД (MS SQL / PostgreSQL) | Собственная + LDAP |
| Active Directory | Каталог | LDAP / AD | Kerberos / NTLM / OAuth2 |
| Bitrix24 | CRM/Portal | MySQL | Собственная + OAuth2 |
| BMPSoft HCM | HCM | MS SQL | Собственная |
| WebSoft HCM | HCM | MS SQL / PostgreSQL | Собственная + LDAP |
| iSpring Learn / iSpring LMS | LMS | Облачная / On-premise | SAML2 / OAuth2 / LDAP |
| Битрикс24 (корп.) | Портал | MySQL | Собственная |

Задача — обеспечить бесшовную интеграцию без дублирования данных и с минимальными затратами на внедрение.

## Ключевые потоки данных

```text
┌─────────────────┐       ┌──────────────────┐       ┌─────────────────┐
│  HR-система     │──────▶│  Интеграционный  │──────▶│  Наша платформа │
│  (источник)     │◀──────│  слой (API)      │◀──────│  (клиент)       │
└─────────────────┘       └──────────────────┘       └─────────────────┘
                                    │
                          ┌─────────┴─────────┐
                          │                   │
                    Синхронизация       Авторизация
                    сотрудников         (SSO)
```

### Поток 1: Синхронизация справочников (direct sync)

- Список сотрудников (ФИО, должность, подразделение)
- Структура организации

### Поток 2: Результаты оценок (обратная синхронизация)

Рекомендуемый подход — **summary-only**. Не тянем сырые данные оценок обратно в HR-систему.

```text
Платформа (детальные результаты)
    │
    ▼
Summary Aggregator
    │
    ▼
┌───────────────────────────────────┐
│  Summary DTO                      │
│  {                                │
│    employeeId: "123",             │
│    assessmentId: "kpi-2024-q4",   │
│    completedAt: "2024-12-15",     │
│    score: 80,                     │
│    status: "completed",           │
│    metadata: {                    │
│      passed: true,                │
│      percentile: 72               │
│    }                              │
│  }                                │
└───────────────────────────────────┘
    │
    ▼
HR-система (хранит только summary)
```

Почему summary-only:
- HR-системы не умеют работать с нашими сущностями (вопросы, варианты, тайминги)
- Адаптер под каждую HR-систему — дорого и хрупко
- Достаточно знать: "сотрудник прошел оценку на 80%, КПД пройден"
- Детальные результаты хранятся только в нашей платформе

Альтернатива для заказчиков, которым нужны полные данные — выгрузка в отдельную БД/schema на стороне клиента.

### Поток 3: Авторизация (SSO)

- Единый вход через корпоративный провайдер
- Маппинг ролей AD/LDAP → роли платформы

### Поток 4: События

- Увольнение / перевод сотрудника
- Изменение должности
- Завершение тестирования

## Варианты интеграции

### Уровень 1: Минимальный (чтение данных)

**Подход:** REST API или файловый обмен (CSV/XML/JSON).

```text
HR-система → Экспорт → FTP/S3/API → Импорт в платформу
```

- Плюсы: быстро внедрить, не зависит от HR-системы
- Минусы: задержка синхронизации, ручная настройка

**Когда:** MVP, пилоты, заказчик не готов к глубокой интеграции.

---

### Уровень 2: Стандартный (Webhooks + API)

**Подход:** HR-система отправляет события, платформа потребляет.

```text
HR-система ──webhook──▶ Интеграционный слой ──▶ Платформа
                         │
                    Обработка событий
                    Маппинг данных
                    Валидация
```

- Плюсы: Near-real-time, стандартные протоколы
- Минусы: зависит от поддержки webhooks в HR-системе

**Когда:** 1С (через расширение), Bitrix24, облачные HCM.

---

### Уровень 3: Глубокий (Connector / Plugin)

**Подход:** Пишем плагин/расширение под конкретную HR-систему.

```text
┌─────────────────────────────────────────────┐
│  Платформа                                  │
│  ┌─────────────────────────────────────┐    │
│  │  Integration Module (npm-пакет)     │    │
│  │  ┌───────────┐  ┌───────────────┐  │    │
│  │  │ 1CConnector│  │ ADConnector   │  │    │
│  │  └───────────┘  └───────────────┘  │    │
│  └─────────────────────────────────────┘    │
└─────────────────────────────────────────────┘
```

- Плюсы: нативная интеграция, глубокая синхронизация
- Минусы: затраты на разработку под каждую систему

**Когда:** крупные заказчики, долгосрочные контракты.

---

### Уровень 4: Универсальный (standards-based)

**Подход:** Используем отраслевые стандарты.

| Стандарт | Назначение | Поддержка |
|----------|------------|-----------|
| SCIM 2.0 | Автоматическая синхронизация пользователей | AD, Okta, Azure AD |
| SAML 2.0 | SSO (Single Sign-On) | iSpring, большинство HCM |
| OAuth2 / OIDC | SSO + авторизация | Bitrix24, облачные сервисы |
| xAPI / Caliper | Логирование результатов обучения | LMS-системы |
| HR-XML | Обмен HR-данными | 1С, SAP |

- Плюсы: совместимость «из коробки» с многими системами
- Минусы: не все системы поддерживают все стандарты

**Когда:** стратегическое решение, долгосрочная платформа.

## Встраивание через iframe и корпоративный SSO

### Вариант A: Trusted Headers (рекомендуется для LAN)

Портал передаёт identity пользователя через HTTP-заголовки.

Требования:
- Портал должен уметь передавать заголовки (Bitrix, 1С, кастомные — обычно умеют)
- Reverse Proxy перед нами (nginx, HAProxy, IIS ARR)
- Доверие к прокси (IP-фильтрация или подписанные заголовки)

### Вариант B: Token Exchange (для DMZ / облачных порталов)

Портал обменивает свой токен на токен платформы через POST /api/auth/token-exchange.

### Вариант C: Kerberos Constrained Delegation (глубокая интеграция с AD)

- Плюсы: полностью прозрачно для пользователя
- Минусы: требует настройки AD (SPN, delegation), сложность в внедрении

### Рекомендация

| Среда | Подход |
|-------|--------|
| Чистый LAN + AD | Вариант C (Kerberos) или A (Trusted Headers) |
| DMZ, портал в облаке | Вариант B (Token Exchange) |
| Гибрид (Bitrix в LAN, плеер в DMZ) | Вариант A + reverse proxy |
| Нет AD, только логин/пароль | Вариант B (Token Exchange) |

### Безопасность iframe

```text
1. Content-Security-Policy: frame-ancestors
   → разрешаем iframe ТОЛЬКО с доверенных доменов
2. SameSite cookies
   → cookie не отправляется при cross-origin
3. X-Frame-Options: ALLOW-FROM <portal>
   → legacy защита
4. Token lifetime ≤ 5 мин
   → одноразовый токен для iframe
5. Validate Referer/Origin
   → на бэкенде проверяем откуда пришёл запрос
```

## Рекомендуемая стратегия

```text
┌──────────────────────────────────────────────────────┐
│                    Платформа                         │
│                                                      │
│  ┌──────────────────────────────────────────────┐    │
│  │          Integration Abstraction Layer        │    │
│  │                                               │    │
│  │   ┌─────────┐ ┌─────────┐ ┌──────────────┐  │    │
│  │   │ SCIM    │ │ SAML/   │ │ Webhook      │  │    │
│  │   │ Connector│ │ OIDC    │ │ Consumer     │  │    │
│  │   └─────────┘ └─────────┘ └──────────────┘  │    │
│  └──────────────────────────────────────────────┘    │
│                        │                             │
│                  Feature Modules                     │
│   (integrations-1c, integrations-ad, etc.)           │
└──────────────────────────────────────────────────────┘
```

1. **Core** предоставляет Integration Abstraction Layer (IAL)
2. **Feature Modules** реализуют конкретные коннекторы как npm-пакеты
3. Заказчик подключает нужные модули при сборке
