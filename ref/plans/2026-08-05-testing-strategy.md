# Стратегия тестирования

## Контекст

До 2026-08-05 в проекте **не было ни одного теста**: `turbo.json` объявлял задачу `test`, но ни один
пакет не определял скрипт, а единственный `*.test.ts` в репозитории был ассетом скилла.

Первые 31 тест появились вместе с работой по фильтрам (`2026-08-05-list-filters-and-or.md`) —
`node --test` в `platform-core`, покрывают `contracts/filters.ts` и `backend/services/filter-sql.ts`.
Этот план — про то, как расширять дальше и какая инфраструктура под это нужна.

Документ описывает **направление**, а не обязательство сделать всё сразу: тиры 1–4 отгружаются
независимо и в порядке убывания отношения «польза / стоимость».

## Ключевой рычаг: drizzle рендерит SQL офлайн

Главная находка при написании первых тестов, и она обобщается на весь бэкенд:

```ts
// biome-ignore lint/suspicious/noExplicitAny: драйвер не используется — нужен только рендер SQL
const db = drizzle({ client: {} as any });
const { sql, params } = db.select().from(t).where(clause).toSQL();
```

`.toSQL()` **не открывает соединение**. Значит любой код, который *строит* запрос, тестируется без БД:
проверяется и форма SQL, и биндинг параметров. Так покрыты вложенность OR, схлопывание группы из
одного ребёнка, NULL-арм у `notIn`, экранирование LIKE и все пути на 400 — без единого контейнера.

**Правило:** прежде чем заводить БД под тест, спросить — можно ли проверить это через `.toSQL()`.

## Тир 1 — unit-тесты, инфраструктура не нужна

Раннер уже есть (`node --test`, `turbo test` с `dependsOn: ["build"]`). Кандидаты — чистая или
почти чистая логика с нулевым покрытием, отсортированы по ценности:

| Файл | Строк | Почему |
|---|---|---|
| `module-admin/src/frontend/lib/cron-schedule.ts` | 148 | `cronToScheduleConfig` ↔ `scheduleConfigToCron`: round-trip — идеальная форма теста, а тихий баг означает задачи, запускающиеся не в то время |
| `module-admin/src/frontend/widgets/admin-filter-dialog/lib/draft.ts` | ~120 | `draftToTree`/`treeToDraft` — написано в этой сессии и **не покрыто**; инвариант «id никогда не попадает в дерево» держит совпадение queryKey |
| `module-workflow/src/backend/validation.ts` | 238 | Структурная валидация конфига процесса — единственное, что стоит между плохим конфигом и сломанным движком |
| `module-workflow/src/backend/graph-analysis.ts` | 110 | Достижимость и парность split/join — чистая графовая логика |
| `module-workflow/src/backend/conditions.ts` | 114 | JSONLogic-эвалуатор: решает маршрутизацию процесса |
| `platform-core/src/frontend/hooks/use-swipe-select.ts` | 120 | Алгоритм проекции на линию. Геометрию нужно вынести из хука — тогда она чистая |

Дополнительно через `.toSQL()`, без БД: сборка `buildListSelect`/`applyJoins` (в том числе новые
`joinOn`/`joinType`), `activeFilter` (soft-delete), генерация ORDER BY.

**Стоимость:** близка к нулю, новых зависимостей нет. Отсюда и начинать.

## Тир 2 — `app.inject()` + настоящий Postgres (наибольшая отдача)

`app.inject()` прогоняет полный запрос через роутинг, хуки, валидацию схемы и сериализацию **без
сетевого сокета** — быстро, без браузера и портов.

### Почему это ложится сюда особенно легко

Проверено по коду:

- `apps/api/src/index.ts` уже разделяет `createApp()` + `bootstrap(app, modules, context)` и
  `app.listen()` — тестовый харнесс просто не вызывает `listen`. Отдельная точка входа не нужна.
- **Миграции уже применяются внутри `bootstrap()`** (`platform-core/src/backend/app.ts:200-214`):
  сначала core (`core_migrations`), затем все зарегистрированные модулями через
  `context.migrations.getAll()` в таблицы `${moduleId}_migrations`. Своей машинерии миграций
  писать не надо — достаточно поднять пустую БД и позвать `bootstrap`.
- Подключение берётся из `process.env.DATABASE_URL` (`app.ts:106`) — переключение на тестовую БД
  это одна переменная окружения.

### Что это ловит

Ровно тот слой, где живут реальные баги. Как регрессии оно поймало бы всё, что чинилось в этой
сессии: обход фильтров через `listFetch`, сломанный экспорт 5 HR-типов, `request.t`/`Accept-Language`,
guard в `preHandler`, и новый 400 на невалидном фильтре.

### Инфраструктура

- **Postgres.** В `docker-compose.dev.yaml` уже есть `postgres`, `redis`, `seaweedfs`. Самый дешёвый
  путь — отдельная база `amplicada_test` в том же стеке. Для изоляции в CI — `@testcontainers/postgresql`
  (контейнер на прогон).
- **Redis** нужен для сессий; для большинства API-тестов можно не аутентифицироваться через реальную
  сессию, а подменить `auth-service` в service locator — он и так резолвится по строковому токену.
- **Изоляция между тестами:** транзакция с откатом (быстро) либо `TRUNCATE ... CASCADE` между тестами
  (проще и честнее для кода, который сам открывает транзакции — а движок workflow открывает).

### Чего избегать

- **`pg-mem` — не подходит.** Это JS-реимплементация; она падает на `ilike`, кастах `::text` и
  `FOR UPDATE SKIP LOCKED` — то есть ровно на том, что мы и хотим проверять.
- **PGlite** — настоящий Postgres в WASM, без Docker, и это привлекательно для тира 1.5. Но он
  фактически одно-соединенческий, поэтому **не может** проверить защиту от гонок в движке workflow.

### Первые сценарии

1. `GET /api/admin/documents/:type` с деревом `A AND (B OR C)` — строки те, что нужно; `count(*)`
   согласован с данными.
2. Тот же запрос с невалидным фильтром → **400** и список проблем в `details`.
3. `export-view` CSV/JSON: содержимое ровно отфильтрованное, заголовки колонок переведены по
   `Accept-Language`.
4. **Пять HR-типов после ухода от `listFetch`** — фильтр, сортировка по колонке версии, экспорт,
   и `total` против фактического числа строк (ожидаемо изменился: узел без актуальной версии больше
   не раздувает счётчик).
5. `ilike(sql\`${column}::text\`)` по jsonb-выражению кастомного поля — самая рискованная строка
   фильтров, офлайн-рендер её не покрывает.
6. Движок workflow: parallel gateway с конкурентными коннектами — по плану
   `2026-07-22-workflow-parallel-gateway.md` вживую **никогда не прогонялся**.

## Тир 3 — компонентные тесты фронтенда (Vitest + Testing Library)

`apps/web` уже на Vite (6.x), поэтому Vitest добавляется почти бесплатно — общий конфиг и общий
пайплайн трансформации. Брать только логику, не разметку:

- диалог фильтров: добавление/удаление условий и групп, сброс при открытии, предупреждение о
  схлопывании слишком глубокого дерева;
- `admin-document-list`: сбросы состояния во время рендера при смене типа документа (там уже был
  реальный баг — resize колонки ретриггерил сброс sorting/rowSelection);
- `LanguageSwitcher`/`ThemeSwitcher`: смена языка инвалидирует кеш React Query.

Тесты вида «отрисовался ли div» не писать — они дороже в поддержке, чем ловят.

## Тир 4 — Playwright, последним и намеренно тонким слоем

Единственное, что доказывает согласие всего стека: логин → навигация → построить `A AND (B OR C)` →
увидеть правильные строки → выгрузить CSV.

**Рекомендация: 5–10 smoke-сценариев, а не набор покрытия.** Логин, один CRUD-круг, один
отфильтрованный список, одна выгрузка. Всё остальное дешевле и точнее проверяется тиром ниже.
Playwright — канарейка, а не покрытие: он самый медленный, самый флакующий и самый дорогой в
поддержке. Trace viewer и `--ui` делают отладку терпимой, но это не повод расширять слой.

Нужен поднятый стек и засеянные данные — то есть тир 4 имеет смысл только после тира 2, где сеялка
данных всё равно появится.

## Открытые вопросы

- **CI.** Сейчас его нет. Пока нет CI, тир 2 гоняется руками — это снижает его ценность, но не
  обнуляет: даже разовый прогон против настоящей БД закрывает вопросы, которые офлайн-рендер не может.
- **Сеялка данных.** Появится в тире 2; стоит оформить её как переиспользуемые фикстуры — в
  `contracts/documents.ts` уже есть `FixtureDefinition`/`FixtureRegistry`, возможно их и использовать.
- **Расположение тестов.** Сейчас `*.test.ts` рядом с исходником, прогон по `dist/`. Для тира 2
  (нужны контейнеры/env) вероятно понадобится отдельная задача turbo — `test:integration`, чтобы
  `pnpm test` оставался быстрым и не требовал Docker.

## Замечания по раннеру (проверено эмпирически)

- Тесты гоняются по `dist/`, не по `src/`. Node **не** резолвит специфаер `./x.js` в файл `x.ts` —
  проверено на 22.18 и 24.19, обе дают `ERR_MODULE_NOT_FOUND`. Кодовая база использует
  `.js`-специфаеры (конвенция tsc + ESM), поэтому прогон по исходникам потребовал бы менять
  специфаеры во всём проекте ради тестов. `turbo test` уже имеет `dependsOn: ["build"]` — ложится ровно.
- На Node 24 **type stripping включён по умолчанию**, флаг `--experimental-strip-types` не нужен;
  импорт со специфаером `./x.ts` работает без флагов. На `.js` → `.ts` это не влияет.
- Дефолтный репортёр `node --test` на Node 24 — spec (галочки) вместо TAP.
