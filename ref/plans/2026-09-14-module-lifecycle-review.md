# Модульная архитектура — первый проход

Разбор для автора платформы: зависимости, загрузка, остановка и удаление модулей.
Это предложения для обсуждения, не принятое архитектурное решение и не реализованный
план. Основа — текущий working tree, включая существовавшие до анализа изменения.
БД и приложения не запускались. Формат данных не менялся, пропущенных миграций нет.

**Обновление 2026-09-14:** исправлен путь `app.close()`: обе фазы shutdown, обратный
порядок `stop()` модулей, продолжение очистки после ошибок. Добавлены тесты с Fastify
без внешних сервисов; `pnpm typecheck` и `pnpm --filter @amplicada/platform-core test`
прошли. Это только часть итерации 1: сортировка зависимостей, очистка
частичного bootstrap и ожидание выполняющихся фоновых работ пока не реализованы.

**Обновление 2026-09-15:** реализованы автоподключение из production dependencies, необязательные профили,
независимый CLI и генерация backend/frontend/CSS,
метаданные в package.json и валидация/сортировка зависимостей обоих bootstrap.
Решение — [ADR-05](../adr/05-application-composition.md), использование —
[application-composition](../guides/application-composition.md). Выводы ниже отражают
исходный аудит; пункт о неисполняемых dependencies теперь закрыт. Удаление модулей,
очистка частичного bootstrap и типизация service tokens остаются отдельными работами.

Внешняя проверка: core/admin/auth/tools упакованы через `pnpm pack` и установлены в
чистый проект `/tmp/amplicada-package-smoke/verified-app` с `ignoreScripts: true`,
`blockExoticSubdeps: true`, `minimumReleaseAge: 43200`, без новых исключений. Активен
только auth из прямых dependencies; admin установлен как библиотечный peer.
Прошли discovery без конфига, tsc, Vite без alias на исходники core и загрузка backend
экспортов обычным Node. PostgreSQL/Redis/S3 и HTTP-login этим smoke-тестом не проверялись.
При проверке исправлены состав tarball (dist раньше исключался), JSON import attributes
и внутренние UI aliases. npm-публикация не выполнялась. Предупреждения peer check
относятся к подстановке локальных tarball вместо semver неопубликованных пакетов.

Упрощение этой итерации: full/minimal перенесены в fixtures теста CLI и отвязаны от
демоприложений. Удалены переменная выбора профиля, поиск корня workspace, глобальные
inputs Turbo для состава, лишняя корневая зависимость на CLI и дублирующие команды
его test/typecheck. Обычная сборка получает модули из dependencies, явный `--config`
остаётся отдельной возможностью. Данные и схемы не изменены.

## Оценка направления

Модульный монолит с составом пакетов на этапе сборки соответствует модели отдельных
клиентских сборок. Общие транзакции, identity в core, отдельные схемы и миграции модулей,
contracts и расширения документов дают хорошую основу. Service locator можно сохранить.
Главный пробел — отсутствие проверяемого жизненного цикла модулей и полного учёта
принадлежащих им ресурсов. Сейчас модульность лучше описывает добавление, чем удаление.

## Зависимости: целевая модель

Разделять три вида связи:

- **Пакетная:** импорт контракта, компонента или схемы, фиксируется в package.json.
- **Обязательная при запуске:** потребителю нужен установленный модуль, фиксируется в manifest.
- **Опциональная интеграция:** вклад в extension point либо отдельный модуль интеграции.

Они пересекаются, но не взаимозаменяемы. Топологическая сборка Turborepo не сортирует
массив `bootstrap`. Импорт контракта опциональной интеграции всё ещё требует доступности
пакета при сборке; исключить и эту зависимость позволяет отдельный пакет интеграции.

Для обязательных связей: проверить уникальность id, присутствие зависимостей и отсутствие
циклов до модульных побочных эффектов; выдать ошибку с цепочкой зависимости. Затем использовать
стабильный топологический порядок в backend и frontend. Уточнить, какие требования общие,
а какие относятся только к одной стороне. Core — обязательная предпосылка вне списка модулей.

Для текущего HR зависимость от workflow создаёт `fixed-assignee`: он использует только
переданный userId, без кадровой логики. Кандидат на перенос в workflow. Будущего делегата
«руководитель сотрудника» можно разместить в отдельной интеграции HR/workflow, если нужна
сборка HR без workflow. Для заявок обязательная зависимость от engine естественна.

Важное ограничение: граф пакетов не видит ссылки в сохранённых workflow-конфигах.
Например, после исчезновения `fixed-assignee` переход на использующую его ноду завершится
ошибкой в `WorkflowEngine`. До отключения провайдера требуется проверить конфиги и активные
экземпляры. Нужны метаданные владельца делегата, а не вывод владельца из имени.

## Загрузка и остановка: целевое поведение

Минимальная эволюция существующего API:

1. Проверить состав и построить порядок; зарегистрировать метаданные всех модулей.
2. Вызвать `setup` в этом порядке: регистрации, создание сервисов, объявления миграций
   и обработчиков. Не читать данные модулей и не запускать фоновые работы до миграций.
3. Применить миграции core, затем модулей по графу; сверить fixtures.
4. После всех `setup` связать опциональные вклады и проверить целостность реестров.
   Для простых потребителей достаточно существующего `start`; отдельная фаза нужна
   только если необходимо связать все сервисы до начала какой-либо фоновой работы.
5. Запустить инфраструктуру и модули в явно определённом порядке готовности, затем HTTP.
6. При остановке прекратить приём работ, дождаться/отменить текущие, остановить модули
   в обратном порядке зависимости, затем закрыть инфраструктуру.

Регистрацию очистки ресурсов нужно делать при их приобретении, чтобы сбой до конца
bootstrap тоже освобождал ресурсы. Ошибка одного stop не должна пропускать остальные.
Это очистка процесса; она не обещает откат уже применённых миграций или внешних эффектов.

При нескольких процессах миграции и сверка fixtures должны иметь одного координатора
или сериализацию. В текущем bootstrap `reconcileFixtures(db)` вызывается без общей
транзакции, хотя комментарий внутри метода ссылается на транзакцию bootstrap; путь
создания содержит несколько запросов. Гонки и восстановление после сбоя требуют
отдельной проверки против PostgreSQL.

## Удаление: что считать данными модуля

Отключение сохраняет данные для возврата модуля. Полное удаление очищает явно описанный
набор ресурсов. При compile-time составе это операция обслуживания с пересборкой и
перезапуском приложения; горячая выгрузка для этого не нужна.

| Ресурс | Пример | Предлагаемая политика |
|---|---|---|
| Собственная схема | `hr_learning` | Удалить после обработки внешних зависимостей |
| Документы собственных типов | Курсы и попытки в `core.document_index` | Удалить индекс и данные расширений с учётом FK; учесть soft-deleted записи |
| Расширения чужих документов | `document_custom_fields.module`, отдельные extension-таблицы | Удалить вклад модуля, сохранить сам чужой документ |
| Задачи и история | Задача ingest в `core.scheduled_tasks`, runs/logs | Остановить исполнителей, удалить по явному владельцу/каталогу |
| Файлы | `learning/_incoming/...`, `learning/<packageId>/...` | Сохранить перечень очистки до удаления источника этих сведений; удалять с повторами |
| Данные, созданные через другой модуль | Process instances для hr-requests | Согласовать доменную очистку через workflow; не удалять все процессы workflow |
| Общие сущности | `core.identity_user` при удалении auth-password | Сохранить пользователей, удалить credentials провайдера |
| История миграций | `${moduleId}_migrations` | Согласовать очистку с удалением схемы, иначе переустановка может пропустить создание таблиц |
| Конфигурационные ссылки | providerId в версиях workflow | Блокировать удаление, пока ссылки не обработаны по явной политике |

Нужен каталог принадлежности ресурсов, доступный и после исключения модуля из рабочей
сборки: сохранённые метаданные установки либо инструмент обслуживания с пакетом модуля.
`DocumentType.module` уже даёт часть этого каталога — не стоит вводить дублирование без нужды.
У записей общих типов, например scheduled-task, отдельно нужен владелец экземпляра.

Предлагаемый процесс: предварительный план удаления → блокировка новых работ во всех
процессах → доменная очистка зависимых ресурсов → очистка БД и storage → проверка остатков
→ сборка без модуля. План должен перечислять зависимые модули, FK, конфиги и ресурсы,
включая расширения других модулей на удаляемых документах. Удалять зависимые модули
автоматически нельзя: состав удаления должен быть явным.

БД и storage не образуют одну транзакцию: состояние удаления и оставшиеся операции
нужно сохранять, шаги делать повторяемыми. Для текущей стадии достаточно небольшой
команды обслуживания и проверяемого сценария, универсальный установщик преждевременен.
Полный сброс одноразового dev-контура допустим по политике проекта, но не проверяет
сценарий избирательного удаления с сохранением остальных модулей.

## Итерации

1. **Жизненный цикл:** исправить shutdown, обработку ошибок старта, stop модулей;
   включить проверку и сортировку dependencies. Проверки: пропущенная зависимость,
   дубликат, цикл, перестановка входа, обратная остановка, частичный сбой старта.
   Изменение договорённости из ADR-02 оформить новым ADR при принятии.
2. **Владение и удаление:** разобрать hr-learning целиком; сделать предварительный
   план очистки, отключение исполнителей и повторяемое удаление. Проверить сохранность
   чужих данных, файлы, core-записи, переустановку и восстановление после обрыва.
3. **Границы:** оценить HR/workflow и UI/admin; типизировать service tokens,
   запретить случайные дубликаты регистраций. Согласовать существующие правила
   dependency-cruiser с разрешёнными публичными межмодульными API.
4. **Отдельные следующие аудиты:** авторизация в HTTP и программных вызовах;
   транзакции, конкуренция и доставка событий; bootstrap чистой БД и матрица клиентских
   сборок. Локальный EventBus не считать гарантированной доставкой бизнес-событий.

Полный аудит document runtime, workflow, изоляции учебного контента и UI в этот проход
не входит. Старые документы содержат расхождения с кодом; они не использовались как
доказательство реализации. [ADR-02](../adr/02-dependency-injection.md) остаётся принятой
политикой до отдельного решения, этот документ её не заменяет.
