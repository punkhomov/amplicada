# 04. Orphaned-сверка, heartbeat флота, алерты

Родительский план: [2026-07-14-task-scheduler.md](2026-07-14-task-scheduler.md)

**Блокируется:** [02](02-lock-and-execution.md) (backend-механизмы); баннер в UI дополнительно блокируется [03](03-admin-basic-management.md)
**Блокирует:** ничего напрямую, но логически стоит сделать до продакшена
**Пакет:** `platform-core` (reconciler, heartbeat, событие алерта) + маленькая доработка `module-admin` (баннер)

## Что делаем

Три независимых друг от друга механизма надёжности, которые можно реализовывать в любом порядке внутри этой фазы:

1. Обнаружение "зависших" run'ов, чей воркер пропал
2. Видимость: жив ли вообще хоть один worker-инстанс
3. Алерт на падение критичной задачи

## Orphaned-сверка

Lease-лок ([02](02-lock-and-execution.md)) решает проблему одного упавшего инстанса среди нескольких — лок сам разваливается по TTL. Но запись в `scheduled_task_runs` при этом остаётся в статусе `running` навсегда, если её никто явно не переведёт в терминальное состояние.

Периодическая (или при старте `worker`-роли) сверка: run в статусе `running` дольше `timeout + grace`, а лок для задачи уже не существует → `orphaned`.

## Heartbeat воркер-флота

Другой случай: воркеров вообще не осталось (например, `worker`-роль задеплоена с 0 реплик или все инстансы упали разом). В этом случае croner-таймеры нигде не тикают, и задача просто молча не выполнится в положенное время — lock/lease тут не помогает, потому что лок никто и не пытается взять.

- Каждый `worker`-инстанс раз в ~30s обновляет `worker:heartbeat:{workerId}` в Redis с TTL
- Admin UI показывает баннер «нет активных воркеров», если ни один heartbeat не свежий

Обнаружение именно пропущенных *срабатываний расписания* (а не просто отсутствия воркеров) сознательно отложено — см. родительский план, раздел «Отложено».

## Алерт на падение критичной задачи

`alertOnFailure: boolean` уже часть контракта ([01](01-contracts-and-roles.md)). Здесь — сама реакция: при переходе run'а в `failed`/`timeout` с этим флагом эмитится событие для алертинга.

**Нужно свериться перед реализацией**, есть ли уже в проекте канал уведомлений (email/Slack/etc через существующий модуль) — если да, это просто точка интеграции с ним; если нет, канал доставки — отдельная задача за рамками этого плана, здесь только генерация события.

Статус: код написан, `pnpm -w typecheck` и `pnpm exec biome check` проходят чисто по всем новым/изменённым файлам. Раздел «Проверка» не прогонялся вживую (по решению пользователя, тестирование в рантайме пока отложено).

Уточнения, не описанные исходным текстом плана:
- **Канала уведомлений в проекте нет** (проверено — ни одного email/Slack/webhook пакета ни в одном `package.json`, ни готового сервиса под таким именем). Пользователь явно подтвердил: email не нужен сейчас. Поэтому здесь только генерация события `task.alert` (отдельное от `task.run.failed`, эмитится только когда `alertOnFailure: true` и исход — реальный сбой, `error`/`timeout`, но не `cancelled`) + дефолтный listener в `app.ts`, который просто логирует через `app.log.error` с префиксом `[task-alert]`. Реальный канал доставки — самостоятельная задача, когда понадобится
- **`TaskLock.exists(taskId)`** — добавлен новый метод (`redis.exists`) специально для reconciler'а, не было в файловой таблице исходного плана явно, но логически часть той же "Lease-лок" зоны ответственности из [02](02-lock-and-execution.md)
- **Неточность reconciler'а, о которой стоит знать**: лок проверяется по `taskId`, а не по конкретному `runId`. Если старый зависший run по задаче A обнаруживается одновременно с тем, что по этой же задаче уже стартовал новый (легитимный) run и держит лок — старая запись не будет помечена `orphaned` в этом проходе (лок для `taskId` формально есть). Она словится следующим проходом реконсиляции, когда новый run завершится и лок освободится. То есть возможна задержка в один цикл (~30s), не некорректный результат навсегда
- **SSE, не WebSocket, для будущей фазы 05** — сверился со скиллом `fastify-best-practices`: готового SSE-рецепта там нет, только `@fastify/websocket`. Поскольку поток логов однонаправленный (сервер → браузер), а запуск/отмена уже идут отдельными REST-эндпоинтами, WebSocket избыточен — возьмём `reply.raw` + `text/event-stream` без нового пакета. Решение зафиксировано здесь, реализация — в [05](05-realtime-logs.md)

## Проверка

1. Убить `worker`-процесс во время выполнения задачи → через какое-то время run помечается `orphaned`, а не висит в `running` вечно
2. Остановить все worker-инстансы → баннер «нет активных воркеров» появляется в разумное время в UI
3. Поднять воркер обратно → баннер исчезает
4. Задаче с `alertOnFailure: true` спровоцировать ошибку → убедиться, что событие алерта сгенерировано (и дошло до канала, если он подключен)
5. Задаче с `alertOnFailure: false` (default) спровоцировать ошибку → убедиться, что алерт НЕ генерируется
