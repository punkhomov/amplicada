# Отчёт о реализации: Task Scheduler (фазы 01–05)

Родительский план: [2026-07-14-task-scheduler.md](2026-07-14-task-scheduler.md)

Сводка для проверки: что реально сделано, какие решения оказались не такими, как в исходном тексте планов (и почему), и как пощупать систему руками. Фазы 01–05 реализованы кодом, ни разу не прогонялись вживую (Docker не поднимался в процессе реализации) — `pnpm -w typecheck` и `pnpm exec biome check` чистые на каждом шаге, это единственная форма проверки на данный момент.

## Критичные находки по ходу реализации

Не косметика — реальные баги/дизайн-ошибки, которые не были видны на этапе планирования и всплыли только при чтении существующего кода или при столкновении дизайна с реальностью.

### 1. `register()` не мог писать в БД синхронно (фаза 01)

Планировалось: `register()` сразу делает upsert в `scheduled_tasks`. На деле — `bootstrap()` в `app.ts` вызывает `setup()` всех модулей **до** прогона core-миграций. Если бы `register()` писал в БД напрямую, первый же запуск падал бы с `relation "scheduled_tasks" does not exist`. Решение: `register()` синхронный, копит в `Map`; separate `reconcile(db)` вызывается один раз из `bootstrap()` сразу после core-миграций — тот же паттерн, что уже был у `context.migrations` (регистрация копит список, применение — пакетное и позже).

### 2. Асимметрия доставки событий по ролям (фаза 05, найдено и исправлено сегодня)

Изначальная реализация: `TaskRunner` эмитил событие и локально (`eventBus.emit`), и параллельно публиковал в Redis. `TaskEventBridge` (Redis → локальный `eventBus`, нужен для SSE) запускался только при `ROLE=web` — на `ROLE=all` его не стартовали, чтобы не задвоить доставку (TaskRunner и так писал в тот же локальный eventBus напрямую). Это давало два разных пути в зависимости от роли — фрагильно и асимметрично, замечено при повторном чтении кода.

**Исправлено**: `TaskRunner` теперь **только публикует в Redis**, никогда не эмитит локально. `TaskEventBridge` запускается **на любой роли безусловно** и является единственным путём наполнения локального `eventBus`. Поведение теперь одинаковое для `web`/`worker`/`all` — нет спецкейсов под конкретную роль в этой части системы. Как побочный эффект стало явным: alert-слушатель в `bootstrap()` (тот, что логирует `[task-alert]`) тоже теперь получает событие только через мост, а не напрямую — на `worker`-роли до этой правки он работал "случайно" (из-за прямого локального emit), теперь работает всегда одинаково, явно.

### 3. Reconciler проверяет лок по `taskId`, а не по `runId` (фаза 04, известное ограничение)

Если старый зависший run по задаче A совпадает по времени с новым легитимным run той же задачи (уже держащим лок) — старая запись не будет помечена `orphaned` в этом проходе сверки, потому что лок для `taskId` формально существует. Само исправится на следующем проходе (~30s), когда новый run завершится и освободит лок. Не баг "навсегда", но задержка возможна — стоит иметь в виду при разборе логов.

### 4. Отмена не останавливает код, только статус (фаза 03, осознанное решение, не баг)

`TaskRunner.cancel(runId)` абортит `AbortSignal`, но если handler не пробрасывает его в свои запросы — работа продолжится в фоне. Платформа гарантирует **статус `cancelled` и освобождение лока**, даже если handler потом успешно "дозавершится" сам — раннер принудительно перезаписывает итоговый статус, если была команда отмены. Это ожидаемое поведение (см. «Отложено» в родительском плане — force-kill через `child_process` сознательно не делали), но легко перепутать с багом при отладке: если ваш демо-handler не проверяет `signal`, после нажатия «Отменить» в логах вы всё равно увидите, что он доработал до конца.

## Как это работает — пошагово

### Регистрация и активация

1. Модуль вызывает `context.tasks.register(id, options, handler)` в своём `setup()` — просто кладёт в `Map` в памяти процесса
2. После core-миграций `bootstrap()` вызывает `TaskRegistryImpl.reconcile(db)` — один upsert-проход по всем зарегистрированным задачам. Новая задача попадает в БД с `paused: true, schedule: null`. Задачи, пропавшие из кода, помечаются `stale`, не удаляются
3. В админке (`/admin/tasks`) задаче задаётся `schedule` (валидируется через `croner` на бэке) и снимается `paused` — только через это она вообще может начать выполняться

### Выполнение по расписанию

4. На `worker`-роли (`ROLE=worker` или `all`) `TaskScheduler` раз в 5с перечитывает `scheduled_tasks`, создаёт/убирает `croner`-таймеры под активные (`!paused && !stale && schedule`) задачи
5. По срабатыванию таймера — `TaskRunner.run()`: берёт Redis-лок (`SET NX PX`, TTL = `timeout + 15s`, токен уникален на попытку), создаёт `running`-запись в `scheduled_task_runs`, вызывает handler с `{ signal, log }`, параллельно продлевает лок Lua-скриптом каждые `ttl/3`
6. По завершении — атомарно освобождает лок (тоже Lua, только если токен совпадает), пишет терминальный статус (`success`/`failed`/`timeout`/`cancelled`)

### Ручной запуск и отмена (кросс-процессно)

7. Кнопка «Запустить сейчас» → `POST /admin/tasks/:id/run` → `web` публикует `taskId` в Redis-канал `task:run-now` → `worker`, подписанный на этот канал внутри `TaskScheduler`, вызывает тот же `triggerNow()`, что и штатный таймер — Redis-лок гарантирует, что при нескольких worker-репликах выполнится только один
8. Кнопка «Отменить» → аналогично через канал `task:cancel-run`, `runId` → `worker` вызывает `TaskRunner.cancel(runId)`

### Доставка в браузер (реалтайм)

9. Внутри `execute()` каждый переход состояния (`started`/`succeeded`/`failed`) и каждый вызов `log.info`/`log.error` идёт через `emitTaskEvent(redis, type, payload)` — **только** `redis.publish('task:events', JSON)`, больше ничего
10. `TaskEventBridge` — на **любом** процессе, любой роли — держит отдельное Redis-подключение, подписан на `task:events`, всё, что приходит, реэмитит на локальный `context.eventBus`
11. `GET /admin/tasks/events` (SSE, живёт на `web`) подписан на 4 типа событий в `eventBus`, форвардит каждое в открытые браузером соединения как `event: <type>\ndata: <json>`
12. Браузер: один `EventSource` на страницу (`useTaskEventStream`). Список задач патчит `activeRunId` в кэше react-query по приходу `started`/`succeeded`/`failed` — отсюда переключение кнопки «Запустить»⇄«Отменить» без перезагрузки. Страница деталей задачи то же самое плюс живые логи, привязанные к `runId`

### Надёжность (фаза 04)

13. `TaskReconciler` (только `worker`-роль, раз в 30с): `running`-записи старше `timeout+grace` без активного лока → `orphaned`
14. `WorkerHeartbeat` (только `worker`-роль, раз в 30с): пишет `worker:heartbeat:{workerId}` с TTL 90с. `GET /admin/tasks/fleet-status` считает живые ключи — если 0, баннер в UI
15. `alertOnFailure: true` на задаче + падение (`failed`/`timeout`, не `cancelled`) → событие `task.alert` → сейчас только `app.log.error` с префиксом `[task-alert]`, реального канала доставки нет (осознанно, по вашему решению)

## Как проверить руками

Базовый сценарий (уже проговаривали для `auth-password-demo`):

1. Поднять стек (`docker compose up` / `pnpm dev` — там, где Postgres+Redis реально доступны)
2. `/admin/tasks` → `auth-password-demo` стоит на паузе → «Возобновить» → «Запустить сейчас»
3. Статус и кнопка должны переключиться на «running»/«Отменить» **без перезагрузки страницы**
4. Открыть деталку задачи, развернуть running-строку — 4 строки лога должны появляться по одной с интервалом ~2с
5. Дождаться завершения — статус должен стать `success`, кнопка вернуться в «Запустить сейчас»

Точки, которые стоит отдельно пощупать, раз они были главными находками сегодня:

6. Запустить с явным `ROLE=web` в одном процессе и `ROLE=worker` в другом (два разных `node` процесса на одну БД/Redis) — реалтайм должен работать точно так же, как в `ROLE=all` (пункт 3 выше) — события идут исключительно через Redis-мост
7. Проверить, что событие не приходит в SSE дважды за одно действие (например, залогировать в devtools Network → EventStream и посчитать сообщения на один клик «Запустить сейчас»)
8. Нажать «Отменить» на задаче, handler которой **не** уважает `AbortSignal` (например, временно убрать `signal` из `fetch` в демо-таске) — статус должен всё равно стать `cancelled`, но в консоли/логах будет видно, что handler продолжает и завершается сам чуть позже
