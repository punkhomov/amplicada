# Task Scheduler — повторяемые задачи в core

Верхнеуровневый план. Детали реализации — в подпланах этой папки, разбитых по фазам.

## Текущая проблема

1. Нет инфраструктуры для фоновых задач — модулям негде зарегистрировать периодические операции.
2. Горизонтальное масштабирование (несколько инстансов API) требует coordination — без распределённого лока задачи будут дублироваться.
3. HTTP event loop не должен блокироваться таймерами и тяжёлыми задачами.
4. Нет visibility — невозможно посмотреть список задач, статус, историю запусков, логи выполнения.
5. Нет способа среагировать на падение критичной задачи, кроме как случайно заметить в логах.

## Решение

Добавить в `@amplicada/platform-core` модуль TaskScheduler:
- Разделение роли процесса через `ROLE=web|worker|all` (env var, default `all`) — тот же монолитный кодбейз, без распила на сервисы. `web` обслуживает HTTP и не тикает планировщиком; `worker` не слушает HTTP (кроме health-check) и только выполняет задачи; `all` — оба сразу (локалка/маленькие деплои)
- `croner` для таймеров — тикает в main thread `worker`-роли
- Код регистрирует **что** за задача (id, handler, description, timeout, alertOnFailure) — **когда** она выполняется решает исключительно админка (schedule, paused), хранится в БД, код это никогда не перезаписывает
- Redis-лок как **lease с продлением** (heartbeat), а не статичный TTL — привязан к `timeout` задачи, переживает штатное выполнение и сам разваливается при падении процесса
- Redis Pub/Sub для ручного запуска и отмены: `web`-роль (admin UI) не выполняет и не отменяет handler сама, а публикует команду, которую подхватывает `worker`-роль
- Кооперативная отмена через `AbortSignal`, real-time логи через тот же Pub/Sub, история — в БД
- Heartbeat воркер-флота — видимость, если ни один `worker`-инстанс не жив
- Admin UI: список задач, редактирование расписания, история запусков, live-логи, пауза/возобновление/отмена/ручной запуск

## Архитектурный принцип: направление зависимости

**`platform-core` не знает о существовании `module-admin`.** Контракт `TaskScheduler` и вся его реализация (registry, lock, runner, scheduler, reconciler, heartbeat) — самодостаточный модуль core, который ничего не импортирует из admin и не завязан на то, что admin вообще существует в системе.

`module-admin` — это единственная сторона, которая зависит: она импортирует контракт из `platform-core`, дергает его API (`context.tasks`), подписывается на его события. Если `module-admin` завтра выпилят из проекта — `platform-core` и весь механизм расписаний продолжит работать: задачи по-прежнему будут регистрироваться и выполняться, просто управлять паузой/расписанием/ручным запуском можно будет только напрямую через БД, без UI.

Это ограничение — не пожелание, а проверяемое инвариант: ни один файл в `packages/platform-core/**` не должен импортировать что-либо из `packages/module-admin/**`. Обратное — сколько угодно.

## Архитектура

```
┌───────────────────┐        ┌───────────────────┐
│   web-инстанс(ы)   │        │  worker-инстанс(ы) │
│   Fastify + HTTP   │        │  croner timers     │
│   Admin UI (SSE)   │        │  Handlers          │
│   TaskEventBridge* │        │  lease-lock         │
│   tasks.register() │        │  tasks.register()  │
│   (только upsert   │        │  heartbeat          │
│    определения)    │        │                     │
└─────────┬──────────┘        └─────────┬──────────┘
   module-admin (зависит)      platform-core (не зависит)
          │  run-now / cancel-run (pub/sub)          │
          │  task:events — все события одним каналом │
          └──────────────►Redis◄────────┘
              (lease-lock + Pub/Sub + fleet heartbeat)
```
\* `TaskEventBridge` (Redis → локальный `eventBus`, откуда берёт события SSE) стартует только на чистой `web`-роли — на `ROLE=all` события и так эмитятся в тот же локальный `eventBus` напрямую, без похода в Redis.

## Зависимости (сводно)

| Пакет | Зачем | Новый? |
|-------|-------|--------|
| `croner` | Парсит cron, timezone, таймеры. ~3KB, zero-dep | Да |
| `redis` (node-redis) | Уже есть, используется для сессий. Lease-лок, Pub/Sub, heartbeat | Нет |

`AbortController`/`AbortSignal` — нативный Node API, доп. зависимость не нужна. ioredis не нужен — используем существующий `redis` клиент.

## Отложено (не в v1)

- **Обнаружение пропущенных срабатываний** при полностью недоступном воркер-флоте (catch-up/replay расписания) — сопоставимо по сложности с отдельной retry/backlog-системой
- **Форсированная отмена** через `child_process` на run — кооперативной отмены через `AbortSignal` достаточно для v1; child_process-изоляция на run усложняет стрим логов и IPC, стоит своих денег только если появятся handler'ы, которые систематически не уважают `signal`
