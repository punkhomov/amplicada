# 03. Базовое управление из админки

Родительский план: [2026-07-14-task-scheduler.md](2026-07-14-task-scheduler.md)

**Блокируется:** [01](01-contracts-and-roles.md), [02](02-lock-and-execution.md)
**Блокирует:** банер heartbeat в [04](04-reliability.md), live-логи в [05](05-realtime-logs.md)
**Пакет:** `module-admin`. Импортирует контракт и API `platform-core`, но не наоборот — `platform-core` про этот пакет ничего не знает.

## Что делаем

Первый UI-слой: список задач, редактирование расписания, история запусков, ручной запуск, отмена, пауза/возобновление. Без real-time логов и без баннера здоровья флота — это следующие фазы.

## Ручной запуск (Redis Pub/Sub)

`web`-роль (admin UI) **не выполняет handler сама**, даже если он есть у неё в памяти — иначе тяжёлая задача заблокирует именно тот HTTP-процесс, ради изоляции которого затевалось разделение ролей ([01](01-contracts-and-roles.md)).

1. `web` публикует `run-now(taskId)` в Redis Pub/Sub
2. `worker`-инстансы подписаны на канал (подписка — часть [02](02-lock-and-execution.md), доработка scheduler'а под этот подплан); получив сообщение, идут по тому же пути, что и штатный триггер — лок гарантирует единственное выполнение при нескольких worker-репликах

## Отмена запущенной задачи

1. Админ жмёт «Отменить» на конкретном `runId` → `web` публикует `cancel-run(runId)`
2. `worker`, который держит лок этого run'а, вызывает `abortController.abort()` для `signal`, переданного в handler
3. Это **кооперативная** отмена — если handler не пробрасывает `signal` в свои запросы, работа физически продолжится в фоне. Платформа гарантирует освобождение лока и статус `cancelled`, не форсированную остановку кода (см. «Отложено» в родительском плане)

## Расписание — редактирование и валидация

Админ задаёт `schedule` (cron) и снимает `paused`. Валидация на бэке через `croner` при сохранении — битый паттерн возвращает 4xx с понятной ошибкой, а не падает в 500.

Статус: код написан, `pnpm -w typecheck` и `pnpm exec biome check` проходят чисто по всем новым/изменённым файлам. Раздел «Проверка» не прогонялся вживую (по решению пользователя, тестирование в рантайме пока отложено).

Уточнения, не описанные исходным текстом плана:
- **`validateCronSchedule()`** живёт в `platform-core` (`task-scheduler.ts`), а не в `module-admin` — чтобы не тащить `croner` вторым прямым dependency в admin-пакет. `module-admin` просто импортирует готовую функцию из `@amplicada/platform-core/backend`
- **Подписчик Pub/Sub — отдельное соединение** (`redis.duplicate()` + `.connect()`), не тот же клиент, что держит лок/выполняет команды — стандартная практика node-redis для pub/sub
- **Отмена реализована через `TaskRunner`**, не `TaskScheduler`: раннер хранит `Map<runId, AbortController>` (`inFlight`) и `Set<runId>` уже отменённых (`cancelledRuns`). `cancel(runId)` абортит signal; после завершения (успешного или нет) раннер проверяет, был ли run отменён, и **принудительно перезаписывает статус на `cancelled`** — даже если handler успел завершиться штатно после abort(), потому что платформа обещает статус `cancelled` по факту команды, а не по факту реальной остановки кода
- **У страницы деталей задачи нет отдельного `GET /tasks/:id`** — переиспользуется список `GET /tasks` (тот же react-query кэш, `find()` на клиенте по id). Экономия одного эндпоинта, не показалось оправданным заводить его для одной задачи в списке из пары десятков
- **`TaskRunFailedEvent.reason`** расширен с `'error' | 'timeout'` до `+ 'cancelled'` — событие `task.run.failed` теперь общее для всех неуспешных терминальных исходов, отдельного `task.run.cancelled` не заводили (не было в исходной таблице событий фазы [02](02-lock-and-execution.md), и DB-статус `cancelled` уже покрывает потребность истории)

## Проверка

1. Включить задачу из UI (задать cron, снять паузу) → убедиться, что `worker` (02) подхватывает без рестарта
2. Паузить через UI → `worker` пропускает следующий тик
3. Нажать «Запустить сейчас» → выполнение реально идёт в процессе `worker`, а не `web` (залогировать PID/instance ID и сравнить)
4. Нажать «Отменить» на выполняющемся run'е → статус `cancelled`, лок освобождён
5. Ввести в поле расписания невалидный cron → получить понятную ошибку, а не 500
6. Убедиться, что `packages/platform-core` по-прежнему не содержит ни одного импорта из `packages/module-admin`
