# workflow — политика полей, модель актора, асинхронная автоматика

Консолидированный план по пяти пунктам из todos (`(workflow)`-блок): доработка с правкой полей,
i18n статусов, workflow для оценки, «actor = система», ИИ-шаг в процессе. Анализ показал, что пять
задач сводятся к четырём базовым концепциям — план описывает все, но исполняемый скоуп — фазы A и B;
фазы C–E зафиксированы как направления, чтобы не перепроектировать их заново.

Контекст: движок — `packages/module-workflow` (см.
[2026-07-16-workflow.md](2026-07-14-workflow/2026-07-16-workflow.md)), первый потребитель —
`packages/module-hr-request` ([2026-07-18-hr-requests.md](2026-07-18-hr-requests.md)).
Ключевые файлы: `module-workflow/src/backend/engine.ts` (интерпретатор),
`src/contracts/graph.ts` (типы нод), `src/backend/schema.ts` (таблицы),
`module-hr-request/src/backend/routes.ts` + `src/frontend/pages/request-card-page.tsx` (портал).

## Текущая проблема (по пунктам todos, с привязкой к коду)

1. **Доработка: нельзя менять поля заявки.** Механизм наполовину есть:
   `engine.executeAction(..., { payloadPatch })` применяет патч к payload, а роут
   `POST /hr-requests/:id/actions/:action` принимает `body.fields` и синхронизирует их в
   `hr_requests.fields`. Чего нет:
   - **Политики** — движок применяет patch без ограничений. Это дыра: любой согласующий может
     прислать `fields` вместе со своим действием и перезаписать **любые** ключи payload
     (например, поменять `cost` перед гейтвеем). Сейчас UI этого не делает, но API позволяет.
   - **UI** — карточка заявки рендерит форму readonly для всех состояний, кроме черновика
     (`canEdit = draft && author`), исполнитель шага физически не может править поля.
   - **Истории изменений** — в `workflow_audit_log` есть `comment`, но нет диффа полей.
2. **i18n статусов/действий** (не приоритет). Label'ы нод и рёбер вшиты в конфиг графа и
   напрямую являются статусами/названиями кнопок. Важно только не закраситься в угол — и мы не
   закрашены: статус ключуется стабильным `node.id`, действие — стабильным `edge.action`; label —
   лишь отображение. Слой перевода добавляется поверх без миграций.
3. **Workflow для других объектов (оценка).** Вопрос «что движку, а что потребителю». Два
   ортогональных вектора расширения: *процесс* (движок уже универсален) и *данные/формы*
   (концепция «полей» сейчас заперта в hr-requests: `RequestFormField` + `GenericRequestForm`,
   хотя ничего заявочного в ней нет). Пайплайн расширения данных (360 добавляет компетенции) —
   тот же паттерн, что `DocumentExtension` в админке, только на сервисе потребителя.
4. **«Actor = система» у авто-переходов.** Частично ложная тревога: в БД хопы **уже**
   атрибутируются инициатору каскада (`writeAuditHops` пишет `actorId = startedBy/actingUser`,
   `action = 'auto'`; инициатор процесса — `process_instances.created_by`). «Система» — это
   рендер: оба таймлайна (`process-timeline-page.tsx`, `request-card-page.tsx`) при
   `action === 'auto'` показывают слово «система» вместо актора, который лежит в той же строке
   ответа (`actorLogin`). Настоящая проблема — на будущее: `workflow_audit_log.actor_id`
   NOT NULL FK на `identity_user`, то есть **по-настоящему системный переход (таймер, фоновая
   автоматика) записать некем** — нет понятия системного актора.
5. **ИИ-шаг (LLM-проверка обоснования).** Концептуально ложится идеально: автодействие пишет
   вердикт в `payload.aiVerdict` → следующий Gateway маршрутизирует. Два дефекта текущего
   sync-serviceTask:
   - *Мелкий (баг)*: провайдер получает `ctx` по ссылке и может мутировать `ctx.payload`, но
     `startProcess` вставляет payload **до** `advance`, а `executeAction` сохраняет **после** —
     результат автодействия персистится только во втором случае. Несимметрично и случайно.
   - *Крупный (архитектурный)*: serviceTask исполняется синхронно **внутри транзакции движка под
     `FOR UPDATE`** — LLM-вызов повесит лок на секунды, ретраев нет, а ошибка/таймаут LLM
     прилетит согласующему как ошибка его действия. Для внешних вызовов нужна асинхронная
     нода-ожидание.

## Решение

Четыре концепции вместо пяти задач: (A) **поля как first-class концепция** — политика
редактируемости per-шаг + дифф в аудит + симметричное сохранение payload; (B) **модель актора** —
`actor_type` в аудите + честный рендер таймлайна; (C) **асинхронная автоматика** — wait-state нода
для внешних вызовов (ИИ — просто один из делегатов); (D/E) **зафиксированные принципы** без кода —
i18n поверх стабильных ключей и обобщение полей при втором потребителе. Исполняем A+B (одна
сессия), C — по потребности, D/E — только принципы в этом документе.

## Фаза A — политика полей + дифф в аудит (исполняемая)

### A1. Контракт: `editableKeys` на UserTask-ноде

`src/contracts/graph.ts`:

```typescript
export interface UserTaskNode {
  // ...существующее...
  /**
   * Ключи payload, которые исполнитель может менять действием на этом шаге
   * (payloadPatch в executeAction). Отсутствует/пусто = менять нельзя ничего.
   */
  editableKeys?: string[];
}
```

Секьюрный дефолт: пустой список закрывает текущую дыру — патчи запрещены, пока админ явно не
разрешил ключи на конкретном шаге. Ключи — свободные строки (движок не знает форм потребителя,
это ключи payload; сверка с полями формы типа — сознательно не здесь, см. «известное ограничение»
про переименование ключей в плане hr-requests).

### A2. Движок: enforcement + дифф

`engine.ts`, в `executeAction` перед применением патча:

- если `options.payloadPatch` непуст — проверить, что все его ключи ⊆ `node.editableKeys`;
  нарушение → `InvalidActionError` с перечислением недопустимых ключей (по образцу
  `delegateError` — в сообщении нода и ключи);
- после применения посчитать shallow-diff (только реально изменившиеся ключи, формат
  `{ key: { from, to } }`) и записать его в audit-строку самого действия (не в хопы).

Схема: новая колонка `workflow_audit_log.payload_diff jsonb` (nullable) — миграция
`0001_audit_payload_diff_actor_type.sql` в `module-workflow/migrations` (совмещаем с B, см. ниже).

### A3. Багфикс симметрии payload (нужен и для C)

`startProcess`: после `advance` сохранять `ctx.payload` в instance (сейчас insert идёт до
advance — мутации serviceTask-провайдера теряются; в `executeAction` уже сохраняется после).
Контракт делегата: мутация `ctx.payload` по ссылке — **благословлённый** способ serviceTask
вернуть данные процессу (задокументировать в `contracts/registry.ts` на `ServiceTaskProvider`).

### A4. Редактор: поле «Редактируемые ключи payload»

`properties-panel.tsx`, секция userTask: текстовое поле со списком ключей через запятую (тот же
минимализм, что редактор options у select в типах заявок) → `editableKeys: string[]`.

### A5. hr-requests: UI доработки + дифф в таймлайне

- `GET /hr-requests/:id` дополнительно отдаёт `editableFields: string[]` — `editableKeys` текущей
  ноды, если `isAssignee`, иначе `[]` (роут уже загружает конфиг и текущую ноду).
- Карточка (`request-card-page.tsx`): если `editableFields` непуст — соответствующие поля формы
  рендерятся редактируемыми (остальные readonly), изменённые значения уходят как `fields` вместе
  с действием (роут actions уже прокидывает их в `payloadPatch` и синхронизирует
  `hr_requests.fields` — менять не надо; при недопустимых ключах движок откатит транзакцию
  целиком, десинка не будет).
- Таймлайн (роут `:id` уже читает `workflow_audit_log`): добавить `payloadDiff` в выборку;
  карточка рендерит «Изменены поля: Стоимость: 15000 → 25000» (ключ → label через `formFields`
  типа, неизвестный ключ — как есть).

Сценарий доработки собирается из готовых деталей: ребро «на доработку» → userTask
(assignee `process-initiator`, `editableKeys: [нужные ключи]`, label «На доработке») → автор
правит поля и жмёт действие «Отправить снова».

## Фаза B — модель актора (вместе с A)

- **UI (обе таймлайн-страницы)**: при `action === 'auto'` показывать реального актора
  (`actorLogin` уже в данных) + пометку «авто» вместо слова «система». Семантика: авто-переход
  атрибутируется тому, чьё действие его вызвало (инициатору каскада) — так уже пишет движок.
- **Схема (та же миграция, что A2)**: `workflow_audit_log.actor_id` → nullable;
  новая колонка `actor_type varchar(10) NOT NULL DEFAULT 'user'` (`'user' | 'system'`).
  Сегодня движок везде пишет `'user'`; `'system'` + `actor_id IS NULL` зарезервированы для
  фазы C (таймеры, фоновая автоматика). Джойны таймлайнов на `identity_user` станут LEFT JOIN
  (актор может быть NULL) — поправить оба роута (`processes.ts`, hr-requests `:id`).
- Делаем сейчас, пока данных в таблице мало и NOT NULL → nullable бесплатен.

## Фаза C — асинхронная автоматика (направление; реализовывать при первом реальном потребителе — ИИ-проверка, интеграции, уведомления)

Дизайн зафиксирован, чтобы не перепроектировать:

- **Новый тип ноды `asyncTask`** — третье wait-state наряду с userTask/end (`current_state` может
  на ней останавливаться). Поля: `providerId`, `params`, политика ретраев.
- **`settle`** на asyncTask: создать запись в новой таблице `workflow_automation_jobs`
  (`process_instance_id, node_id, status pending|running|done|failed, attempts, last_error`) и
  закоммитить. Отдельная таблица, а не `workflow_tasks` — там `assignee_id NOT NULL` и смысл
  другой (человеческая задача).
- **Воркер** через task-scheduler ядра: забирает pending-джобы, исполняет провайдера **вне
  транзакций движка** (долго, с ретраями — можно), затем зовёт новый метод
  `engine.completeAutomationJob(jobId, { payloadPatch })` — тот в собственной транзакции
  применяет патч, пишет audit с `actor_type='system'`, `actor_id=NULL` и продолжает `advance`.
  Исчерпаны ретраи → `failed`, процесс стоит на asyncTask-ноде, виден в админке (страница джобов,
  ручной retry).
- **ИИ-кейс** (ответ на вопрос из todos: да, встраивается): делегат в будущем модуле
  (module-ai/module-integrations — движок про ИИ не знает), промпт типа «оцени обоснование
  0–10, ответь числом» → `payloadPatch: { aiScore }` → Gateway `payload.aiScore >= 5` →
  согласовано / на доработку. «Костыльный» вариант через текущий sync-serviceTask технически
  заработает после A3, но не рекомендуется (лок под FOR UPDATE на время LLM-вызова, ошибка LLM —
  в лицо пользователю); sync-serviceTask остаётся для быстрых локальных действий.

## Фаза D — i18n (принцип, кода нет)

Не делаем до платформенного i18n (отдельный пункт todos). Принцип: **код стабилен, label —
дефолтная презентация**. Статус = `node.id`, действие = `edge.action` — оба стабильны и не
переводятся. Когда появится i18n — слой перевода `(workflowCode, nodeId|action, locale) → label`
поверх конфига (таблица или json в Document workflow), резолв label'ов уже изолирован
(`resolveRequestStatus`, `nodeLabels` в API) — точек замены мало. Миграций не потребуется.

## Фаза E — обобщение под оценку (принцип, кода нет)

Не строим фреймворк впрок. Когда стартует модуль оценки:

- оценка = **свой модуль со своим API поверх engine** — ровно паттерн hr-requests (свои таблицы,
  свой вычисляемый статус из label'ов нод, движок in-process через `WORKFLOW_ENGINE_TOKEN`);
- концепция «полей» выносится в общее место (контракт `FormField` + `GenericForm`-рендерер,
  сейчас — `RequestFormField`/`GenericRequestForm` в hr-requests) — снимать кальку с живого кода,
  не проектировать вслепую;
- расширение данных другими модулями (360-компетенции) — точки расширения в сервисе модуля
  оценки: пайплайн load/save по образцу `DocumentExtension` админки;
- в этот момент — ADR «концепция полей» (что такое поле, политика редактируемости, как применяется
  в заявках/оценке).

Новых npm-пакетов и инфраструктуры нет. Одна миграция в `module-workflow`.

## Проверка (руками, сквозная — сценарий доработки)

1. В граф `external-training` добавить: из «На согласовании у руководителя» ребро
   `rework`/«На доработку» → userTask «На доработке» (assignee `process-initiator`,
   `editableKeys: ["cost","description"]`) → ребро `resubmit`/«Отправить снова» → обратно на
   согласование. Опубликовать новую версию.
2. Подать заявку (cost 50000) → согласующий жмёт «На доработку» → заявка приходит автору,
   статус «На доработке», поля cost/description редактируемы, link — readonly.
3. Автор меняет cost на 15000, «Отправить снова» → в таймлайне «Изменены поля: Стоимость:
   50000 → 15000»; Gateway уводит по ветке `< 20000`.
4. Негативный: `POST /:id/actions/... { fields: { link: "..." } }` на шаге согласования (ключ вне
   `editableKeys`) → 4xx с перечислением недопустимых ключей, payload и `hr_requests.fields` не
   изменились.
5. Таймлайн: auto-хопы показывают «{логин} (авто)», не «система»; на старых процессах (созданных
   до миграции) таймлайн не падает.
6. Инстансы, запущенные на старой версии графа (без `editableKeys`), продолжают работать: патчи
   на их шагах запрещены (пустой дефолт), действия без полей проходят.
