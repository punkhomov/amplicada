# Статическая композиция приложений

> Формат метаданных и семантика зависимостей заменены [ADR-06](06-module-conventions.md).
> Остальные решения об этапах сборки и lifecycle сохраняются.

## Контекст

Состав приложения повторялся в backend, frontend и CSS. Поле dependencies
существовало, но bootstrap его не использовал. HR требует workflow уже в setup,
а миграции заявок ссылаются на его таблицы. При этом apps — демонстрационные
приложения; реальные потребители устанавливают платформу и модули из npm.
Базовый сценарий должен обходиться без дополнительного списка модулей.

## Решение

По умолчанию состав определяется прямыми production dependencies приложения.
`@amplicada/application-tools` предоставляет независимый CLI `amplicada-modules`,
который читает package.json установленных пакетов. Обычные библиотеки без метаданных
и devDependencies не активируются. Turbo и структура данного репозитория не нужны.
Опциональный `--config` с modules/targets позволяет ограничить установленный состав
для отдельной задачи. Обычная сборка использует только dependencies; примеры конфигов
живут в fixtures тестов CLI, общей папки конфигураций приложений нет.
Версии, установка и совместимость пакетных зависимостей остаются задачей pnpm/lockfile.

Описание модуля хранится в секции `amplicada` его package.json: id, name, requires,
необязательные backend/frontend (имя экспорта и dependencies), необязательный CSS.
Генератор не импортирует код модулей и не требует их dist для чтения метаданных.
Модули получают runtime-манифесты из тех же данных.

Разделяем три графа: требования состава (`requires`), backend dependencies и frontend
dependencies. Requires проверяется при подготовке приложения; dependency каждой стороны
требует присутствия соответствующей стороны поставщика. Графы проверяются независимо:
порядок серверных сервисов не задаёт порядок UI. Дубликаты id, отсутствующие зависимости
и циклы отклоняются до записи generated-файлов.

В discovery обязательные поставщики ищутся среди dependencies/peerDependencies
потребителя и подключаются автоматически, если импортируются из приложения.
Если pnpm изолировал поставщика как вложенный пакет, пользователь добавляет его
в dependencies приложения. Генератор не устанавливает пакеты, не сканирует весь
node_modules и не привязывает imports к внутренним абсолютным путям .pnpm.
В явном профиле все модули перечисляются и устанавливаются в targets явно.

Перед build/dev/typecheck CLI пишет раздельные статические импорты backend,
frontend и CSS в `src/generated/`. Файлы не хранятся в git; однажды подключённые
точки входа не меняются при добавлении модуля. Оба runtime могут находиться в одном
проекте или в разных. Наши демоприложения вызывают CLI из своих scripts.
CLI и метаданные модулей учитываются стандартным dependency graph приложений в Turbo.
Глобальных inputs для профилей и переключения состава через окружение нет.
Generated outputs восстанавливаются с dist.

Оба bootstrap повторно проверяют и сортируют переданные им модули общей функцией
`sortModules`, затем регистрируют метаданные всего состава до первого setup. Setup и
start идут в порядке зависимости, shutdown — в обратном. Миграции регистрируются
синхронно во время setup и выполняются после всех setup: сначала core, затем модули.
Из setup нельзя запускать фоновые работы или обращаться к ещё не созданным таблицам.

Это заменяет **только** договорённость ADR-02 о декларативном dependencies без
исполнения. Service locator и extension points сохраняются; DI-контейнер не вводится.
Прямое подключение массивом модулей остаётся допустимым и тоже проверяется.

## Последствия

- Добавление модуля в зависимости, install и build достаточно для его подключения
  в подготовленное приложение. Отдельный конфиг состава необязателен.
- Runtime получает статические imports. Смена состава требует пересборки/перезапуска;
  во время dev изменение dependencies или профиля требует перезапуска команды dev.
- Пакеты включают dist, миграции и frontend-исходники для Tailwind source scanning.
  Внутренние UI-импорты относительные; JSON использует стандартные ESM import attributes.
  Потребителю не нужен alias на исходники платформы или TS-loader для backend dist.
- Неактивный модуль не проходит setup/start и не регистрирует миграции. Его библиотечный
  код может попасть в bundle через прямой импорт активного модуля; это отдельно от активации.
- Zero-config относится к композиции. Каркас приложения, настройки сборщика и окружение
  инфраструктуры пока настраиваются отдельно; команда create-amplicada здесь не вводится.
- Удаление данных, горячая выгрузка, собственные semver-ограничения модулей и анализ
  service tokens не входят в решение. Публикация пакетов в npm — отдельный выпуск.
- Данные и схемы БД не изменены; миграций и пропусков миграции данных нет.
