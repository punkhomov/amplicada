# ADR-07: Контракт уведомлений v2

## Context

[ADR-04](04-notifications.md) закрепил границу: ядро маршрутизирует и владеет надёжностью
(outbox, ретраи, ретенция), канальные модули — транспорт и адресные книги. Контракт первого
поколения минимален: `send({ userId, kind, subject, body, html?, channel?, locale? })`, контент
рендерит вызывающий.

Потребителей, которые уже запланированы, такое API не покрывает:

- **auth-password** — регистрация, сброс пароля, email-OTP: нужны шаблоны по коду с i18n и
  ссылками с токеном;
- **workflow** — «вам назначена задача»: шаблон с переменными и идемпотентность повтора
  бизнес-действия;
- **learning** — «за N дней до срока»: рассылка пачкой и отложенная отправка;
- **admin broadcast** — отправка сейчас циклом `send()` внутри HTTP-запроса, без батча в логе.

Дополнительно нужны: вложения, именованные отправители, конверты `cc/bcc/replyTo/headers`,
шаблоны, объявляемые кодом (fixtures), и read-only для таких шаблонов в админке.

Потребитель сейчас один — админская рассылка, поэтому контракт ломается без слоя совместимости;
данные одноразовые (политика проекта).

## Decision

1. **`NotificationContent` — union:** inline-контент, code-шаблон (`{ code, locale?, data? }`),
   документ-шаблон (`{ id, data? }`). Ядро резолвит шаблон, рендерит `{{path}}` по dot-path
   (html-часть — с экранированием подстановок; отсутствующая переменная → пустая строка + warn)
   и снапшотит результат в outbox — при ретрае контент не перерендеривается.
2. **Шаблоны — документ-тип ядра** `notification-template`; code-шаблоны объявляются fixtures
   модулей (одна fixture-строка = пара `(code, locale)`, перезапись из кода при bootstrap).
   Read-only guard действует **только у типов с `fixtureReadonly: true`** (у типа включён):
   `update`/`delete`/`bulkDelete` fixture-строки → 409. `scheduled-task` не затронут — его
   фикстуры редактируются.
3. **`sendMany` — батч** из одного `batchId`, по строке на получателя, **без eager**: доставку
   делает worker-диспетчер, ответ сразу `queued`, фактический статус — в логе; `retryBatch`
   повторяет `failed` строки батча. Одиночный `send` остаётся eager (кроме будущего `scheduledAt`).
4. **`dedupeKey`** — идемпотентность бизнес-действия: partial unique
   `(kind, dedupe_key, user_id)`; конфликт возвращает существующий id, дубль не создаётся.
5. **`scheduledAt`** — отложенная доставка: `next_attempt_at = scheduledAt`, eager не запускается.
6. **Вложения** — манифест `NotificationAttachment[]` в сообщении и в шаблоне; лимиты
   10 МиБ/файл и 20 МиБ/письмо одной константой `NOTIFICATION_ATTACHMENT_LIMITS`; на отправке
   канал проверяет реальный размер через `storage.headObject` и стримит объект в письмо.
7. **Именованные отправители:** `sender` в контракте, резолвит канал; неизвестное имя —
   warn + дефолтный `SMTP_FROM` (fail-open, чтобы опечатка не глушила транзакционные письма).
8. **Конверты:** `cc/bcc/replyTo/headers` в контракте и в outbox; явный `replyTo` сообщения
   приоритетнее sender-овского.

## Rationale

Отвергнутые альтернативы:

- **Слой совместимости с v1.** Данные одноразовые, потребитель один — переходник был бы мёртвым
  кодом с первого дня.
- **Шаблоны в `module-admin`.** Сборка без админки должна уметь слать по code-шаблону; тип
  обязан жить в ядре, админка — только UI.
- **Blanket read-only для fixture-документов.** Сломал бы редактирование `scheduled-task`
  (тоже fixtures) — поэтому guard включён флагом типа.
- **Eager для `sendMany`.** 200 получателей = 200 SMTP-отправок внутри HTTP-запроса; надёжность
  батча — забота диспетчера.
- **Контент на каждого получателя в `sendMany`.** Шаблон один на батч; данные — только
  `{{path}}`-подстановки.
- **Получатель-адрес/роль union-типом.** Нужно для `task.alert`, но модели прав пока нет — вне v2.
- **Цепочки каналов (email → sms).** Отдельный план.

## Consequences

- Ломающее изменение контракта и схемы: миграция core `0007`, переезд
  `admin.notification_template` → `core.notification_template`, событие завершения батча
  отложено. Данные одноразовые — формат БД ломается без миграции данных.
- `sendMany` требует worker-роль: на узле `ROLE=web` строки лежат `pending` до воркера;
  компенсация — лог доставок, trade-off фиксируется в docs/notes.
- Fixture-шаблоны — источник истины в коде: `reconcileFixtures` перезаписывает строку на
  bootstrap, ручная правка/удаление отклоняются.
- Вложения — объекты в storage: очистка best-effort при снятии вложения и hard-delete шаблона;
  orphan-объект допустим — он безвреднее незавершённого удаления.
- ADR-04 сохраняется в части границы «ядро маршрутизирует, каналы доставляют»; заменяются
  контракт сообщения и модель доставки (шаблоны, батчи, dedupe, расписание, конверты).
