# Модули по соглашениям и граф зависимостей пакетов

## Контекст

ADR-05 ввёл отдельное описание сторон, CSS, имён экспортов и трёх графов требований.
Exports и зависимости уже описаны в package.json. Все requires были пустыми.
Пользователь выбрал простой контракт с явным составом приложения и optional peers
для интеграций, которые не требуют установки другого модуля.

## Решение

В package.json модуля достаточно `amplicada: true`. Стороны определяются по наличию
`./backend` и `./frontend` в exports, стили — по `./frontend/tailwind.css`.
Обе стороны экспортируют объект регистрации под одинаковым именем `module`.
Стабильные id и отображаемые названия остаются в contracts/manifest.ts; version
читается из package.json. Старые id, включая `hr-requests`, не переименовываются.

Состав — модули в production dependencies приложения или полный список в `--config`.
Все выбранные модули должны быть прямыми dependencies приложения. Генератор читает
их dependencies и обязательные peerDependencies: если зависимость является модулем,
она должна быть включена в состав, иначе выдаётся ошибка с именем поставщика.
Обычные библиотеки не активируются, их вложенные зависимости не обходятся.
DevDependencies и optionalDependencies не задают состав или порядок модулей.

Optional peer (`peerDependenciesMeta[name].optional: true`) может отсутствовать.
Если он явно включён в состав, генератор добавляет связь порядка: setup поставщика
завершается до setup потребителя. Это касается и циклов: optional-связи между выбранными
модулями участвуют в обычной проверке цикла. Наличие только в node_modules не активирует peer.

Один граф по именам npm-пакетов определяет порядок для обеих сторон. Из отсортированного
графа выбираются модули с соответствующим экспортом. Цикл прерывает генерацию до записи.
Generated-код импортирует `module` и добавляет runtime dependencies по id импортированных
объектов; при промежуточном модуле без нужной стороны сохраняется порядок его предков.
Это позволяет bootstrap повторно проверить id/зависимости без дублирования списков автором.
Дубликаты runtime id проверяются bootstrap; генератор не исполняет код для чтения id.

Зависимости разрешаются относительно объявившего их пакета. Разные установки одного
модуля в графе отклоняются, чтобы не получить разные экземпляры сервисов/регистров.
Generated imports используют публичные npm subpaths. Генератор не пишет пути внутрь
.pnpm и не меняет package.json/node_modules. Поиск ограничен локальными node_modules
относительно потребителя, без NODE_PATH: окружение CLI не должно подменять видимость
пакетов приложения. Это обнаружено проверкой архивов вне монорепозитория.

Опциональные прямые вызовы сервисов допустимы: потребитель проверяет
`context.modules.getById(id)`, затем получает сервис через `context.services.resolve()`.
Поставщик обязан зарегистрировать сервис в setup соответствующей стороны. Метаданные
модуля сами по себе не являются статусом готовности: гарантию даёт объявленная связь
и последовательное ожидание setup. Сервисы, создаваемые только в start, эта гарантия
не покрывает. API статусов модулей отложен.

Интерфейсы импортируются через `import type` из contracts; пакет поставщика нужен
автору в devDependencies для компиляции. Импортов реализации опционального peer быть
не должно. Ссылки на его типы не должны утекать в публичный граф .d.ts потребителя.
Extension points из ADR-02 остаются механизмом вкладов без прямого вызова поставщика;
они больше не единственный разрешённый механизм опциональной связи.

Прямое ручное подключение runtime-объектов остаётся низкоуровневым API: без генерации
вызывающий код отвечает за полный состав и dependencies. Исходный объект `module`
сам по себе не читает граф установленных пакетов.

## Последствия

- HR требует явного включения workflow. Auth работает без admin; при включённом admin
  регистрирует действие смены пароля через frontend-сервис `admin:toolbar`.
- Общие утилиты без активации модуля следует выносить в обычный библиотечный пакет.
  Необязательная интеграция использует optional peer с type-only импортами и контекстом
  либо extension point. Специальный флаг выключения dependency не вводится.
- Объектная секция amplicada, requires, списки зависимостей по сторонам и отдельное
  описание CSS удалены. Старый формат метаданных отвергается с явной ошибкой.
- Семантика --config: выбирается полный состав, обязательные зависимости нельзя пропустить.
  Все выбранные пакеты должны быть объявлены в dependencies каждого target.
- Поиск и проверка графа остаются на этапе сборки. Runtime получает статические импорты;
  setup/start идут по зависимостям, shutdown в обратном порядке. Остальная часть ADR-05 действует.
- Данные и схемы БД не меняются, пропущенных миграций данных нет.
