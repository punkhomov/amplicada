# Документация пакетов amplicada

Два слоя, две аудитории. Никогда не смешивай их в одном файле.

| Слой | Аудитория | Содержание | Где |
|---|---|---|---|
| Consumer docs | Потребители пакета: другие модули, админы, конечные пользователи | Что умеет, как пользоваться, справочник фактов, концепции | `packages/<package>/docs/` |
| Developer notes | Разработчики и агенты, которые будут менять пакет | Почему сделано так; отвергнутые альтернативы; отложенное; грабли | `ref/notes/<package>.md` |
| ADR | Платформа целиком | Кросс-модульные решения | `ref/adr/NN-*.md` |
| Plans | История | Намерения на момент написания; источником истины не являются | `ref/plans/` |

Приоритет при противоречии: **код (`src/`) → ADR → notes → plans**. Если документ противоречит коду — прав код.

Этот скилл заменяет общий скилл `documentation` (Diátaxis) для `packages/*/docs/`. Не используй generic-схему «четыре файла»: набор страниц определяется покрытием подсистем (см. ниже).

## 0. Перед предложением изменений в пакет (обязательно)

1. Прочитай `packages/<package>/docs/index.md` — границы, публичная поверхность, ограничения.
2. Прочитай `ref/notes/<package>.md` — стоп-лист повторных предложений, решения (`accepted` / `rejected` / `deferred` / `gap`).
3. Если твоё предложение совпадает с `rejected` / `deferred` / `gap` — не предлагай его молча. Варианты: отказаться; либо привести новые факты и оформить новую запись, которая `supersedes` старую. Отвечать на записанную причину обязательно.
4. Планы в `ref/plans/` — история, а не истина. Проверяй по коду.

## 1. Consumer docs — `packages/<package>/docs/`

### Когда создавать/обновлять

- Новый пакет — создать `docs/index.md`, минимум один `reference/` по публичной поверхности.
- Изменение кода — обновить затронутые страницы и freshness-штамп.
- Пакет потребляется извне — reference обязан покрывать токены, роуты, типы, схемы, env.

### Структура

```
packages/<package>/docs/
├── index.md          # карточка пакета + карта docs + карта покрытия + freshness
├── tutorial.md       # ровно один; первый контакт
├── how-to/
│   ├── index.md      # индекс задач
│   └── <task>.md
├── reference/
│   ├── index.md
│   └── <subsystem>.md
└── explanation/
    ├── index.md
    └── <concept>.md
```

Индексы директорий — именно `index.md` (VitePress резолвит `folder/` → `folder/index.md`; `README.md` он индексирует как обычную страницу). Все ссылки между страницами — относительные на `.md`.

### Правила контента

- Одна страница = один тип Diátaxis. Tutorial учит, how-to решает задачу, reference сообщает факты, explanation объясняет концепцию. Не смешивать.
- Язык — русский; идентификаторы кода — как в коде. Имена файлов — латиница, kebab-case.
- Каждый нетривиальный факт (токен, роут, env, таблица, тип, порядок) — со ссылкой на код `src/...:NN`. Не писать по памяти, не пересказывать план.
- Контринтуитивные факты фиксируй явно (пример: `undefined` в частичном сохранении означает «поле не трогать», а не «обнулить»).
- Ограничение, важное потребителю («не поддерживает X», «требует прав», «известный дефект») — в docs; его рационал и отвергнутые варианты — в notes (упоминание в backticks, без относительной ссылки: docs должны собираться VitePress'ом отдельно от `ref/`).
- В docs не место: TODO-планам, внутренним спорам, истории рефакторингов, «мы пока не сделали Y, потому что...» — это `ref/notes/`.
- Не перегенерировать файл с нуля: точечно обновлять существующее.
- Порог деления страницы: > ~200 строк или > 5 H2 → отдельный файл. После деления обнови `index.md` (карту docs и покрытия) и `index.md` раздела.
- Картинки и вложения — `docs/assets/`, относительными ссылками.

### Карта покрытия (заполняется в `index.md`)

Пройди по подсистемам пакета и для каждой поставь ссылку или явное «— нет». Подсистемы: точки расширения (сервисы/токены/extension points), HTTP API, схема БД и миграции, документы/списки/дашборд, задачи и фоновые процессы, frontend (FSD, роуты, слоты), конфиг (env, зависимости, порядок загрузки), интеграции и потребители, ограничения для потребителя. Карта должна показывать дыры, а не умалчивать.

### VitePress-ready (обязательно)

Сайт документации будет собираться VitePress'ом из этих же файлов:

- директорные индексы — `index.md`;
- только чистый Markdown: без HTML/JSX и платформенных вставок;
- относительные ссылки на `.md` (`./reference/schema.md`, `../explanation/foo.md`); VitePress роняет сборку на битой внутренней ссылке;
- front matter в каждом файле: `title`, `type` (`index` / `tutorial` / `how-to` / `reference` / `explanation`), `updated` (дата сверки), `verified_commit`; опционально `order` для сайдбара;
- один H1 на файл, совпадает с `title`; заголовки стабильные, анкоры предпочтительно не использовать в кросс-файловых ссылках;
- имена файлов латиницей — URL остаются читаемыми.

## 2. Developer notes — `ref/notes/<package>.md`

Канонический формат, легенда статусов, шаблон записи и правила — `ref/notes/README.md`. Прочитай его перед первой записью.

Когда записывать (после любой нетривиальной работы):

- неочевидное решение — почему так, а не иначе;
- отвергнутая альтернатива — чтобы её не предложили повторно;
- сознательно отложенное или известный пробел;
- грабли, которые дорого выяснять заново.

Правила:

- append-only: старые записи не удаляются и не переписываются;
- смена решения = новая запись + `superseded_by` у старой;
- у каждой записи: статус, контекст, решение, почему, отвергнутые альтернативы, что изменит решение, грабли, ссылки на код и ADR/планы;
- сверху файла — стоп-лист самых вероятных повторных предложений со статусами и ссылками на записи;
- пакетное/кросс-модульное решение, меняющее контракт платформы, — это ADR (`ref/adr/`), в notes только ссылка.

## 3. После работы — обновить карты

- `packages/<package>/docs/index.md`: карта docs, карта покрытия, freshness.
- `ref/notes/<package>.md`: новая запись, стоп-лист, дата.
- `packages/<package>/README.md`: таблица документации ведёт на `docs/index.md` и страницы.
- `ref/README.md`: карта notes и модульной документации — при появлении/переименовании файлов.
- `ref/context.md`: ключевые слова — при появлении новой публичной поверхности.

## 4. Шаблоны и проверка

- Шаблоны страниц и front matter — `references/docs-templates.md`.
- Чек-листы (разведка, сверка с кодом, anti-reproposal, ссылки, VitePress) — `references/checklist.md`.
