# Amplicada

**Amplicada** — не приложение. Это **каркас** (framework) для сборки предсказуемых, расширяемых бизнес-приложений из готовых модулей.

Модули — npm-пакеты. Клиентская сборка формируется на этапе `pnpm build` **статически**, без runtime-загрузки. Это даёт:

- **Robust + Predictable** — никакой динамической магии. Модули определяются по `dependencies` приложения; lockfile фиксирует версии. Отдельный конфиг состава необязателен.
- **CI/CD-friendly** — обычный `pnpm build`, обычный `docker build`, обычные тесты. Нет runtime-регистрации плагинов по URL из БД.
- **Vendor Updates** — вендор выпустил новую версию модуля или core → `pnpm update @amplicada/module-*`. Без форков, без копирования кода.

## Чем это не является

### ❌ «Форкни платформу и тащи обновления через страшный мердж»

В других платформах клиентский проект — это форк. Вендор выпустил обновление — разработчик мерджит свою кастомизацию с апстримом. Чем дальше, тем больше рассинхронизация, тем сложнее конфликты.

**Amplicada:** кастомизация — отдельные npm-пакеты (`@amplicada/module-*`). Обновление core — `pnpm update @amplicada/platform-core`. Ваш код не смешан с кодом платформы — нечего мерджить.

### ❌ «Код в БД и конфиги в админке»

Другие системы хранят логику (скрипты, триггеры, плагины, маршруты, права, темплейты) в БД или редактируют через админку. Разработчик лезет в UI, чтобы понять, как вообще работает приложение.

**Amplicada:** весь код — в репозитории. Обычный TypeScript, обычный `git`, обычный код-ревью, обычный CI/CD. Ничего не надо тащить в админку — она для админов, а не для разработчиков.

### ❌ «Своя вселенная: свой DI, своя конфигурация, свой DSL, свои тулы»

Некоторые платформы приносят с собой целый стек собственных абстракций: DI-контейнеры с декораторами, AOP, runtime-расширение схемы данных, свой язык запросов. Разработчик учит платформу, а не пишет приложение.

**Amplicada:** платформа работает **с** Fastify, React, Drizzle, а не **поверх** них. Никакого собственного DI, никаких декораторов, никакого `reflect-metadata`, никаких generic-абстракций. Разработчик использует знакомые инструменты — TypeScript, Fastify, React, Drizzle — и не лезет в админку, чтобы добавить кнопку или маршрут.

### ❌ «Гипер-динамичность ради динамичности»

Runtime-загрузка модулей, визуальные конструкторы, «адаптивная» логика, прослойки на каждую операцию — всё это даёт иллюзию гибкости, но на деле создаёт недетерминированное поведение: трудно тестировать, трудно дебажить, трудно понять, что вообще произойдёт при переходе по URL.

**Amplicada:** статическая композиция на `pnpm build`. Генератор читает метаданные модулей из production dependencies и создаёт отдельные backend/frontend-импорты и CSS. Runtime получает готовый состав.

### ❌ «Платформа, которая блокирует разработку»

Некоторые платформы диктуют, как писать код, заставляют использовать только их API, только их экраны, только их способ расширения. Выход за рамки — боль и танцы с бубном.

**Amplicada:** с платформой вы получаете обычный web-приложение, работающий по тем же правилам, что и классический React + Fastify проект. Хотите свой экран, не вписывающийся в модульную систему? Просто добавьте `<MyPage />` в app. Хотите свой API-эндпоинт без модуля? Напишите обычный Fastify handler. Платформа не блокирует — она предоставляет готовые блоки, но не запрещает ничего сверху.

## Как это выглядит

В подготовленном приложении добавьте модуль в `dependencies`, выполните `pnpm install`,
`pnpm build` и запуск. Команда `amplicada-modules` из пакета
`@amplicada/application-tools`, подключённая к build/dev scripts, сама создаст imports
и CSS. Точки входа не требуют изменений при добавлении модулей.

CLI работает и вне монорепозитория с установленными пакетами. В этой ветке пакеты
подготовлены для `pnpm pack`; публикация в npm отдельно. Обычные настройки сборщика
и инфраструктуры пока остаются в приложении.

[Подключение модулей во внешнем проекте](ref/guides/application-composition.md).
Прямое подключение массивом в bootstrap также поддерживается.

## Состав

| Пакет | Назначение |
|-------|-----------|
| `@amplicada/platform-core` | Инфраструктура: роутинг, auth, registry, event bus, миграции, документы |
| `@amplicada/module-auth-password` | Аутентификация по паролю (bcrypt + server sessions) |
| `@amplicada/module-hr` | HR-сущности (сотрудники, должности, отделы) |
| `@amplicada/module-hr-request` | Портал заявок поверх workflow |
| `@amplicada/module-workflow` | BPM-движок: процессы, ноды, переходы, делегаты |
| `@amplicada/module-admin` | Management UI над core-инфраструктурой |

## Разработка: инфраструктура в Docker, приложение на хосте

Нужны Docker Compose, Node.js и pnpm версии из `package.json`. Инфраструктура и приложения запускаются отдельно:

```bash
pnpm install
pnpm infra:up
pnpm dev
```

Откройте `http://localhost:5173`; API доступен на `http://localhost:3000`. `pnpm dev` запускает watcher'ы только для `apps/api` и `apps/web`; существующая зависимость `^build` в Turbo соберёт их пакеты при старте. После изменения пакета пересоберите его вручную: `pnpm --filter @amplicada/module-hr build` (подставив его имя), затем при необходимости обновите страницу.

Локальные адреса и учётные данные API берёт из `.env.host.example`; переменные, заданные в окружении, имеют приоритет. Данные инфраструктуры сохраняются в Docker volumes.

`pnpm infra:down` останавливает инфраструктуру.
